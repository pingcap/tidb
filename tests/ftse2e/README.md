# Local TiFlash Boolean MATCH E2E

This suite derives fixed result sets from `endless/testcase/fts/function` and `endless/testcase/fts/mysql-test2`. It verifies the real TiDB → TiFlash Boolean-filter execution path, not the TiCI inverted-index path. It creates and drops only a uniquely named `fts_e2e_` schema. It does not start a cluster, modify the QA repository, or change global system variables. The DSN must connect over local TCP or a Unix socket.

Start a dedicated TiUP playground using the current TiDB and TiFlash builds:

```bash
make server
tiup playground v8.5.8 --without-monitor --db 1 --kv 1 --pd 1 --tiflash 1 --db.binpath "$PWD/bin/tidb-server" --tiflash.binpath /Users/solotzg/Work/tiflash/cmake-build-fts-apple/dbms/src/Server/tiflash
```

In another terminal, run:

```bash
TIDB_FTS_E2E_DSN='root@tcp(127.0.0.1:4000)/?charset=utf8mb4' go test ./tests/ftse2e -run '^Test(BooleanMatchTiFlashE2E|LocalMatch.*TiFlashE2E)$' -count=1 -v
```

Without `TIDB_FTS_E2E_DSN`, the cluster tests skip. They print `tidb_version()`, create matching tables with and without a TiFlash replica, wait for `information_schema.tiflash_replica.AVAILABLE=1`, and check both plans and fixed expected row IDs. Supported native queries must use an MPP TiFlash `TableFullScan` or `TableRangeScan` and evaluate MATCH in an MPP TiFlash `Selection` with no root MATCH residual; unrelated root selections are allowed. Queries on the no-replica tables must retain MATCH in a root Selection over TiKV. No tested path may use TiCI. The shared plan validator also accepts root MATCH above a TiFlash scan when a test explicitly expects TiDB fallback; scan placement alone never proves scalar pushdown. Result IDs are sorted by the test runner rather than by SQL, because SQL `ORDER BY` can change the chosen TiFlash plan. The 44-case default matrix covers required/excluded terms, phrase, prefix, NULL, composite-column MATCH including reordered columns, five multi-MATCH combinations (OR, AND, AND NOT, OR over composite MATCH columns, and NGRAM AND), rejected duplicate columns, committed INSERT/UPDATE/DELETE, Chinese NGRAM and prefix matching, five collations, and a compound MATCH across binary and case/accent-insensitive collations. MATCH must use the complete column set of one public FULLTEXT definition; separate single-column definitions do not suffice. The NGRAM cases require `ngram_token_size=2` and skip with an explicit message otherwise.

The suite leaves `tidb_allow_mpp`, `tidb_allow_tiflash_cop` and `tidb_enforce_mpp` unchanged and checks their native-session values are the defaults ON/OFF/OFF. The review regressions reuse binary-protocol prepared statements across integer, string, and NULL search parameters. Statement summary checks the sampled executed non-NULL MATCH plans, requiring TiFlash MPP evaluation with no root MATCH residual. This branch's legacy plan codec decodes MPP nodes as `cop[tiflash]`; such labels are accepted only for decoded summaries that also contain the MPP TableReader/ExchangeSender envelope, not as permission to execute actual cop/batchCop plans. This requires the test cluster's `tidb_enable_stmt_summary` to be ON (the test checks it without changing GLOBAL variables). It avoids the stale plan returned by this branch's `EXPLAIN FOR CONNECTION` after binary EXECUTE and the independent argument rewriting performed by a prepared EXPLAIN. STANDARD split prefixes such as `+foo.bar*`, `foo.bar*`, and `baz -foo.bar*` are tested separately: MATCH must remain in a root Selection, even if the replica supplies the table scan, and results must match the no-replica TiDB evaluator. These split-prefix terms are not currently eligible for TiFlash scalar pushdown.

The token-semantics matrix also checks ordinary STANDARD split words (`foo.bar`, `+foo.bar`, and `baz -foo.bar`), phrases across delimiters and supplementary characters. Local MATCH semantic protocol version 2 restricts STANDARD words and the NGRAM Boolean query lexer to BMP Unicode 15.0.0 letters/numbers plus ASCII underscore. NGRAM document scanning instead retains all valid multibyte characters, including punctuation, emoji and supplementary characters; ASCII non-word bytes separate runs, invalid UTF-8 truncates the document, and runs shorter than the gram size emit neither grams nor positions. Filtered phrases discard leading filtered query tokens but verify every following token against the unfiltered document stream. `AGAINST(NULL)` returns non-NULL zero. Required terms removed by the analyzer still match nothing, consistent with the actual MySQL InnoDB oracle. TiDB strictly tests Go's `unicode.Version == "15.0.0"`; TiFlash uses its generated L/N range table. Both verify the unchanged full-range helper fingerprint `71f51f3810b3b529`, a regression guard rather than a security primitive. The helper checksum does not describe the complete parser-specific rules. These Unicode cases support token sizes 2 and 3 without changing GLOBAL variables. Version 1 is rejected by both decoders; deploy version-2 TiFlash support before version-2 TiDB.

`TestLocalMatchReviewFixesTiFlashE2E` additionally verifies that every column within one composite MATCH has the same collation. Mixed column collations return error 1235 for either column order, including NULL/empty searches, on both the replica and no-replica tables; independent MATCH expressions may still use different collations. It checks both orders under five homogeneous collations and filtered-phrase verification across rows, columns, NULLs and separate required/prohibited clauses, including an 81,920-byte repetitive miss. TiFlash caches failed raw phrase verification only for the current row, column and clause; positive clause matches still accumulate across columns. The C++ regression counts comparisons to detect repeated full-column verification without asserting a wall-clock SLA.

Local MATCH disables prepared and non-prepared plan reuse for both TiDB fallback and TiFlash placement, even for a literal AGAINST value. Analyzer settings are captured at planning time, so changing stopwords or server collation must rebuild the plan. The force-plan-cache fix control cannot override this correctness restriction; ordinary SQL still uses its existing cache policy. The per-signature compiled-query cache inside one execution is unchanged. `TestLocalMatchPlanCacheTiFlashE2E` repeatedly executes binary prepared statements while switching stopword ON/OFF, server BIN/CI collation and NULL/non-NULL parameters, for STANDARD/NGRAM and replica/no-replica tables. It asserts fixed results and `@@last_plan_from_cache=0`, and inspects sampled executed MATCH plans for actual TiFlash Selection or TiDB fallback.

`TestLocalMatchStopwordLookupTiFlashE2E` checks 320 result-and-plan cases against both the unchanged Go matcher and TiDB SQL fallback. It varies STANDARD/NGRAM, two MATCH column collations, five independently selected server stopword collations, and stopwords ON/OFF. The corpus includes case/accent/full-width variants, NGRAM stopword substrings, NULL and filtered phrases. It reads the cluster's current token sizes without changing GLOBAL settings; repeat on a dedicated size-3 cluster for that configuration. Every supported native case must place MATCH in a TiFlash MPP Selection after the replica becomes ready.

`TestLocalMatchRangesTiFlashE2E` covers STANDARD/NGRAM with and without a replica: inclusive/exclusive primary-key bounds, BETWEEN, disjoint ranges, signed INT minimum/maximum, ranges containing no stored keys, and ranges containing only excluded/NULL documents. The 32 result-and-plan cases require an actual TiFlash `TableRangeScan` for each native query; the ranges come from primary-key predicates, not an FTS index. Four contradictory ranges instead require a scan-free `TableDual` plan and an empty result; TiDB fallback may retain an unevaluated root Selection above it, so these are not pushdown evidence. Another 48 binary prepared executions vary both bounds and AGAINST, including empty and contradictory intervals followed by a nonempty interval; all assert fixed results and zero plan-cache hits. Statement summary verifies sampled executed prepared range plans, not every parameter binding. `TestMatchPlanValidation` runs without a cluster and guards 19 positive/negative plans, including unrelated root filters, forbidden root MATCH residuals, missing MATCH, incorrect scan placement, TiCI, cop/batchCop rejection and the required MPP envelope for decoded summaries.

Generate or verify TiFlash's header from the paired TiDB checkout (the generator uses only Go's standard library and enforces the fixed Unicode version and helper fingerprint):

```bash
go run ./pkg/expression/matchagainst/generator -output /path/to/tiflash/dbms/src/Functions/LocalMatchAgainstTokenChars.h
go run ./pkg/expression/matchagainst/generator -check -output /path/to/tiflash/dbms/src/Functions/LocalMatchAgainstTokenChars.h
```

`-check` never writes the file and fails on a missing or different header. Run it for paired changes; ordinary Go unit tests do not require another repository to be present. A future Unicode classification change requires a new semantic protocol version supported and deployed by TiFlash before TiDB adopts it; do not just update the version assertion or checksum.

The extended tests add 480 deterministic differential queries (seed 70484/70485) across STANDARD/NGRAM, five MATCH and server collations, and stopwords ON/OFF. They require matching row IDs and TiFlash Selection plans. The snapshot test holds both read transactions open across seven commits on another connection, checks repeatable-read results against newly committed results, and replays a historical `tidb_snapshot`. These are controlled overlapping transactions, not a randomized concurrent stress test. The large-document test checks seven queries over 991,242 bytes of MEDIUMTEXT, including a 1,028-byte Boolean search, and logs single-run wall times. It asserts correctness and plans, not a latency SLA.

`TestLocalMatchTokenMemoryTiFlashE2E` adds opt-in concurrent token-memory stress: two MATCH columns, large/short/NULL/empty rows, STANDARD/NGRAM, binary/general-ci collation, stopwords ON/OFF, and phrase/prefix/miss queries. Each of eight configurations verifies TiDB fallback results and native MPP plans before 48 query executions on four native connections. Enable it with `TIDB_FTS_MEMORY_STRESS=1`; documents default to approximately 1 MiB and can be bounded with `TIDB_FTS_MEMORY_BYTES=262144`. It runs on the current NGRAM size and never changes GLOBAL settings. Repeat sizes 1/2/3 separately on a dedicated server and collect external process RSS/VmHWM as described in the [h124 harness](scripts/h124/README.md#bounded-token-memory-stress). Passing this test is not an allocation/leak or production memory-limit guarantee.

To test legacy collation semantics, bootstrap a separate playground with a TiDB configuration file containing `new_collations_enabled_on_first_bootstrap = false`, then run:

```bash
TIDB_FTS_LEGACY_E2E_DSN='root@tcp(127.0.0.1:4401)/?charset=utf8mb4' go test ./tests/ftse2e -run '^TestLegacyCollationLocalMatchTiFlashE2E$' -count=1 -v
```

This test verifies the persisted bootstrap mode, case-sensitive matching and built-in stopword lookup, and root Local MATCH evaluation both with and without a replica. Old-collation mode is not currently eligible for TiFlash scalar pushdown; TiFlash may still supply the scan. The test cannot change the mode of an already bootstrapped cluster.

Index-bound analyzer configuration, custom stopword tables, TiCI `IndexRangeScan`, and FTS selectivity statistics are outside this brute-force pushdown suite.

## Real MySQL compatibility oracle

Start a dedicated local MySQL 8.0.44 InnoDB instance, then run the three-way comparison:

```bash
MYSQL_FTS_E2E_DSN='root@tcp(127.0.0.1:33060)/?charset=utf8mb4' TIDB_FTS_E2E_DSN='root@tcp(127.0.0.1:4406)/?charset=utf8mb4' go test ./tests/ftse2e -run '^TestLocalMatchMySQLCompatibility$' -count=1 -v
```

This opt-in test compares 680 queries (34 searches × STANDARD/NGRAM × five collations × stopwords ON/OFF) against real MySQL FULLTEXT results and the Go matcher. With both DSNs it also checks TiDB fallback and actual TiFlash Selection plans, plus 40 NULL/NOT-NULL searches. Each connection must be local; only uniquely named test schemas are created/dropped. No GLOBAL configuration is changed by the suite. Both servers must have the same min/max token sizes and NGRAM size. Repeat with sizes 1/2/3; MySQL requires a startup configuration change for NGRAM size, whereas the dedicated TiDB cluster can be configured before the run. Restore any setup changes afterward. Omitting the TiDB DSN runs just the MySQL/Go oracle. This finite matrix is not proof of complete MySQL FTS compatibility.

## Reusable benchmark inputs and microbenchmarks

For a server-side TiUP cluster and persistent-connection SQL measurements, use the [h124 harness](scripts/h124/README.md). Its bundle contains Linux amd64 SQL and E2E executables, owned cluster lifecycle commands, replica-ready corpus setup, result/plan verification, alternating TiDB/TiFlash measurements and process samples. Preparing this bundle does not run a cluster or establish performance results.

The Go and C++ cases use identical four-row corpus units (match, excluded match, uppercase variant, miss), padded without splitting UTF-8 to 128 B, 4 KiB or 256 KiB. The matrix covers STANDARD, NGRAM 2/3, binary/general-ci collation, builtin stopwords ON/OFF, required/excluded terms, phrase, prefix and analyzer-filtered required terms. Each runtime has 144 row/block cases. Go also compares separate parsing with shared-AST planning (short and long searches). These are microbenchmarks, not SQL/MPP acceleration measurements: Go compiles the query before timing and measures per-row document construction/matching; C++ measures 16-row scalar blocks including the production per-block query compilation. The reported byte rates refer to input size, not bytes actually tokenized when a query matches nothing.

Local smoke checks reuse the existing builds; one Go iteration or a short C++ run is not performance evidence:

```bash
go test ./tests/ftse2e -run '^$' -bench BenchmarkLocalMatch -benchtime=1x -count=1
cmake --build /path/to/tiflash/existing-build --target bench_local_match_against --parallel 4
/path/to/tiflash/existing-build/dbms/bench_local_match_against --benchmark_filter='BM_LocalMatchAgainst/128/' --benchmark_min_time=0.001
```

The dedicated C++ target is enabled by `ENABLE_TESTS` and uses the existing benchmark framework and test libraries. It avoids building unrelated vector-index benchmarks or downloading external datasets. For meaningful measurements, build it in the server's Release configuration and use repeated runs; retain the build flags, Git revisions, hardware and benchmark JSON. Do not compare Go and C++ microbenchmark numbers directly: their execution units differ.

Generate a streaming CSV with no database access (two fields: `id,body`, no header). The Go benchmark and generator share the same corpus implementation:

```bash
go run ./tests/ftse2e/cmd/benchdata -rows 1000000 -bytes 4096 > /server/data/local-match-4k.csv
```

This example produces about 4 GiB and is intended for the server, not local smoke. Use `-rows 8 -bytes 128` for tool checks. This repetitive, highly compressible synthetic corpus is a reproducible baseline, not a replacement for representative customer data or varying selectivity. The generator validates its arguments and propagates output errors; it does not create tables or change cluster configuration. Import into paired tables with the same collation and matching FULLTEXT definitions, one with a ready TiFlash replica and one without. Before timing, compare result sets and prove MATCH is in TiFlash Selection with no root residual (`EXPLAIN`/`EXPLAIN ANALYZE`); record `tidb_version()`, TiFlash build/version, sysvars and replica state. Pin the requested parser, token sizes, stopword settings, scan placement and concurrency. Warm up, repeat and report distributions, CPU and memory; treat microbenchmarks and SQL latency as separate results. Release server acceptance remains pending.
