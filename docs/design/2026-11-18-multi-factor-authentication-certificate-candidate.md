## 密码与客户端证书为何可以构成双因素认证

非空账号密码属于“知道的秘密”，客户端通过认证协议证明持有证书对应的私钥属于“持有的凭据”。同一账号强制验证两者可以构成双因素认证，但因素分类本身不足以确认客户接受这种实现。本方案使用 MySQL 的 TLS 账号约束；它不提供 MySQL 原生 MFA 的有序插件因子、对应管理语法和协议。

[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) 第 2.2.1 节允许密码与单因素密码学认证组合，第 3.1.6 节将密码学密钥的持有证明归为“something you have”。私钥存储在软件中并不自动排除这一分类，但需要访问保护；硬件中不可导出的私钥提供不同的保护强度。此处引用该标准解释因素分类，不表示已经评估本部署是否满足其完整认证等级要求。

本方案需满足以下约束，并将其纳入验收：

- 账号采用密码认证且密码非空，密码校验与证书校验都不能省略。
- 服务端验证客户端证书及其私钥持有证明。公开证书文件本身、仅配置服务端证书或仅要求 `REQUIRE SSL` 都不足以提供这个持有因素。
- 证书身份绑定到目标账号，例如同时匹配预期的 `ISSUER` 和 `SUBJECT`；用户的私钥按其身份分配和保护。
- 在支持的连接路径中，两项校验必须共同成立；同名其他 Host 账号、代理终止 TLS、会话迁移等路径需要分别核查，不能默认具备同一保证。

客户端可以自动使用私钥完成认证，不要求界面出现两次输入提示。若客户另有指定动态口令、硬件介质或具体测评条款，则应按该具体要求补充评估；当前原文未包含这些限定。

## 证书候选方案与现有能力

采用账号密码与绑定账号的客户端证书联合认证，复用 MySQL 的 `REQUIRE ISSUER ... AND SUBJECT ...` 语义。当前 TiDB 已有密码校验和 TLS 证书约束，但还需验证账号维护、连接入口和凭据更新是否持续满足上述口径；发现的缺口进入后续技术 spec，不预设完全无需代码修改。

证书方案没有实现 `AND IDENTIFIED`、`AuthNextFactor` 或 `authentication_policy`，因此不能作为已实现 MySQL 原生 MFA 的证明。原生多因子插件链的调研保留在源码记录中；最终交付范围待重新确定。

账号维护必须持续保留已配置的双因素要求：普通改密、锁定、解锁或密码策略更新未显式修改证书要求时，原证书约束保持不变。证书要求由有账号管理权限的管理员维护，普通用户不能自行取消或替换。两条行为均与所查 MySQL 一致。

当前 TiDB 基线已实测复现上述保持性与权限边界缺口，修复方案待技术 spec 确认；因此下文描述交付目标，不代表未修复版本已经满足全部要求。非空密码通过下述已选定的全局密码策略和自助修改权限共同维护，不能仅依赖全局密码强度开关。

## 已确认的接入与管理范围

首版覆盖客户端直连 TiDB，使用支持 TLS 客户端证书的 MySQL 命令行客户端作为标准示例和验收客户端。代理及 TiProxy 会话迁移不在首版支持承诺内，其他驱动版本需另行验证。任何支持路径都必须保持已确认的两因素要求。

证书由外部 CA 或已有企业证书管理流程签发，管理员维护账号绑定并负责人工恢复。首版提供配置、检查和轮换步骤，不新增内置证书签发、自助找回或自动吊销系统。变更对后续认证生效，已有连接由管理员按需另外终止。

## 密码策略与管理权限

采用已确认的 MySQL 风格职责边界：管理员将目标账号配置为非空密码与证书联合认证；普通用户可以按密码策略修改自己的密码，修改认证插件、导入认证串及修改证书要求须具备相应管理权限。

本方案将 `validate_password.enable=ON` 且密码最小长度大于零作为启用前提，保留已经配置的更强密码要求。目标账号采用受该策略支持的内置密码认证插件：`mysql_native_password`、`caching_sha2_password` 或 `tidb_sm3_password`。管理员先检查：

```sql
SHOW GLOBAL VARIABLES LIKE 'validate_password.%';
```

下面是采用至少 8 个字符（当前默认值）的配置示例，保留更大的现有长度以及其他已配置的复杂度要求。最终长度按部署的密码规范确定，并始终大于零：

```sql
SET GLOBAL validate_password.length = GREATEST(@@global.validate_password.length, 8);
SET GLOBAL validate_password.enable = ON;
```

策略是全局的：同集群其他账号的后续明文设密和改密也会受到约束，但不会自动改写已有密码，也不因旧密码不满足新策略就改变其现有登录结果。开启校验前已为空密码的目标账号，必须由管理员先设置有效的非空密码。

仅开启这个开关不足以满足要求：还需修复普通用户通过修改自身认证插件或导入空认证串绕开自助改密限制的权限缺口。该权限边界按 MySQL 对齐，合法自助改密保留。拥有账号管理、系统表写入或全局策略修改权限的管理员仍能改变账号配置，需负责维持本方案的启用条件；本方案不新增限制授权管理员的独立 MFA 开关。

用户已接受全局策略对其他账号后续设密和改密的影响。本次不新增每账号密码强度配置，交付也不自动修改现有集群的策略值；管理员按本流程选择启用时机。

## 使用流程草案

以下示例说明已选方案，完整维护和恢复流程仍需在修复后完成集成验证。主机名、文件路径、密码和证书 DN 都是示例值。

### 1. 准备证书与 TLS

为服务器准备证书和私钥，为需要独立识别的用户签发具有独立主体身份的客户端证书，并由用户保管其私钥。服务端信任签发客户端证书的 CA；客户端信任签发服务端证书的 CA。两者可以是不同的 CA。服务端证书需覆盖连接主机名，客户端证书应适用于客户端身份验证，并处于有效期内。

TiDB 的服务端配置示例：

```toml
[security]
ssl-ca = "/path/to/client-ca.pem"
ssl-cert = "/path/to/server-cert.pem"
ssl-key = "/path/to/server-key.pem"
```

每个接收 SQL 登录的 TiDB 节点均需配置相应证书与信任 CA。按账号设置证书要求即可表达选定账号的双因素条件，不要求为了本方案统一改变 `require_secure_transport`。该变量与 TLS 配置加载会共同影响客户端证书策略，需检查已有设置并验证原有账号的连接行为。

首版按直连路径验证。代理若终止 TLS，TiDB 校验的是代理到数据库这一段连接提交的证书，不能直接将其当作原始用户证书；该场景留待后续明确需求。

### 2. 检查并配置账号

先由管理员检查同名账号，确认没有不符合访问要求的宽范围账号或重叠规则：

```sql
SELECT User, Host FROM mysql.user WHERE User = 'secure_user';
```

对已经存在的目标账号，管理员还应检查其认证插件、密码是否非空及已有授权，避免将有账号管理权限的账号误作普通用户验收：

```sql
SELECT User, Host, plugin,
       COALESCE(authentication_string, '') <> '' AS has_password
FROM mysql.user WHERE User = 'secure_user';

SHOW GRANTS FOR 'secure_user'@'10.20.30.0/255.255.255.0';
```

以下账号允许来自指定 IPv4 网段的连接，且同时要求密码与匹配的客户端证书：

```sql
CREATE USER 'secure_user'@'10.20.30.0/255.255.255.0'
  IDENTIFIED BY '<设置独立的账号密码>'
  REQUIRE ISSUER '/CN=Example Client CA'
  AND SUBJECT '/CN=secure_user';

SHOW CREATE USER 'secure_user'@'10.20.30.0/255.255.255.0';
```

如只允许一个 IP，可将 Host 改为 `'10.20.30.42'`。`ISSUER` 和 `SUBJECT` 必须与实际证书的完整 DN 字符串相匹配；此例使用仅包含 CN 的示例 DN。账号创建后再按业务需要授予最小权限。

已有账号经确认采用受支持的密码认证插件且密码非空后，可使用 `ALTER USER ... REQUIRE ISSUER ... AND SUBJECT ...` 配置证书要求，保留现有密码和业务授权。账号配置的变更应在交付修复完成后执行并验证。

`REQUIRE SSL` 只要求加密连接。`REQUIRE X509` 要求有效客户端证书，但不自动将证书绑定到某个数据库用户名。推荐同时配置账号预期的 `ISSUER` 和 `SUBJECT`；两项条件已包含证书要求。

### 3. 使用密码和证书登录

```sh
mysql --protocol=TCP --host=tidb.example.com --port=4000 \
  --user=secure_user --password \
  --ssl-mode=VERIFY_IDENTITY --ssl-ca=/path/to/server-ca.pem \
  --ssl-cert=/path/to/secure-user-cert.pem \
  --ssl-key=/path/to/secure-user-key.pem
```

客户端交互输入账号密码，并使用证书私钥完成 TLS 身份验证。`VERIFY_IDENTITY` 要求服务端证书与连接主机名匹配。登录后检查实际采用的账号定义：

```sql
SELECT USER(), CURRENT_USER();
```

### 4. 维护和恢复

本节采用用户已确认的管理员人工管理流程。当前基线已实测复现省略 `REQUIRE` 的改密或锁定再解锁会清除证书要求，下述“保留要求”是交付行为及回归验证目标。

**修改密码。** 用户按权限和密码策略修改自身密码，管理员可为授权范围内的账号重置密码。仅修改密码时，原有证书要求必须保留：

```sql
ALTER USER 'secure_user'@'10.20.30.0/255.255.255.0'
  IDENTIFIED BY '<新的非空账号密码>';
```

修改后用新连接核实：新密码和正确证书成功；旧密码失败；新密码但无证书仍失败。配置检查使用 `SHOW CREATE USER`。普通用户不能通过空密码或省略认证条件把目标账号降为单因素；各设密语法由密码策略或管理权限检查约束。授权管理员的认证串导入能力保留，管理员负责持续维护目标账号的启用条件。

**常规证书续期。** 账号绑定的是证书身份属性，并非特定证书指纹、序列号或单一公钥。新证书沿用同一 issuer/subject 时，新旧证书在有效且受信任的期间都可能通过认证。此方式可用于正常续期，不用于证明旧私钥已经失去登录能力。

**私钥丢失或泄露后的恢复。** 采用以下管理员流程，始终保留密码和证书要求：

1. 管理员核验申请人的身份，检查同名的全部账号定义，锁定受影响账号以阻止后续登录。
2. 若需立即收回已有访问，管理员另外识别并终止相关连接；锁定账号不等于终止既有连接。
3. 为该账号生成新的私钥并签发证书，使用与旧证书不同的新主体身份，例如 `/CN=secure_user-v2`。密码同时泄露时一并重置。
4. 管理员完整更新账号的证书要求，再核对配置并解锁。显式修改 `REQUIRE` 时必须重述所有需要保留的 issuer/subject 条件。
5. 在每个接收登录的节点使用新连接验证：当前有效密码和新证书成功；旧证书、缺少证书或错误密码均失败。

更新绑定的 SQL 示例：

```sql
ALTER USER 'secure_user'@'10.20.30.0/255.255.255.0'
  REQUIRE ISSUER '/CN=Example Client CA'
  AND SUBJECT '/CN=secure_user-v2';
```

仅写 `REQUIRE SUBJECT ...` 不表示保留旧 issuer：按 MySQL 语义，显式 `REQUIRE` 替换本次账号的整组 TLS 条件。改变账号接受的主体身份使旧证书不再匹配该账号，不等于在整个 CA 信任体系中撤销旧证书。

当前 TiDB 的内置 SQL TLS 认证链路未实现 CRL/OCSP 撤销检查。首版采用已确认的账号证书身份更换与人工恢复流程，不新增自动查询 CA 吊销状态的能力。

**配置生效。** 账号变更通过权限缓存更新用于后续认证，不能承诺所有节点瞬时同步；应逐节点验证。已经建立的连接不会因改密、锁定或证书绑定变化自动重新认证或断开。按已确认的运维边界，紧急处置由管理员另外终止连接。

若需要更新服务端证书或信任 CA，在每个 TiDB 节点替换其配置路径下的文件，并由有权限的管理员对该节点执行 `ALTER INSTANCE RELOAD TLS`。这是单实例操作，不会自动广播到所有节点，也不重做已有连接的 TLS 握手；默认加载失败保留旧 TLS 配置。最终流程需通过成功、失败及多节点用例验证。

## 部署启用与回退

这些步骤定义目标部署流程，实际部署在实现及验证完成后执行。

1. 完成账号约束保持性与管理权限修复，并升级所有可接收 SQL 登录和账号管理语句的 TiDB 节点。混合运行尚含缺口的旧节点时，不承诺已建立完整的双因素管理保障。
2. 检查密码策略的已确认启用条件、目标账号定义及管理员恢复通道；为各节点配置 TLS 和信任 CA。
3. 先为测试账号启用密码与证书绑定，在各节点执行成功及缺少任一因素的失败用例，再逐个启用目标账号。
4. 验证普通单因子账号的既有登录行为，并单独验证 IP 地址和网段规则。全局密码策略及按 MySQL 收紧管理权限的预期变化应提前通知相关账号维护人员。
5. 回退到仍含已知管理缺口的版本前，管理员应暂停这些账号的双因素服务、锁定受影响账号并按需终止会话，保留恢复所需的账号和证书配置。回退后不能继续宣称具备已修复版本的保障；恢复服务前重新执行账号维护和登录验收。

## 按 IP 地址或网段限制访问

按用户确认，优先复用 MySQL 风格的账号 `user@host` 模型。Host 限制该账号允许的连接来源，账号权限仍通过 `GRANT` 等现有方式管理。现有能力满足需求时，这部分只做配置说明与验证，不新增功能开发。

这里已经核实的能力是“账号级允许来源”，可以表达来源白名单式的限制。它不等同于具有独立允许规则、拒绝规则及优先级的全局黑白名单管理功能；目前不承诺已有后一种功能，也不因用户举例提到黑白名单就扩大开发范围。

| 写法或场景 | 当前版本行为 |
| --- | --- |
| `'user'@'10.20.30.42'` | 支持精确 IPv4 地址 |
| `'user'@'10.20.30.0/255.255.255.0'` | 支持 IPv4 网络地址和点分十进制掩码；网络地址的主机位应为零 |
| `'user'@'10.20.30.0/24'` | 当前 TiDB 不支持匹配，不能因为语句创建成功就认定可用；MySQL 参考版本支持此写法 |
| `'user'@'%'` | 允许广泛来源；与同名网段账号是不同账号定义 |
| IPv6 网段 | 当前 TiDB 和所查 MySQL 的账号 Host 掩码机制均不支持 |
| 同名账号规则重叠 | 按既有账号选择规则采用一条配置；当前 TiDB 不能承诺统一的最长前缀优先，推荐本方案避免重叠 |

创建网段账号不会收紧已有同名 `@'%'` 账号。必须检查同名账号的来源、认证要求与权限，避免其他账号定义允许不符合要求的访问。

直连时匹配数据库看到的来源 IP。经过代理或 NAT 后，通常看到代理或 NAT 的地址；TiDB 的 PROXY protocol 可以转交客户端来源，但需配置受信任代理并单独验证。`proxy-protocol.networks` 管理可提交代理头的来源，不承担数据库账号来源限制的职责。

## 两项需求分别验收

### MFA 验收场景

固定为允许的来源，单独改变认证凭据，避免将来源限制计入 MFA。

| 凭据 | 预期结果 |
| --- | --- |
| 正确的非空密码、有效且 issuer/subject 匹配的证书和私钥 | 登录成功，取得匹配账号被授予的权限 |
| 错误密码、正确证书和私钥 | 登录失败 |
| 正确密码、未提交客户端证书 | 登录失败 |
| 正确密码、只有证书而没有对应私钥 | 无法完成所需的客户端证书认证 |
| 正确密码、其他账号的证书，或证书不受信任、已过期、尚未生效、主体不匹配 | 登录失败 |
| 改密、账号锁定再解锁、密码策略更新后，提供正确密码但无客户端证书 | 登录失败，原证书约束仍存在 |
| 无账号管理权限的用户试图取消或修改自身证书要求 | 操作被拒绝，原约束保持不变 |
| 无账号管理权限的用户试图改认证插件或导入空认证串；合法路径尝试设空密码 | 分别由管理权限检查和已启用的密码策略拒绝 |
| 管理员将证书绑定切换到新主体后，再使用旧主体证书建立连接 | 配置生效的节点拒绝旧证书，新凭据可以登录 |
| 已登录的直连客户端切换目标账号 | 仍需满足目标账号的密码与证书要求；不能因原账号已登录而跳过目标账号的约束 |
| 普通单因子账号 | 原有登录与合法自助改密保留；明确验证密码策略启用及管理权限收紧的预期影响 |

### IP 来源限制验收

固定为符合账号要求的凭据，单独改变来源地址。使用没有重叠或宽范围同名账号的测试配置。

| 来源 | 预期结果 |
| --- | --- |
| 精确 IP 账号指定的地址 | 登录成功 |
| 精确 IP 账号之外的地址 | 登录失败 |
| 允许网段内的地址 | 登录成功 |
| 允许网段外的地址 | 登录失败 |

基础登录、IPv4 地址/网段、部分账号维护与权限场景已有[实测结果](2026-11-18-multi-factor-authentication-validation.md)，仍有失败项和未覆盖项，不能据此声称已经满足客户完整验收。技术 spec 需将剩余步骤落实为可复现的配置、身份、连接及预期结果，并覆盖权限不足、缓存生效和旧行为保持的边界。

方案、范围与密码策略的分项决策已完成，详细记录见 [源码调研与决策记录](2026-11-18-multi-factor-authentication-research.md)。Q8 用户要求先核实现有功能；验证确认仍有账号维护缺口，用户口径保持不变。
