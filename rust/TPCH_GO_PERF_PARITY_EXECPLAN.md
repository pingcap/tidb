# Make Rust TPC-H Faster Than Go TiDB

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` up to date as work proceeds.

Reference: `PLANS.md` at repository root. Repository policy in `AGENTS.md` applies: correctness first, minimal diffs, no speculative behavior, verifiable evidence with exact commands, and the complete-Go-package transcreation rule for anything reported as a transcreated package (this plan ports Go structure into existing Rust executors; it does not claim new package transcreations).


## Purpose / Big Picture


The Rust TiDB node on `hparser-integration` already beats the Go nightly node on sysbench and TPC-C (see `SYSBENCH_GATE_FINDINGS.md`). On TPC-H at scale factor 1 it does not: with the coprocessor cache warm the 22 queries take 41.7 s on the Rust node against 23.2 s on Go (build `r20`, head a5e12d4a), and nine queries take more than twice Go's time. The user's requirement is the same as for the other two workloads: every TPC-H query faster on the Rust node than on Go, achieved by following Go's implementation structure rather than by workload-specific shortcuts.

TPC-H differs from the other workloads in what it stresses. Sysbench and TPC-C are many small statements, so per-statement overhead decided them. TPC-H is 22 large analytical queries; each one's time is decided by how the node executes joins, aggregates, sorts and expressions over millions of rows fetched from TiKV through the coprocessor. The TiKV side is the same for both nodes (same cluster, same coprocessor requests, verified in `SYSBENCH_GATE_FINDINGS.md`, round 3), so every second of difference is in the node's own executor.

"Faster than Go" is measured with the harness in `SYSBENCH_GATE_FINDINGS.md`: `tiup bench tpch` with `--check`, single stream, each side restarted before its turn, a cold pass then a warm pass, two rounds with alternating order, answers verified on every run. The acceptance number is the warm pass (the coprocessor cache holds the same responses for both nodes, so the warm pass isolates the node's executor); the cold pass is reported too.

Open items, in the order of expected yield: the worker pool's wake-per-chunk scheduling (kernel time about a fifth of the node's samples on join queries; Go's goroutine handoff costs none), the coprocessor cache's cached-set growth across repeated runs (Go's send order drifts, the Rust node's stays in lockstep), the decimal `Datum` (an ASCII digit string, so every decimal read into a datum and every decimal hash key pays a conversion; Q2's aggregate input and join key), and the index-join task preparation still serial on the session thread.


## Surprises & Discoveries

- (2026-09-13) ROOT CAUSE of the remaining warm gap, measured at the scheduler rather than in the profiler: the node pays about three OS context switches per chunk of rows where Go pays less than one, and the queueing that follows is the wall-clock difference. `perf sched` over one warm Q13 (the cleanest case: TiKV is idle because the query is served from the coprocessor cache, so every millisecond is the node's), three runs per side, summed over each node's own threads:

  | | Rust node | Go node |
  | --- | --- | --- |
  | CPU run time | 934 / 873 / 900 ms | 1285 / 864 / 754 ms |
  | scheduling slices | 4641 / 4232 / 4331 | 1161 / 1118 / 916 |
  | average slice | 0.201 / 0.206 / 0.208 ms | 1.107 / 0.772 / 0.824 ms |
  | runnable but not running | 459 / 447 / 456 ms | 40 / 36 / 22 ms |

  The two nodes burn the same CPU. The Rust node is scheduled four to five times as often, in slices four to five times shorter, and its threads accumulate about 450 ms per run of being RUNNABLE WITHOUT A CPU against Go's 30 -- on a query whose wall is 0.36 s on a four-core box, that queueing is roughly a third of the machine. Q13's aggregate consumes about 1,600 chunks, so the Rust node takes about 2.7 scheduler switches per chunk and Go about 0.6. The cause is structural, not a missing optimization: each pipeline stage here is an OS thread (67 of them in the process against Go's 10) and a chunk crosses stages through a bounded channel, so every handoff WAKES a thread; Go runs the same pipeline as goroutines multiplexed onto four OS threads, where a handoff is an in-runtime switch that neither wakes a thread nor enters the kernel. That is why the node holds about 3.2 of four cores where Go holds 3.9, why it makes three times the context switches at equal task-clock, and why both attempts to fix it from inside one operator failed: they moved where a thread blocks, not whether a handoff needs the kernel.

  The same measurement says this is NOT the whole benchmark. It is the mechanism for the queries that use the same or less CPU than Go and still take longer (Q13, Q18, Q2, Q22, Q11). Two other buckets are separate and were run down to the same level of evidence.

- (2026-09-14) Second cause, Q10: the node spends TWICE Go's time copying rows, and its join order is a red herring. Q10 is the one query of the nineteen compared whose plan differs at all -- the Rust planner joins `customer` to `nation` first, materialising 150,000 rows, where Go joins the date-filtered `orders` to `customer` first and materialises 56,444 -- but forcing Go's order with a `leading` hint recovers only about 5% (node CPU 890/820 -> 790/830 ms, wall 0.64/0.61 -> 0.59/0.62 s, answer identical), so the order is a minor contributor, not the cause. Sampling both nodes on repeated Q10 and classifying every leaf symbol into comparable phases (Rust 850 ms of node CPU, Go 600 ms):

  | phase | Rust | Go | delta |
  | --- | --- | --- | --- |
  | chunk copying | 205 ms | 104 ms | +101 ms |
  | hash and aggregate | 148 ms | 92 ms | +56 ms |
  | allocator | 113 ms | 70 ms | +43 ms |
  | distsql decode | 33 ms | 20 ms | +13 ms |
  | expression eval | 28 ms | 18 ms | +10 ms |
  | join proper | 56 ms | 53 ms | +4 ms |
  | kernel and scheduling | 55 ms | 49 ms | +7 ms |

  Copying is the single biggest line and the only one that is a clean multiple of Go's. Attributed to its call sites, it is the join's output materialisation: `Chunk::append_partial_row_by_col_idxs` alone is 8.1% of the node's Q10 samples, with `append_partial_row_limited`, `JoinOutput::side_range` and `Row::datum_with_buffer` behind it, against Go's `chunk.appendCellByCell` at 1.7% with the rest of its copying inside `runtime.memmove`. Q10 carries the wide customer text columns (`c_name`, `c_address`, `c_comment`) through that materialisation, so the cost lands where the rows are widest. That is the next execution target and it is ordinary work, not a runtime property: a per-cell append loop against Go's bulk column copies.

- (2026-09-14) Third bucket, Q16, still open: identical plan (verified operator-for-operator including the table each side reads), identical coprocessor work (43-52 requests and about 150k scan keys on both), LESS node CPU than Go (243 ms against 298), scheduling like Go's (1173 slices against 1356, 120 ms of run-queue delay against 101) -- and still 11% more wall. Neither of the two causes above explains it. It is the cleanest remaining mystery in the benchmark and wants a request-level timeline, not another profile.


- (2026-09-12) The Go node's warm numbers for the scan-bound queries were coprocessor-cache history, not execution speed. Both nodes run Go's coprocessor cache (the Rust port in `tidb-distsql::copr_cache` is wired into the production transport with client-go's defaults, verified with a request/response trace: same admission, same hits), and both refuse to admit a paging task whose index in its request passed 50 (`CheckResponseAdmission`), which for a 13-region selective scan leaves the late, large pages of every region uncached: a never-seen Q14 variant settles at a 65% hit ratio on BOTH nodes (Go 0.85 s, Rust 0.85 s). The Go node, never restarted, had accumulated a 96% hit ratio on the harness's Q14 over hours of runs with varying worker interleavings (0.25-0.4 s), while `ab-q.sh` restarts the Rust node before every measurement. The fair protocol restarts both nodes and runs the same warm-up + two measured runs (`fair-ref.sh`); under it Q14 is 0.85 vs 0.93 s, Q15 1.98 vs 2.20, Q19 1.34 vs 1.45, Q12 0.58 vs 0.72, Q20 1.22 vs 1.37 (Go vs r44), and the whole suite is 23.8 s vs 28.8 s (1.21x). The final harness run must restart the Go node too. The Rust cluster node also serves no `/metrics` (only the unistore node starts the status listener), so its cache counters (`copr_cache_metric_snapshot`) are not observable from outside; that is a separate gap.
- (2026-09-13) The scheduling cost of the worker pool is the largest remaining single bucket on the join queries, and it is a runtime difference, not an executor one. `perf stat` over one Q9: the Rust node makes 28,904 context switches and 1,495 CPU migrations (node CPU 3.62 s) where Go makes 9,059 and 211 (2.87 s); per thread, the session thread switches 6,000 times and each of the 16 pool workers about 1,100. Every parallel probe chunk (about 5,900 per Q9) is one `enqueue` on the pool's shared mutex+condvar queue, which wakes a parked worker (a futex wake and, on this KVM guest, usually an IPI and a migration), and the worker parks again as soon as the queue is empty; kernel frames (`finish_task_switch`, `_raw_spin_unlock_irqrestore`, `irqentry_exit_to_user_mode`) are about 21% of the node's samples. Go's fetcher and probe goroutines hand chunks over inside the runtime (a `goready` onto a running P), so the same one-chunk-per-send design costs no OS wakeup while the Ps are busy. On the same query TiKV's own handle time is 13% higher for the Rust node (8.4 s vs 7.3 s) with identical plans, request counts and scan keys, consistent with the node's extra CPU and wakeups competing with TiKV's four read-pool threads on four cores. A Go-shaped spin-before-park (`stealWork`/`wakep`) was tried earlier and dropped (hangs, no measured gain); the correct version remains the open structural item.
- (2026-09-13) Q12 is answered almost entirely from the coprocessor cache on both nodes (TiKV scans 10k keys for Go and 129k for Rust out of 7.5M), so its 0.23 s vs 0.46 s is node CPU on the session thread: the merge join. The inner side (orders, 1.5M single-row groups) resets its spillable row container once per group as Go's `fetchNextInnerGroup` does, but the Rust `RowContainer::reset` walks the spill coordinator (two mutex acquisitions, a write lock, a lease drop with a condvar notify, and a per-column `memory_usage`) where Go's takes one mutex and resets a slice; `reset_shared` alone is 26% of the Rust node's Q12 samples.
- (2026-09-13) The scan-bound gap (Q14, Q19, and by extension Q15, Q20, Q4) is the coprocessor cache's growth across repeated runs, not its rules. A traced build (`TIDB_COPR_TRACE`, not committed) and Go's `EXPLAIN ANALYZE` agree on every rule: the same 69 lineitem pages per run on both nodes (11 regions, 128-row first page doubling to 4096 or 8192), the same admission (a page whose iterator-wide index exceeds 50 is never stored; the small early pages fail the 5/3 ms process-time floor), the same unbuffered worker-to-consumer rendezvous per page, and the same cold run (12.4M scan keys, 1.32 s vs 1.38 s) and second run (6.8M keys on both, 0.73 s vs 0.79 s). From the third run on the two diverge: the Go node's cached set keeps growing (its hit ratio after a restart goes 0.00, 0.72, 0.75, 0.77, 0.81, 0.84 over six runs, and by run ten Q14 takes 0.30 s with 0.67 s of TiKV handle time) while the Rust node's plateaus (0.66 s and 1.8 s of handle time from run three to run ten). Per region, the Rust trace shows the pages sent in lockstep across the eleven regions, so each region's sixth page (the largest, 230-465 KB and 300k scanned keys) always draws an index of 54-69 and is never admitted; in Go the regions' send order drifts across runs and those pages get admitted a few at a time. The harness's warm pass is the third run after a restart, where the two are still close (Q14 0.59 vs 0.79 s in this measurement); the earlier 199k-vs-2.0M processed-keys comparison had the Go node with dozens of prior runs against a freshly restarted Rust node. Not fixed: the index is taken at the same point in both (before the send, after the previous page's response was handed to the consumer), and an ordering perturbation without a Go counterpart would be speculative.
- (2026-09-13) The coprocessor-cache growth finding above holds for Q9 as well, and the TiKV-side gap it hid is the transport, not the cache. A traced build (`COPR_TRACE`, not committed) over eight Q9 runs after a restart: the single-region orders and partsupp scans are fully cached on the Rust node from run two (indices 1-38), while each of the thirteen lineitem regions keeps only its first 1-5 pages (its 50000-row pages draw indices 118-226 and are refused, 900 MB of responses per run); hits grow 77, 84, 88, 94, 98, 101, 103 across runs two to eight, the same slow drift Go shows. The Go node's advantage in the earlier Q9 comparison (5.3M scanned keys against 5.9M) was its longer cache history; restarted side by side, both scan 8.5M keys cold and 5.99M warm. What remains different at equal keys is TiKV's cost of serving the Rust node: about 10% more read-pool CPU and twice the gRPC-thread CPU, with the Rust node's responses 6% larger (908 vs 859 MB), which pointed at the transport's flow-control windows (Milestone 6, part 8); aligning them changed nothing, and a metric diff of the two warm runs at equal cache state (272 vs 274 DAG requests, 5.99M processed keys on both, the same keys-per-request histogram, the same block-cache hit counts) leaves the Rust node's request stream indistinguishable from Go's apart from the priority label and 5% more response bytes. The excess TiKV CPU (0.45 s read pool, 0.38 s gRPC over a run) is then most plausibly contention: the Rust node itself uses 0.3-0.5 s more CPU on Q9 (3.4-3.6 vs 3.1 s) on a four-core box that TiKV shares, and TiKV's gRPC threads poll their completion queues. The Q9 residual is node CPU (the pool's wakeups and the probe pipeline), as the profiles said. Also seen and not a lever: the Rust node's requests carry `override_priority` 0 where client-go's resource-control interceptor stamps the group's priority (8, "medium"); TiKV resolves 0 to the group's own priority, so only the metrics label differs.
- (2026-09-13) Q3 (node CPU 760 vs Go's 410 ms at equal wall) profiled with DWARF call graphs: 57% of the samples are the session thread, 22% the query workers. The index join's task preparation (`fill_index_task_queue`, 21%) materializes every outer row as a `Vec<Datum>` (`get_datum_row` 2.6%, `Vec<Datum>` collection 3%, datum clones and drops), dedups the probes through a `BTreeMap<Vec<u8>, _>` keyed by the encoded key (insert plus `memcmp` 5%), and builds the inner key ranges through `record_key_range_value_halves` whose per-range `Vec` growth is 2.7% of `rallocx`; Go's `constructLookupContent` reads only the key columns out of the outer chunk rows (`GetDatum` per key column into a reused `keyBuf`), keeps the outer rows as chunks in `task.outerResult`, and dedups by sorting the contents. jemalloc's tcache flush, malloc and sdallocx together are 17% of the node's samples on this query. The index join in Go's shape (Milestone 2, part 2) is the remaining lever for Q3, Q8, Q10, Q16, Q21.
- (2026-09-13) Q17 (node CPU 4.7 s vs Go's 3.8 s) is the root aggregate: TiKV's pushed-down partial aggregate returns 5.3M partial rows (one per group per page) that the node folds into 200k groups, and the aggregate's partial lanes are 66% of the node's samples, with the map lookup alone 28% (`IndexMap::get_index_of`, 250 ns per lookup) and the fold's own code 19%; new groups cost another 5% (`AggState::new_parallel_with` allocating per state). Go's pprof over the same query puts its partial workers at about 2 s per run (`updatePartialResult` 55% of a 9 s window over 2.5 runs: `mapaccess2_faststr` 25%, `avgPartial4Decimal.UpdatePartialResult` 11%, `memeqbody` 9%, `memmove` 12%), 170 ns per lookup on a swiss-table runtime map. The IndexMap keeps an index table beside an entries vector, two cache misses per lookup on a 200k-group map; the swiss-table `hashbrown` map is Go's shape (Milestone 6, part 10, measured next).
- (2026-09-12) Go's Q13 CPU (820 ms) splits 48% aggregate (`mapaccess2_faststr` alone 25%), 25% probe; the Rust node's (2070 ms) 37% aggregate, 33% probe worker, and the probe worker deep-copied every probe chunk (`copy_construct_sel` on a chunk with no selection) before appending from it.


- The coprocessor cache is not the warm gap. A traced build showed the Rust cache key, admission and paging equal to Go's `coprocessor_cache.go`; the r16 guess in the findings document was wrong and has been corrected there.
- The parallel probe pipeline (commits ae441fa3 and a5e12d4a) was the correct Go shape but moved only Q9 (-10%): on most queries the probe phase was not on the critical path. The session thread is: it builds every hash table, decodes every coprocessor response, evaluates every projection row by row and consumes every join result.

## Outcomes & Retrospective


Interim (2026-09-13, r87, measured over three fresh-cache rounds with both nodes restarted per round, six warm runs per query per side): the warm total is 1.019x Go (25.21 s against 24.75 s median), from 1.14x at r65. Six queries are faster than Go (Q5, Q7, Q12, Q17, Q19, Q20 at or under 1.00x) and eight more are inside the measurement's spread; the reliably slower ones are Q2 1.24x, Q22 1.17x, Q13 1.13x, Q16 1.11x, Q10 1.09x and Q18 1.07x. The character of the remaining gap changed with this round of work: on the reliably slower queries the Rust node now uses the SAME or LESS node CPU than Go and asks TiKV for the same data, so what is left is waiting, not work -- the node holds about 320% of four cores where Go holds 390%, and makes three times Go's context switches for the same task-clock. Planning, which had been a fixed several-millisecond tax on every query, is roughly halved (Q8 19.96 -> 9.39 ms per statement, Q9 13.75 -> 6.86, now faster than Go's 8.12). The acceptance bar (all 22 faster warm) stands unmet.

Superseded interim (2026-09-13, r65): the warm total went from 1.80x Go (r20) through 1.53x (r28) to 1.14x, with Q12 faster, six queries at parity and every remaining gap under 1.4x except Q2 (0.17 vs 0.10 s, a fixed per-statement cost on a small result). Every change followed the owning Go package's structure and landed with its own two-run A/B; the two attempts that measured neutral (the constant-length cell copy and the column-wise batch assembly) were reverted rather than kept. What the campaign did not reach is the runtime layer: the executor now does the same work in the same shape as Go on the queries measured, and the residual is the pool's OS-level wakeups per chunk, the allocator, and the decimal datum representation. The acceptance bar (all 22 faster warm) stands unmet; the honest per-query state is in the findings document.


## Context and Orientation


The Rust node lives under `rust/`. The executors are in `rust/crates/tidb-executor/src/` (`join.rs` and `hash_join.rs` for the hash join, `hash_agg.rs` for the hash aggregate, `projection.rs`, `sort.rs`), expressions in `rust/crates/tidb-expr/src/`, the coprocessor client in `rust/crates/tidb-distsql/src/` (`cop_paging.rs`, `copr_cache.rs`). The Go references are `pkg/executor/join/` (`hash_join_v2.go`, `hash_table_v2.go`), `pkg/executor/projection.go`, `pkg/expression/` (`vectorized.go`, `chunk_executor.go`, `builtin_arithmetic_vec.go`), and `pkg/executor/aggregate/`.

"Session thread" means the thread that serves one client connection; on the Rust node it drives the executor tree (`driver::drain_root_executor`) and every operator's `next` runs on it unless the operator hands work to the process-wide worker pool (`crates/tidb-executor/src/worker_pool.rs`). "Worker pool" is the node's fixed pool of threads that the parallel hash aggregate and the parallel hash-join probe use.

The benchmark cluster is a `tiup playground nightly --tag bench` on one 4-core, 15 GB machine: PD, one TiKV, the Go node on port 4000 and the Rust node on port 4001, both against the same TiKV. Scripts, binaries and results live in the session scratchpad (`restart-cluster-keep3.sh`, `tpch-run.sh`, `explain-all.sh`, `ab-bin.sh`); the query texts are go-tpc's 22 queries.


## Plan of Work


Milestone 1 collects the evidence: for each query, the warm `EXPLAIN ANALYZE` on both nodes, and for each query above 1.5x, the operator whose time differs and the reason (structure, plan, or a missing pushdown). The result is a table in this plan naming one root cause per query.

Milestone 2 ports the build phase. Go's `HashJoinV2Exec` fetches build-side chunks on one goroutine and hands them to `Concurrency` build workers that partition rows by key hash and append them into per-partition row tables, then builds each partition's hash index; the row tables are immutable during the probe. The Rust `JoinExec` builds on the session thread. The port keeps the Rust row container and index shapes and moves the per-chunk indexing onto pool tasks with Go's partitioning, so the probe workers see the same immutable table.

Milestone 3 ports column-wise evaluation. Go evaluates a scalar function over a chunk column by column (`VectorizedExecute`), with each function's children evaluated into reusable column buffers; the Rust expression crate evaluates every function per row into a datum. The port adds a column-wise path for the operators TPC-H spends its time in (arithmetic and comparison over fixed-width columns) and uses it from the projection and the aggregate input, falling back to the row path otherwise, exactly as Go falls back when a function is not vectorizable.

Milestone 4 takes the per-query causes from Milestone 1 that the two structural milestones do not cover, one commit each.

Milestone 5 is the full harness run and the document.

## Idempotence and Recovery


Every script above can be rerun; the cluster restart reuses the `bench` data directory. If the disk fills (the cargo target directory grows past 20 GB; the debug tree alone reached 13 GB after a few full-suite runs and a linker then dies with a bus error), `rm -rf rust/target/debug` recovers space without losing release artifacts; the next test run rebuilds it. The temp filesystem is the same disk, so old node binaries and profiles in the scratchpad count too. If the playground dies, `restart-cluster-keep3.sh` brings it back on the same data.
