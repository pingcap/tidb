# Carry stored table columns through the deployable read-only SQL node

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` up to date as work proceeds.

Reference: `PLANS.md` at repository root. This plan must be maintained according to it.

## Purpose / Big Picture

After this campaign, the standalone Rust SQL node can expose one statically configured real TiKV table with more than the clustered integer key. An operator can configure a signed `BIGINT PRIMARY KEY CLUSTERED` column plus a signed stored `BIGINT NOT NULL` column, then use a stock MySQL client to reorder and alias those columns. The returned stored value must have crossed TiKV's row payload and the Rust DistSQL decoder; it may not be synthesized from the record key.

The observable proof is one live query such as `SELECT balance AS amount, id FROM test.accounts`. Its headers must preserve output order, alias, and original column names, and its rows must match seeded negative and positive stored values. Structured logs must continue to prove real PD TSO, real region discovery, BatchCommands-first physical publication, exactly-once connection cleanup, and complete TiUP cleanup.

## Surprises & Discoveries

- Observation: Campaign 19 proves only the clustered key path; its configured catalog and planner map every projected name to the same `pk_handle` scan column, and executor metadata marks every output as primary-key plus not-null.
  Evidence: `rust/crates/tidb-planner/src/read_only_scan.rs` builds every projection with `pk_scan_column`; `rust/crates/tidb-exec/src/real_tikv_read.rs` emits flag `0x0003` for every result.

- Observation: The downstream DAG, response decoder, and MySQL writer are already vector-shaped.
  Evidence: `construct_dag_req` emits every scan output offset, response decoding receives an N-field type list, and result framing iterates caller-supplied `ColumnInfo` and row values.

- Observation: The connected path preserves stored row payloads independently of clustered record keys.
  Evidence: table 114 returned exact `(amount,id)` pairs `(913,-7)`, `(-2048,0)`, and `(77,42)` through the stock MySQL client; neither the negative stored value nor the other balances can be derived from the key.

- Observation: The Campaign 19 control-plane and transport path remained intact after multi-column widening.
  Evidence: the live proof recorded PD cluster `7664074606058950579`, snapshot TSO `467777994228760577`, located and dispatched region 16, one BatchCommands attempt, zero unary fallback, and zero active connections after client exit.

## Decision Log

- Decision: Model column storage with an enum, not independent `pk_handle` and `not_null` booleans.
  Rationale: `ClusteredPrimaryKey` and `StoredNotNull` make invalid flag combinations unrepresentable for this milestone and keep one exact source of truth for TiKV and MySQL flags.
  Date/Author: 2026-07-19 / Codex.

- Decision: Use one repeatable composite startup option, `--column <name>:<id>:<clustered-pk|stored-not-null>`, and remove the parallel `--column-id` surface.
  Rationale: Parallel arrays create length/order edge cases. One descriptor is atomic, validates locally, and scales to additional columns without another option family.
  Date/Author: 2026-07-19 / Codex.

- Decision: Defer predicates and LIMIT.
  Rationale: faithful predicate widening requires ranger coercion and PointGet selection; LIMIT requires the exact tipb Limit executor plus global offset/count enforcement across regions. Client-side truncation or treating equality as a table range would be a workaround.
  Date/Author: 2026-07-19 / Codex.

- Decision: Defer concurrent/authenticated sessions until the stored-value path is proven.
  Rationale: concurrency should multiply a correct per-session engine. Campaign 21 will replace the `Rc<RefCell>` read authority with one shared runtime and per-connection engines rather than serializing the whole engine behind a mutex or duplicating PD/cache/client state.
  Date/Author: 2026-07-19 / Codex.

## Context and Orientation

Campaign 19's entry path is `rust/crates/tidb-server/src/bin/tidb-server.rs` to `node_config.rs`, `real_tikv_node.rs`, `tidb-exec/src/real_tikv_read.rs`, `tidb-planner/src/read_only_scan.rs`, `tidb-exec/src/dag_request.rs`, and Campaign 18's retained DistSQL/PD/TiKV path. The current `ConfiguredTable` contains only one primary-key name and ID. A `ConfiguredColumnKind` must distinguish `ClusteredPrimaryKey` from `StoredNotNull`; all columns in this campaign remain signed MySQL `BIGINT` with binary collation.

The planner must return resolved projection metadata rather than only output names. Each resolved item needs the output name, original source name, stable column ID, column kind, and exact `ScanColumnInfo`. `SELECT balance AS amount, id` therefore scans columns `[balance,id]`, emits DAG offsets `[0,1]`, and publishes MySQL columns `[(name=amount,org_name=balance,NOT_NULL),(name=id,org_name=id,NOT_NULL|PRI_KEY)]`.

## Plan of Work

In the planner slice, replace the one-key `ConfiguredTable` representation with an ordered column list and enum-backed column kind. Validate nonempty unique names and IDs, exactly one clustered primary key, and positive IDs. Resolve each direct projection by its table-visible source name, preserve aliases separately, build the physical scan columns in projection order, and expose immutable resolved projection items. Remove the old path that clones the primary-key scan descriptor for every projected name.

In the executor slice, consume resolved projection items for field types and protocol metadata. `org_name` comes from the source column; `name` comes from the alias or source name. Primary-key and stored flags must differ exactly. Strengthen the DAG regression so two projected columns produce two protobuf columns and output offsets `[0,1]`. Do not change the transport, range, TSO, or response ownership.

In the server configuration slice, replace `--column` plus `--column-id` with repeatable atomic descriptors. Parse and validate the descriptor once, preserve configured order, and construct the planner column list without reconstructing flags elsewhere. Startup logging must report the checked column count and descriptors without losing the existing cluster/table evidence.

In the wire slice, extend the fake-engine TCP lifecycle test to return two columns with different flags and signed values in reordered aliased form. This proves that no server writer assumes one field even before the live environment is started.

Finally, adapt the Campaign 19 live runner into a new Campaign 20 runner. Seed rows whose stored values cannot be inferred from their keys. Start the Rust binary with two column descriptors and query the stored column first under an alias. Validate headers and rows through the stock MySQL client, then validate the existing TSO/region/BatchCommands/connection/cleanup evidence.

## Interfaces and Dependencies

`tidb-planner::read_only_scan` owns `ConfiguredColumnKind`, `ConfiguredColumn`, `ConfiguredTable`, `ResolvedProjectionColumn`, and `ReadOnlyScanPlan`. Use constructors that cannot represent a nullable primary key or a primary-key flag on stored data. `ReadOnlyScanPlan::projected_columns()` returns resolved projection metadata; `table_scan().pushdown().columns` remains the exact protobuf scan list.

`tidb-exec::real_tikv_read` consumes those types but does not recreate catalog policy. `tidb-server::node_config` owns only textual startup parsing; `real_tikv_node` maps validated descriptors into planner constructors. No layer may infer primary-key status from column position or name.
