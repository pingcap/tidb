# Execute bounded ORDER BY LIMIT over the configured real-TiKV join

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as implementation proceeds.

Reference: `PLANS.md` at repository root. This plan follows the repository ownership, evidence, worktree, and shared-gate rules in `rust/PARALLEL.md` and `rust/workstreams/slices/README.md`.

## Purpose / Big Picture

Campaign 26 makes the Campaign 25 two-table read node useful for deterministic paginated reads. After implementation, one authenticated stock MySQL connection can execute a bounded two-table signed `BIGINT` join against real TiKV and add `ORDER BY ... LIMIT`, or apply `LIMIT` without ordering. A user observes exact multi-key ascending and descending rows, offsets, aliases, ordinals, persistent-session reuse, and continuity through PD/TiKV leader churn.

The implementation is a direct bounded port of TiDB's planner Sort/Limit/TopN and executor sort/TopN responsibilities. It does not reconstruct SQL, sort an unbounded full result and truncate afterward, create another server or session path, or substitute an in-memory fixture for real TiKV. `ORDER BY` is admitted only with an explicit checked `LIMIT`; the executor retains at most `offset + count` candidates, bounded again by one process configuration value. `LIMIT` without `ORDER BY` streams, skips, stops, and cancels upstream without draining hidden rows. `LIMIT 0` returns before PD timestamp or TiKV transport work.

The first boundary remains deliberately narrow: exactly the Campaign 25 configured two-relation query, non-null signed `BIGINT` order keys, direct column references, unique select aliases, positive select-list ordinals, multiple ASC/DESC keys, and literal nonnegative LIMIT/OFFSET forms. ORDER expressions, ORDER without LIMIT, NULL, unsigned and mixed-type comparison, coercion, collation, filesort spill, partition TopN, index-order exploitation, TiKV TopN pushdown, prepared parameters, aggregation, windows, and dynamic memory quotas remain rejected or explicit ledger gaps.

## Surprises & Discoveries

- Observation: the workspace contains broad in-memory `ORDER BY`/`LIMIT` helpers in `rust/crates/tidb-exec/src/order.rs` and source-identity planner leaves, but the deployable real-TiKV planner explicitly rejects both clauses.
  Evidence: `rust/crates/tidb-planner/tests/read_only_scan_source.rs` and `configured_relation_tree_binding_source.rs` assert rejection, while `tidb-exec::order` is used by the older row-wise engine rather than Campaign 25's real-TiKV join path.

- Observation: implementing aggregation next would connect more existing leaf modules but would not be a small vertical.
  Evidence: the current design still lists aggregation together with NULL/coercion/unsigned and general expression gaps; correct aggregate output needs group binding, empty-input behavior, accumulator typing, metadata, HAVING, and memory semantics in addition to execution kernels.

- Observation: TiDB's sortexec fleet includes parallel workers, spill, rank TopN, failpoints, memory trackers, and arbitrary datum comparison, while the deployable node currently exposes only configured non-null signed `BIGINT` columns.
  Evidence: `pkg/executor/sortexec/*.go` and their exact ledger obligations are much broader than the first executable subset. Campaign 26 therefore retains them at conservative `PARTIAL` and names every excluded branch.

- Observation: Campaign 25 split its server work into a configuration/lifecycle foundation and a final dispatch/live proof.
  Evidence: `server-multi-relation-node-foundation` owns the shared lifecycle/configuration seams and harness; `server-live-multi-relation-join-proof` owns `real_tikv_multi_node.rs` and the live scenario. `sql_node.rs` remains a foundation-owned lifecycle seam, so Campaign 26 extends the existing node rather than reopening a second server surface.

## Decision Log

- Decision: make bounded ORDER BY LIMIT the next deployable vertical.
  Rationale: deterministic top-N and pagination are immediately user-visible, exercise planner-to-executor composition, and reuse the exact Campaign 25 storage and join authorities. Aggregation has a substantially larger semantic prerequisite closure.
  Date/Author: 2026-07-19 / Codex.

- Decision: require explicit LIMIT whenever ORDER BY is present in this campaign.
  Rationale: the process has no spill or general memory-quota authority yet. A transparent bounded admission rule is correct; silently truncating ORDER BY or materializing an arbitrary full result is not.
  Date/Author: 2026-07-19 / Codex.

- Decision: bind order keys to physical FullSchema offsets before final projection.
  Rationale: MySQL/TiDB permits ordering by an unprojected source column. Using only projected offsets would create a special-case rejection and make aliases/USING coalescing disagree with Campaign 25's physical schema.
  Date/Author: 2026-07-19 / Codex.

- Decision: use one bounded max-heap for ORDER BY LIMIT and a separate streaming window for LIMIT-only.
  Rationale: sorting every joined row and truncating is the development shortcut that creates the production bottleneck. The operator shape should encode bounded memory and early completion as normal behavior.
  Date/Author: 2026-07-19 / Codex.

- Decision: add one process-wide `--max-topn-rows` value to the existing `NodeConfig`.
  Rationale: capacity must be explicit and validated before side effects. A hard-coded hidden limit, query-local environment variable, or second configuration parser would create another policy authority.
  Date/Author: 2026-07-19 / Codex.

- Decision: keep every Campaign 26 evidence transfer at `PARTIAL`.
  Rationale: the bounded signed-BIGINT path does not complete Go's sort, TopN, Limit, planner optimization, spill, memory, partition, index, server, or RealTiKV source families. Existing predecessor gaps and split-test domains must be preserved exactly during promotion.
  Date/Author: 2026-07-19 / Codex.

## Frozen Public Contracts

The first slice defines these semantics in `tidb_planner::configured_order_limit_contract`. Exact Rust spelling may follow nearby style, but fields, ownership, and error boundaries must not drift between agents:

    pub enum ConfiguredOrderDirection { Ascending, Descending }

    pub struct ConfiguredOrderKey {
        full_offset: usize,
        direction: ConfiguredOrderDirection,
    }

    pub struct ConfiguredLimitWindow {
        offset: usize,
        count: usize,
        end_exclusive: usize,
    }

    pub struct ConfiguredOrderLimitSpec {
        order_keys: Vec<ConfiguredOrderKey>,
        limit: ConfiguredLimitWindow,
    }

`ConfiguredLimitWindow::new(offset, count)` computes `end_exclusive` with checked addition. It exposes `is_empty()` and never accepts a caller-supplied unchecked end. `ConfiguredOrderLimitSpec` requires nonempty keys; LIMIT-only is represented by a separate plan variant, not an empty-order special case inside TopN.

The planner slice adds one parse-once entrypoint to Campaign 25:

    ConfiguredJoinPlan::lower_select(select: &tidb_ast::SelectStmt, catalog: &ConfiguredCatalog)

The existing `ConfiguredJoinPlan::lower(sql, catalog)` parses once and delegates. `ConfiguredOrderedQueryPlan::lower(sql, catalog)` also parses once, calls the typed entrypoint, and returns exactly one of:

    LimitOnly { input: ConfiguredJoinPlan, window: ConfiguredLimitWindow }
    TopN { input: ConfiguredJoinPlan, spec: ConfiguredOrderLimitSpec }

The stable-order executor accepts `&[Row]` or owned `Vec<Row>` plus `&[ConfiguredOrderKey]`, validates every referenced cell as non-null `Datum::Int`, and returns a typed error on a short row or wrong type. It uses the existing `order.rs` comparison authority; it does not define another scalar order.

The bounded TopN owner exposes a state object constructed from `ConfiguredOrderLimitSpec` and a caller capacity. Construction rejects `end_exclusive > capacity` before consuming rows. Each heap entry carries its source ordinal so equal keys retain source order. Finalization returns only `[offset, end_exclusive)` in canonical order and reports immutable evidence: capacity, high-water candidates, rows consumed, and rows emitted. Its LIMIT-only companion accepts `ConfiguredLimitWindow`, skips and emits lazily, requests no more than needed from upstream, and cancels/closes upstream once complete.

The Campaign 25 join result remains the sole row and metadata representation. `ConfiguredOrderedQuery` wraps or consumes that result; it must not decode TiKV rows again or create a second `Row` type. The server accepts one executor-owned RecordSet with the same projected metadata interface Campaign 25 already gives MySQL encoding.

## Plan of Work

Stage A creates only the shared immutable contract and focused construction tests. It neither parses SQL nor executes rows. Promote its exact evidence immediately while retaining the claim so B and C unlock without consuming the campaign gate.

Stage B changes Campaign 25's planner once. It introduces a typed `SelectStmt` entrypoint, makes SQL wrappers delegate, binds direct order keys against FullSchema before projection, resolves unique explicit aliases and positive ordinals, parses all literal LIMIT syntaxes, and rejects the complete unsupported family before runtime side effects. It is the sole planner routing steward.

Stage C refactors `tidb-exec::order` into the canonical checked multi-key signed-BIGINT comparison seam. It preserves existing row-engine behavior and tests. It does not implement a heap, read a RecordSet, or modify executor routing.

Stage D builds the bounded heap and LIMIT-only streaming window. Because `tidb-exec` disables automatic integration-test discovery and Stage E owns `Cargo.toml`, D compiles through the already-registered `source_shard_b` until E exports the module. This is the same temporary source-inclusion protocol used by Campaign 25; Stage E removes any temporary bridge that becomes redundant.

Stage E consumes Campaign 25's configured join result and routes either LIMIT-only or TopN execution. It owns `tidb-exec` routing and test registration. LIMIT-only propagates required rows and cancellation; TopN drains one join stream exactly once. Both preserve projected metadata and close the single upstream authority on success, error, cancellation, or client disconnect.

Stage F extends the one `NodeConfig` with a validated process-wide TopN capacity. It does not alter query dispatch. The default and accepted maximum must be documented in code and tests; zero, overflow, duplicate, and malformed values fail startup.

Stage G extends Campaign 25's one multi-relation dispatcher. It applies the configured capacity before starting PD/TiKV work, returns LIMIT 0 locally, passes one cancellation authority through every layer, and publishes stable query evidence. It does not add a listener, worker pool, session opener, record-set encoder, or shutdown path.

Stage H adds one scenario script using the existing live harness hooks. The fixture contains duplicate primary and secondary order keys so multi-key direction and ties are observable. One persistent stock MySQL connection proves qualified columns, aliases, ordinals, an unprojected order key, both offset syntaxes, LIMIT-only early completion, LIMIT 0 zero transport, no matches, cap rejection, unsupported rejection, topology churn, blocked shutdown, zero exit, and complete tag-owned cleanup.

## Validation and Acceptance

Focused validation must first prove fail-closed behavior against the exact unsupported boundary, then positive behavior. Any bug fix needs a regression that fails against the predecessor for the intended reason and passes after the fix.

Planner acceptance requires one parse, correct FullSchema offsets for qualified/unqualified keys, explicit alias and positive ordinal resolution, ordering by an unprojected configured column, source-order multiple keys, checked limit forms, and no timestamp acquisition for LIMIT 0, overflow, cap excess, ambiguity, or unsupported expressions.

Executor acceptance requires exact signed `BIGINT` lexicographic ordering, independent directions per key, deterministic source ordinals for ties, typed short-row/type errors, heap high-water at most `offset + count`, exact offset slicing, LIMIT-only early stop, cancellation and close exactly once, and unchanged Campaign 25 join metadata.

Live acceptance uses one persistent stock client and two real TiKV tables. It must return exact rows for at least these shapes: `ORDER BY a.AccountID ASC LIMIT 2`, `ORDER BY o.Amount DESC, a.AccountID ASC LIMIT 1,2`, select alias ordering, positive ordinal ordering, an unprojected key, LIMIT-only with offset, LIMIT 0, and a no-match join. It must reject ORDER without LIMIT, zero/out-of-range ordinal, expression key, arithmetic or parameterized limit, overflow, and configured-cap excess before PD/TiKV side effects.

The receipt records one Rust PID and connection identity; both table IDs; each nonempty query's one snapshot timestamp and two physical range publications; join offsets; order offsets and directions; limit offset/count; heap capacity/high-water; rows consumed/emitted; upstream cancellation; PD/TiKV topology sequence; shutdown order; exit status; and tag-owned cleanup. No in-memory fixture row or independent snapshot can satisfy acceptance.

## Idempotence and Recovery

Slice worktree creation, focused tests, dry-run promotion, queue checks, and harness cleanup are safe to rerun. Promotion is transactional and retains active claims. Do not manually edit generated ledgers or slice status.

If A's public contract changes after B or C is claimed, stop both consumers, amend all affected manifests and claims, and restart from one frozen contract. Do not add compatibility aliases or conversion wrappers to keep stale work compiling.

If a leaf fails, abandon only that claim and worktree. If a provider is still active, leave consumers gated rather than copying provider code. If the integrated gate or live proof fails, release nothing; preserve diagnostics, correct the owning slice, rerun its focused loop, and rerun the complete immutable campaign gate.

The live script must use the harness's tag and PID ownership checks. Cleanup may terminate only tag-owned processes and removes runtime/auth artifacts only after every owned process and endpoint is gone.
