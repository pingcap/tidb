## Purpose / Big Picture

After this campaign, the standalone Rust SQL node is a deployable loopback service rather than a single-client demonstration. A required startup user file defines non-root accounts by host and stored `mysql_native_password` hash. A stock MySQL client can authenticate and at least three clients can overlap while querying Campaign 20's configured table through one process-owned PD client, region cache, maintenance worker, and TiKV transport authority.

The observable proof is one live process with at least three overlapping authenticated client sessions. Every client must receive the exact real-TiKV rows, use a distinct connection ID and nonzero snapshot TSO, and share the same PD cluster. Structured evidence must show at least two simultaneously active connections, BatchCommands publication, exactly-once connection cleanup, zero active connections after clients exit, and complete TiUP and secret-file cleanup.

## Surprises & Discoveries

- Observation: `SerialSqlNode::serve_next` owns one engine and blocks inside one connection until disconnect, so the listener cannot admit a second session even though the socket accept loop exists.
  Evidence: `rust/crates/tidb-server/src/sql_node.rs` lends its sole engine mutably through `SerialQueryEngine::execute`, whose lazy `SerialQueryResult` borrows that engine.

- Observation: the process-wide authorities are already close to shareable: `PdClient` is cloneable and `BackgroundRegionCache` is `Arc` backed. The remaining hard ownership boundary is tonic worker lifetime versus per-query command submission.
  Evidence: `rust/crates/tidb-txnkv/src/rpc/transport_runtime.rs` currently stores both its command sender and unique worker `JoinHandle` in `TransportRuntime`.

- Observation: `Rc` query state is not itself a concurrency defect if it is created and consumed inside one fixed worker thread.
  Evidence: `SharedReadRuntime`, DirectUnary response evidence, lock delegates, and pending response sources are query-local; moving their construction into the worker avoids making every lazy result globally `Send`.

- Observation: the current empty-root admission and deterministic connection salt are demonstration shortcuts, not an authentication boundary.
  Evidence: `mysql_connection.rs` calls `empty_root_is_admitted`, and the handshake salt is derived from the connection ID.

## Decision Log

- Decision: own PD, region-cache maintenance, and tonic transport exactly once per process; expose cloneable command handles and a session factory to fixed workers.
  Rationale: this permits physical request overlap without serializing the engine or duplicating cluster authorities and background workers.
  Date/Author: 2026-07-19 / Codex.

- Decision: construct each query session inside its worker and allow its lazy decoder, evidence, and retry state to remain thread-local.
  Rationale: the worker owns the session for the connection lifetime, so requiring the returned session and result source to cross threads adds broad type churn without increasing concurrency.
  Date/Author: 2026-07-19 / Codex.

- Decision: use a fixed worker count with rendezvous or a strictly bounded accepted-socket queue.
  Rationale: unbounded thread-per-connection admission is not deployable backpressure. Bounded ownership makes overload and shutdown behavior deterministic.
  Date/Author: 2026-07-19 / Codex.

- Decision: require a mode-0600 TSV auth file containing `username<TAB>host<TAB>mysql_native_password<TAB>*40HEX`, loaded once at startup.
  Rationale: plaintext passwords and hashes in process arguments leak through process inspection. One atomic descriptor per user eliminates parallel-list edge cases and preserves a future multi-plugin shape.
  Date/Author: 2026-07-19 / Codex.

- Decision: implement the actual native-password verifier, OS-generated NUL-free salt, dummy verification for unknown users, constant-time equality, canonical host identity, and AuthSwitchRequest when the client initially selects another plugin.
  Rationale: preserving the handshake shape but accepting empty root would multiply an insecure shortcut. Unknown, wrong, and unsupported credentials must share the same 1045 surface.
  Date/Author: 2026-07-19 / Codex.

- Decision: retain loopback-only binding and defer TLS.
  Rationale: `mysql_native_password` does not protect password-equivalent material against an active or observing network adversary. This campaign proves local deployment concurrency, not public-network security.
  Date/Author: 2026-07-19 / Codex.

## Context and Orientation

The current binary entry is `rust/crates/tidb-server/src/bin/tidb-server.rs`. Configuration is parsed by `node_config.rs`; `real_tikv_node.rs` constructs one `RealTiKvSerialEngine`; `sql_node.rs` accepts and serves one socket at a time; and `mysql_connection.rs` performs the handshake and COM_QUERY loop. Campaign 18's real physical path begins in `tidb-exec/src/real_tikv_read.rs`, crosses `tidb-txnkv/src/read_runtime.rs`, and submits through the tonic worker in `rpc/transport_runtime.rs`.

The tonic layer must split unique lifecycle ownership from cloneable request submission. A process authority owns shutdown and the worker join handle. Session handles may submit requests but cannot close or join the process worker. The shared read authority owns the process region cache; `open_session` creates local `Rc<RefCell<_>>` DirectUnary state inside the calling worker. Closing a session must only cancel that session's in-flight query.

The server owns a fixed-size worker pool and a `Send + Sync` session factory. A socket is handed to a worker before the factory is called, ensuring the returned query session never crosses threads. The authenticated identity is established before COM_QUERY and remains immutable for that connection. Connection tracking covers handshake through disconnect and decrements exactly once on every error or shutdown path.

## Plan of Work

In the transaction slice, separate tonic transport owner lifetime from cloneable `Send + Sync` request handles. Preserve one worker, one BatchCommands channel authority per store, existing unary fallback, cancellation, and completion behavior. Add a concurrency regression proving two handles can overlap and dropping one cannot retire the other.

In the DistSQL slice, introduce a cloneable process read authority that combines the shared region cache with a cloneable transport handle. Its `open_session` method creates query-local DirectUnary state inside the worker. Remove session access to process shutdown and preserve response-owned evidence.

In the executor slice, split `RealTiKvReadEngine::connect` into process authority construction and connection-local session construction. PD timestamp acquisition remains shared and safe; table metadata and query cancellation are session local. Tests must prove isolated snapshot/evidence state across overlapping sessions.

Integrate native authentication, AuthSwitchRequest sequence handling, immutable authenticated identity, overload behavior, active connection tracking, and graceful drain. Delete empty-root admission, deterministic salt, and duplicate accept-loop authority after their behavior is absorbed.

## Interfaces and Dependencies

The transaction layer exposes a unique transport owner plus a cloneable command handle. Only the owner can initiate shutdown and join the worker. The DistSQL layer exposes a cloneable process read authority whose `open_session` constructs thread-local query state. The executor exposes a process `RealTiKvReadAuthority` and a connection-local query session.

The server exposes a `Send + Sync` session factory. Workers call `open_session` after receiving a socket; the returned session and lazy result source remain worker local and need not implement `Send`. The fixed pool owns bounded admission and graceful drain. The authentication catalog is immutable, shared, and host aware; successful verification produces the canonical authenticated identity passed into session context.
