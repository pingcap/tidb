# Execute signed BIGINT predicates inside real TiKV

This ExecPlan is a living document and follows `PLANS.md`.

## Purpose / Big Picture

Campaign 23 turns Campaign 22's deployable direct-projection node into the first useful filtered read node. A stock MySQL client sends a single-table `SELECT ... WHERE ...` to the Rust executable; the planner binds the configured schema, TiDB expression lowering produces exact TiPB signed-integer comparisons, the TiKV DAG contains `TableScan` followed by `Selection`, and real TiKV—not a Rust post-filter—returns the matching rows. The same process and connection remain valid through the already-proven three-store topology churn and bounded shutdown path.

The bounded semantic surface is ordinary non-null signed `BIGINT` column-versus-integer comparisons (`=`, `!=`, `<`, `<=`, `>`, `>=`) and `AND` conjunctions. Either operand order is accepted. Projection columns remain source ordered; predicate-only columns are appended once to scan input and excluded through explicit output offsets. `NULL`, unsigned values, coercions, `OR`, functions, arithmetic, subqueries, joins, aggregates, ordering, limits, writes, and dynamic catalog remain explicit gaps.

This campaign deliberately uses a full table key range plus a source-shaped TiKV `Selection`. Clustered-primary-key range detachment is the next optimization boundary; it must optimize the same physical semantics rather than becoming a special-case replacement for general predicates.

## Decision Log

- Decision: implement TiKV `Selection`, not a clustered-key equality shortcut.
  Rationale: a key-only shortcut would leave stored-column predicates unsolved and create a second semantics path. Selection is the source-shaped general operator; ranger can later optimize its access conditions.

- Decision: scan projection columns first and append deduplicated predicate-only columns.
  Rationale: stable input offsets make expression encoding simple, retain MySQL projection order, and eliminate conditional result reshaping. DAG output offsets are exactly the projection prefix.

- Decision: flatten `AND` into repeated Selection conditions.
  Rationale: this matches TiDB's list-based TiKV Selection contract and avoids inventing a logical-AND scalar encoding for the first boundary.

- Decision: do not add a separate server implementation slice or dynamic catalog prerequisite.
  Rationale: COM_QUERY already forwards SQL and frames variable row counts. The product proof belongs at the real planner/DAG/TiKV boundary; dynamic infoschema is an independent multi-table/DDL-visibility milestone.

- Decision: all slice manifests remain dependency-ready with empty `depends_on`; this plan enforces the intra-campaign DAG.
  Rationale: predecessor source families remain conservatively PARTIAL, so checked `covered` dependencies would make successor dispatch impossible.

## Implementation DAG

    A proto + expression PB wire --------+--> B planner bind -----+
                                        |                        |
                                        +--> C physical Selection +--> D TiKV DAG --> E real executor --> F live proof

A freezes the exact dependency-closed TiPB wire and its expression-owned signed comparison conversion. B and C then run in parallel. D consumes both planner interfaces and A's converter. E composes the production query path. F is the only live slice.

## Plan of Work

Stage A extends the dependency-closed `select.proto` projection with exact upstream `FieldType`, `ExprType`, the six integer comparison `ScalarFuncSig` values, `Expr`, `TypeSelection`, `Executor.selection`, and `Selection`. It also adds an expression-owned converter from a resolved signed-BIGINT comparison to TiPB. Constants use TiDB `codec.EncodeInt`-compatible memcomparable bytes. Column references encode zero-based executor input offsets. Scalar functions keep operand order and exact integer signatures. Wire and converter tests assert tags, enum values, optional presence, source flags, round trips, and fail-closed unsupported inputs.

Stage B replaces the planner's blanket predicate rejection with bounded binding. It resolves qualified columns against the configured table, recursively flattens `AND`, accepts only the six comparison shapes, computes stable scan offsets, and retains every existing rejection before runtime side effects.

Stage C completes the source-shaped physical Selection owner above the table scan. It owns resolved conditions and input offsets without absorbing protobuf serialization or executor request construction.

Stage D widens `ConstructDAGReq` from one scan to the exact bounded TiKV list `[TableScan, Selection]`, leaves `Selection.child` absent, retains empty executor-ID presence, and consumes caller-supplied output offsets. Existing table/index scan behavior remains unchanged.

Stage E composes planner output, expression conversion, DAG construction, RequestEnvelope shape, full table ranges, real PD TSO, DistSQL, and result metadata. It publishes immutable plan evidence before completion. Focused tests prove no Rust row filtering, predicate-only columns do not leak, empty results are valid, cancellation remains authoritative, WHERE becomes positive transport coverage, and writes still fail before TSO/send.

Stage F adapts the Campaign 22 topology runner. On one persistent authenticated stock connection it proves `id=-7`, `id!=0`, `balance<0`, `balance<=77`, `id>0`, `id>=0`, `balance>1000`, and reversed `77<=balance`, comparing row sets because no `ORDER BY` is present. The stored-column predicate must publish `[TableScan, Selection]`. The same PID/authority/session spans A to B to C to restarted B. A real `id=-7` query is blocked by the prewrite barrier before SIGTERM; ordered shutdown and complete cleanup remain mandatory.

## Validation and Acceptance

Leaf agents use source inspection, focused tests, formatting, and `git diff --check`; they do not run workspace builds or the shared gate. Every bug regression is captured failing against the predecessor for the intended reason before it passes. Once all six leaves and owner evidence freeze, the steward records exact predecessor transfers, freezes integrated membership, and runs exactly one expensive campaign gate:

    python3 rust/scripts/work-unit-queue.py check
    CARGO_BUILD_JOBS=12 rust/scripts/rewrite-gate.sh integrate
    make -j12 lint

`make bazel_prepare` is not required unless the final diff unexpectedly changes Go imports/files/tests, Bazel metadata, or Go modules. `make bazel_lint_changed` is not run.

Ready acceptance requires exact TiPB bytes, planner/DAG focused tests, production executor tests, the live stock-client matrix against real TiKV, topology continuity, bounded cancellation, ordered successful shutdown, tag-owned cleanup, the shared gate receipt, and repository lint. No single layer or mock result is sufficient.
