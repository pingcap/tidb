# Connect TiDB table planning to an injected unary read runtime

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`,
`Decision Log`, and `Outcomes & Retrospective` current as work proceeds.

Reference: `PLANS.md` at repository root. This plan follows the repository
requirement for an ExecPlan on a significant refactor.

## Purpose / Big Picture

Campaign 08 closes two adjacent gaps in the Rust read path. First, a normal
TiKV table access path becomes a real planner task and table-reader plan rather
than isolated scan metadata. Second, an executor table/index reader sends an
already-built request through the checked coprocessor coordinator to an
address-directed unary client supplied by the caller, then decodes the returned
rows through the existing response owner. A separate checked inventory pins the
external `client-go` source and complete original test universe so later gRPC,
region-cache, retry, and lock-resolution ports start from the actual upstream
implementation rather than TiDB wrapper guesses.

The observable campaign result is an in-process source-shaped read test that
passes one table/index request through the same planner, request, response, and
reader authorities used by production Rust modules. This campaign deliberately
does not claim a network socket, live TiKV, PD discovery, retry, lock resolution,
or COM_QUERY integration.

## Surprises & Discoveries

- Observation: TiDB does not own the actual TiKV connection, dispatch, retry,
  or lock-resolution algorithms.
  Evidence: `pkg/store/copr` delegates through the pinned
  `github.com/tikv/client-go/v2` module, whose `internal/client.Client` accepts
  an address, request, and timeout.
- Observation: the previously translated planner index choice and scan-to-DAG
  paths can disagree if table and index plan metadata grow as separate
  authorities.
  Evidence: Campaign 07 review found candidate identity could diverge from the
  serialized scan. Campaign 08 therefore extends the existing datasource task
  authority and keeps the validated DAG lowerer as an explicit prerequisite.
- Observation: the three existing response/RPC/reader slices share two Rust
  paths and cannot safely be extended in separate worktrees.
  Evidence: `query_runtime/query_response.rs` and `response_channel.rs` occur in
  more than one predecessor write set. One terminal successor absorbs all three.

## Decision Log

- Decision: track client-go in separate external inventories without adding its
  counts to TiDB product-parity percentages.
  Rationale: the upstream module is part of the behavior to port, but it is not
  a TiDB repository source/test anchor and must not distort existing ledgers.
  Date/Author: 2026-07-18 / Codex.
- Decision: implement an injected address-directed unary capability before a
  concrete gRPC client.
  Rationale: this directly translates the `SendRequest` boundary and connects
  all currently checked TiDB ownership while keeping connection pooling, TLS,
  PD, retries, and lock resolution explicit future client-go slices.
  Date/Author: 2026-07-18 / Codex.
- Decision: do not place an address in region-task topology.
  Rationale: client-go chooses an address after locating a region; routing state
  belongs to the transport, not the region task's immutable identity.
  Date/Author: 2026-07-18 / Codex.

## Context and Orientation

`rust/workstreams/slices/` contains exact ownership contracts. The planner
successor absorbs the current live index-choice owner plus table scan/reader
metadata. The unary successor absorbs `distsql-tikv-unary-rpc-contract`,
`distsql-query-response-runtime`, and `executor-table-index-reader-runtime` so
only one agent owns the shared response lifecycle.

The external module is pinned by `go.mod` at
`github.com/tikv/client-go/v2 v2.0.8-0.20260708122311-01bd8f99f4da`.
Its production source inventory and complete test declaration inventory must
be deterministic and checksum-bound to that exact module version.

## Plan of Work

First add the client-go inventory generator and checked TSV artifacts under
`rust/difftests`. The generator resolves the exact pinned module from `go.mod`,
rejects version drift, inventories every production Go file, invokes the
existing AST declaration helper for every original Test/Benchmark/Fuzz
declaration, and supports `--write` and `--check`.

Next claim both checked slices in the primary checkout and create isolated
`codex/<slice>` worktrees. The planner agent edits only its declared planner
paths. The unary agent edits only its declared DistSQL, TxnKV, executor, proto,
test, and evidence paths. Neither agent edits Cargo manifests, shared campaign
records, generated ledgers, or this plan.

After both commits return, integrate them into the primary campaign branch,
inspect the union for duplicate authorities and fail-open behavior, regenerate
the TiDB ledgers, and run the static queue checks. Only then run the single
12-job integration gate. Evidence/status promotion happens after the immutable
gate receipt, followed by receipt-backed claim release.

## Validation and Acceptance

The planner source test must prove a normal non-empty TiKV table path produces
one table scan, one root table-reader plan, and preserves the existing index and
empty-range TableDual paths. It must reject TiFlash, partitions, filters,
ordering, multiple table candidates, and every unsupported task shape.

The unary source tests must prove exact address and timeout forwarding, one
send per prepared logical task, atomic response decoding before coordinator
mutation, logical-order publication, required-row propagation, and exact-once
close. Missing/duplicate routes, unsupported operations, and retry-requiring
region/lock/other/batch errors must fail closed without silently publishing
partial response state.

The client-go inventory check must fail on pin drift, missing files, changed
checksums, and any added/removed Test/Benchmark/Fuzz declaration. The campaign
gate must pass format, strict workspace Clippy, workspace tests, queue/dashboard
checks, inventory checks, parser isolation, and `git diff --check -- rust`.

## Idempotence and Recovery

Inventory writers and ledger generators are safe to rerun. A failed feature
branch remains isolated and can be fixed without touching the other worktree.
If any implementation, test, manifest, or inventory changes after gate begin,
abort the receipt and rerun the complete gate. Never release completed work as
abandoned and never force-delete a worktree containing uncommitted changes.

## Interfaces and Dependencies

The bounded client capability must remain equivalent to:

    SendRequest(address, request, timeout) -> raw response or transport error

The direct query transport owns an exact region-to-address map and composes the
existing `CopReadTaskRuntime`, unary request/response codec, `QueryResponse`,
and `TableIndexReader`. It rejects Analyze, Checksum, TiFlash, retries, and
unrepresented request shapes. The planner returns a table-reader plan only; it
does not directly depend on the transport implementation.
