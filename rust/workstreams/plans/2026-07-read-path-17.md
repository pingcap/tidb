# Connect previous-region lookup, canonical cache maintenance, and BatchCommands

This ExecPlan is a living document maintained under repository-root
`PLANS.md`.

## Purpose / Big Picture

Campaign 17 closes three honest Campaign 16 production boundaries in parallel.
It directly transits the pinned Go `GetPrevRegion` path, moves foreground reads
and background maintenance onto one synchronized RegionCache authority with
the exact peer-vector observation guarding send failures, and extends the
retained tonic transport worker with the real BatchCommands duplex stream.

The campaign admits 14 exact pinned production sources and 65 exact original
obligations. Its Rust write sets do not overlap. It must not introduce a second
cache, PD client, selector, retry loop, completion table, channel pool, or Tokio
runtime.

## Surprises & Discoveries

- Before this campaign, `SharedReadRuntime` used
  `Rc<RefCell<RegionCache<_>>>`, while the background worker moved a different
  cache into `Arc<Mutex<_>>`. The integrated runtime now shares one synchronized
  cache authority and makes injected versus maintained construction explicit.
- Before this campaign, the peer-vector observation guard existed only in
  source-shaped tests. Production now carries the selection-time observation
  into failure handling and revalidates it atomically before mutation.
- Pinned async RegionRequest uses BatchCommands only for the first attempt,
  then returns to the same selector and synchronous retry loop. A unary-first
  async implementation would not be a port.
- `GetPrevRegion` reuses `GetRegionRequest` and `GetRegionResponse`; the missing
  surface is the RPC path and retained client/loader call, not a new model.
- Tonic waits for duplex response headers when opening `BatchCommands`. Doing
  that without the pinned five-second dial bound or shutdown cancellation on
  the sole owner can stall every unary, close, and liveness command.
- A canceled completion was removed from the sole in-flight table only when a
  response later arrived. Cancellation therefore needs a generation-safe
  retirement hook on the existing completion/in-flight authority, not a scan
  or a second pending table.

## Decision Log

- Decision: split the audited maintenance closure at the independent PD wire
  boundary.
  Rationale: previous-region projection owns disjoint Rust files and can be
  reviewed and landed atomically while the cache ownership refactor proceeds.
  Date/Author: 2026-07-19 / root.
- Decision: keep cache ownership, worker lifecycle, peer observation issuance,
  and send-failure consumption in one slice.
  Rationale: splitting those mutations would permit a foreground/background
  cache fork or a stale observation race.
  Date/Author: 2026-07-19 / root.
- Decision: extend the retained unary worker/channel pool for BatchCommands.
  Rationale: a second runtime or pool would make close, generation, and
  forwarding ownership ambiguous.
  Date/Author: 2026-07-19 / root.
- Decision: defer concrete async integration until the BatchCommands stream
  and canonical request policy are available.
  Rationale: pinned Go does not use unary for the first async attempt and does
  not create a second selector/backoff authority.
  Date/Author: 2026-07-19 / root.
- Decision: retain empty `evidence_prerequisites` for these external-module
  slices and record the Campaign 16 capabilities in `support_anchors` and this
  plan.
  Rationale: the checked prerequisite schema currently accepts only the TiDB
  source/test ledgers, not qualified `client-go::` or `pd-client::` anchors.
  Whole-slice `depends_on` would be false because Campaign 17 consumes bounded
  capabilities from still-`partial` Campaign 16 slices rather than requiring
  them to be `covered`. Extending the queue schema is a separate governance
  increment and must not be hidden inside a transaction-runtime leaf.
  Date/Author: 2026-07-19 / root.

## Plan of Work

Create checked slice claims before any production edit. Each leaf works only
inside its manifest write set, reads the exact pinned Go sources and tests
first, and uses only `rustfmt` plus `git diff --check` during implementation.
No leaf runs Cargo.

The previous-region leaf adds `/pdpb.PD/GetPrevRegion` through the retained PD
worker and preserves key encoding, bucket options, endpoint failover, response
validation, and region projection. The cache leaf replaces foreground-only
ownership with one cloneable synchronized cache handle, starts and joins one
maintenance worker, captures peer topology with selection, and consumes that
exact observation before any send-failure mutation. The batch leaf adds the
real tonic duplex RPC, route-scoped streams, pending-before-send publication,
generation-safe demultiplexing, reconnect, forwarding isolation, and exact
close drainage over the existing transport runtime.

Root integrates complete leaf commits, repairs only cross-slice seams, reviews
the combined authority graph, runs exact Go obligations with `go test -p 12`,
and performs one shared Rust gate.

## Validation and Acceptance

Every `module_tests` anchor in the three manifests must be run in its pinned Go
module. After source integration and cross-review:

    cd rust
    CARGO_BUILD_JOBS=12 scripts/rewrite-gate.sh integrate

`make -j12 lint` is required for Ready. Live proof must distinguish local
tonic fixtures from real PD/TiKV behavior. Without live services the campaign
may close only as `PARTIAL`, with real leader change, store restart, forwarding
reconnect, TLS, and concurrent foreground/maintenance proof left explicit.
