# First deployable read-only SQL node

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current according to repository-root `PLANS.md`.

## Purpose / Big Picture

Campaign 19 builds the first independently runnable Rust SQL node: a bounded TiKV configuration, a MySQL TCP lifecycle, direct-column `COM_QUERY` lowering through the existing parser/planner/DAG authorities, a real PD-issued snapshot timestamp, Campaign 18's retained PD/RegionCache/BatchCommands TiKV path, and a stock-MySQL-client proof that returns seeded rows. Unsupported SQL, authentication, configuration, and concurrency fail explicitly.

The campaign owns 12 exact production sources and 51 exact original obligations across seven disjoint slices. Shared crate exports, Cargo manifests, evidence ledgers, and final composition remain root-owned so feature agents cannot create parallel runtime authorities.

## Surprises & Discoveries

- Observation: Campaign 18 proved a live empty range using a fixed timestamp, so it did not establish visibility of committed MVCC rows.
  Evidence: the live topology runner's request used the empty range and a fixed start timestamp.
- Observation: the concrete production DistSQL transport contains `Rc<RefCell<_>>` and is not `Send`.
  Evidence: `DirectUnaryQueryTransport` retains its serial response/runtime state; the first node therefore admits one connection at a time instead of hiding it behind threads.
- Observation: no Rust infoschema/catalog loader exists.
  Evidence: planner leaves require pre-resolved table descriptors. The milestone takes an explicit configured schema/table/table-ID/column descriptor and rejects all unknown objects.
- Observation: tonic's PD TSO bidi open can deadlock when PD waits for the first request before publishing response headers.
  Evidence: the first live run timed out for 60 seconds; the focused server-withheld-header regression failed before `open_and_request` queued the first request and passes afterward.
- Observation: the retained Cop response coordinator rejects unordered delivery, and an empty `DAGRequest.output_offsets` makes a successful TiKV scan project zero columns.
  Evidence: the next two live runs failed with `unordered_response` and then returned an empty result despite one successful BatchCommands dispatch. Exact metadata/output-offset regressions now cover both production boundaries.

## Decision Log

- Decision: extend the existing dedicated PD worker with a persistent TSO stream rather than creating another PD client or accepting an externally supplied timestamp.
  Rationale: one control-plane owner preserves membership routing, deadline, stream retirement, cluster identity, and monotonicity while making the node independently deployable.
  Date/Author: 2026-07-19 / root.
- Decision: admit only one signed `BIGINT PRIMARY KEY CLUSTERED` table and direct-column projection in the first milestone.
  Rationale: this reaches the real product path without inventing infoschema, predicate, partition, or common-handle semantics.
  Date/Author: 2026-07-19 / root.
- Decision: keep the first node explicitly serial.
  Rationale: this reflects the concrete transport's ownership model honestly and avoids an unsound thread wrapper; concurrency becomes a later root-layer transport refactor.
  Date/Author: 2026-07-19 / root.

## Outcomes & Retrospective

The product milestone is live: a stock MySQL client connected to the Rust
binary and read the exact seeded rows `[-7, 0, 42]` from a real TiKV through a
real PD-issued TSO and the retained BatchCommands path. The proof recorded PD
cluster identity, physical table and region identities, one physical
BatchCommands publication with no unary fallback, zero leaked connections,
and total tag-owned topology cleanup.

The live loop found three integration gaps that isolated mocks did not expose:
TSO open-before-send, unordered request metadata, and missing tipb output
offsets. Each was fixed at its owning source-shaped boundary and received a
focused regression. The remaining product boundary is intentionally narrow:
the node is serial, loopback-only, empty-password root-only, and exposes one
statically configured non-partitioned signed clustered-key table with a direct
column projection. It is deployable as this read-only milestone, not a claim
of general TiDB SQL/session/catalog parity.

## Context and Orientation

`tidb-server` already owns handshake parsing, framed command dispatch, listener lifecycle, and incremental result-set writing, but its `Connection` directly constructs an in-memory `Session`. `tidb-planner` owns TiKV scan/read-task lowering, `tidb-exec` owns DAG construction and table-reader decoding, and `tidb-distsql` owns the production Campaign 18 transport. Campaign 19 adds an injected serial query-engine boundary and composes these authorities without copying their policy.

## Plan of Work

The bootstrap slice parses only `-P`, `--host`, `--store tikv`, `--path`, and the explicit bounded catalog descriptor. The PD slice ports the pinned TSO wire exactly and retains one leader-routed stream in the existing worker. The codec slice completes physical-table record boundaries. The planner slice validates the complete admitted AST before lowering. The executor slice requests a fresh TSO, builds the exact range and DAG request, and consumes the retained real transport. The connection slice executes the handshake/command/result lifecycle with exact cleanup. Root then exports and composes the new leaves in the executable binary.

The live proof starts a unique TiUP topology, seeds a table through Go TiDB, obtains its physical table ID, launches Rust on a distinct port, runs a stock MySQL query against Rust, and asserts exact nonempty rows plus structured TSO/region/BatchCommands and cleanup evidence. Go TiDB is fixture setup only; it does not supply the Rust snapshot timestamp or answer the asserted client query.

## Concrete Steps

From `rust/`, validate and claim ready leaves:

    python3 scripts/work-unit-queue.py check
    python3 scripts/work-unit-queue.py claim-slice --owner <slice> --slice <slice>

Leaves run source assertions, `rustfmt --check`, and `git diff --check`; they do not run Cargo. Root integrates exports and manifests, then runs:

    CARGO_BUILD_JOBS=12 scripts/rewrite-gate.sh integrate

After the live proof and evidence promotion, run from repository root:

    make -j12 lint

## Validation and Acceptance

Acceptance requires a real executable, bounded startup failures, a stock client handshake, PING/QUERY/QUIT, a real nonzero PD TSO, exact planner/DAG/range construction, a BatchCommands-first real TiKV request, exact seeded rows, zero leaked connections, and total cleanup of the Rust process, TiUP processes, endpoints, registry row, tag directory, and temporary catalog/configuration.

An empty result, fixed/wall-clock timestamp, unary-only proof, seed in-memory `Cluster`, fake transport, or direct opaque DAG/key construction fails acceptance.

## Idempotence and Recovery

The live runner owns a unique tag and every child PID and installs cleanup traps before startup. TSO stream failures retire the current stream before bounded retry; ambiguous TiKV publication is never automatically duplicated outside the existing request coordinator. Re-running first proves that no owned endpoint or registry row remains.

## Artifacts and Notes

The static catalog is a visible milestone boundary, not an implicit fallback. The binary logs the admitted table descriptor, PD cluster identity, snapshot TSO, located region IDs, BatchCommands-first attempt, and connection-count transitions as structured evidence.

## Interfaces and Dependencies

The PD client exposes a synchronous `get_timestamp` backed by its retained worker. `ConfiguredTable` is the sole bounded catalog descriptor. `ReadOnlyScanPlan` owns admitted SQL validation and physical scan lowering. `RealTiKvReadEngine` retains the production transport and requests a fresh timestamp per statement. `serve_mysql_connection` borrows that serial engine and owns packet sequence/reset and exact cleanup. Root owns all crate exports and the final binary composition.
