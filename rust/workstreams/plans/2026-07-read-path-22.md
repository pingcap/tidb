# Survive TiKV topology churn and report every process shutdown failure

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` up to date as work proceeds.

Reference: `PLANS.md` at repository root. This plan must be maintained according to it.

## Purpose / Big Picture

After this campaign, the bounded Rust SQL node remains usable while the TiKV leader for its configured table moves between stores, one leader process dies, a surviving peer takes leadership, and the stopped TiKV returns at the same address. Authenticated stock MySQL clients continue receiving Campaign 21's exact rows from real TiKV rather than observing a stale connection, a silently poisoned proxy route, or an unnecessary process restart.

The executable also owns a provable shutdown sequence. It first stops admission and drains every SQL session, then stops and joins RegionCache maintenance, then the TiKV transport worker, and finally the PD worker. Worker panics, missing close acknowledgements, partial worker-pool construction, and simultaneous node/drain/authority failures are returned and logged instead of disappearing in `Drop` or behind the first error. A successful live run emits the ordered shutdown stages and exits zero; deterministic focused regressions inject each failure class and require a nonzero result.

This campaign hardens the runtime below every future SQL feature. It does not add SQL syntax, expressions, writes, TLS, dynamic catalog behavior, or transaction semantics. Those domains can continue in parallel because the six Campaign 22 write sets do not enter planner, expression, datatype, or catalog modules.

## Surprises & Discoveries

- Observation: the transport already knows two different generations but does not carry both to DistSQL.
  Evidence: `rust/crates/tidb-txnkv/src/rpc/batch/transport.rs` keeps `ActiveStream.connection_version` beside `BatchRoute.generation`, while `BatchPublicationReceipt` returns only the route and request IDs. A successful response containing StoreNotMatch therefore reaches DistSQL without the physical ChannelPool version that `close_address_version` requires.

- Observation: the current StoreNotMatch omission is deliberate and documented, not a hidden typo.
  Evidence: `rust/crates/tidb-distsql/src/cop_paging/direct_unary_query_transport.rs` explains that a delayed response cannot be turned into an address-wide mutation because the response lacks the selected physical channel version. The correct repair is to preserve immutable dispatch evidence, not to restore an unconditional address close.

- Observation: automatic cleanup currently hides worker failure at all three process authorities.
  Evidence: `TransportRuntime::shutdown`, `PdClientShared::drop`, and `BackgroundRegionCacheInner::drop` discard close acknowledgements or `JoinHandle::join` results. `BackgroundRegionCache::shutdown` is fallible but depends on `Arc::try_unwrap`, so the production path cannot use it as an ordinary owner protocol while cloneable session handles share the same type.

- Observation: server shutdown can hide failures even before cluster authorities are dropped.
  Evidence: `spawn_workers` can return after a later spawn failure without explicitly joining workers already created; the accept loop does not receive immediate terminal worker state; `join_workers` returns on the first panic; and `accept_result.and(join_result)` loses the drain error when admission already failed.

- Observation: the exact upstream shutdown order is already an inventoried obligation rather than a new design preference.
  Evidence: pinned client-go `tikv/kv.go` closes RegionCache before its TiKV RPC client and closes PD afterward. `client-go::tikv/kv_test.go:285:TestKVStoreCloseCheckRegionCacheClosedBeforePDClose` is currently untriaged and is assigned to the ordered authority slice.

- Observation: Campaign 18 and Campaign 21 each prove only half of the needed live boundary.
  Evidence: Campaign 18 uses a custom transaction-test process to restart one forwarded follower while preserving the leader. Campaign 21 uses stock clients but starts only one PD and one TiKV and performs no topology mutation before terminating the SQL node.

- Observation: response-time physical evidence is insufficient to prove that a query was in flight before a live store freeze.
  Evidence: the BatchCommands publication receipt knows physical address, ChannelPool version, stream generation, and forwarded target before completion, but the pending trait discarded that route and the server emitted transport evidence only after result finish or close. Campaign 22 therefore requires an observer over immutable publication evidence; the live runner must not use timing sleeps as a substitute.

- Observation: the shared-gate receipt hashes integrated campaign membership and the local Go-test domain manifest.
  Evidence: Campaign 21 froze `integrated-members.tsv`, campaign status, evidence transfers, and domain-owner rows before `gate-begin`. Releasing first or changing those inputs between receipts would make Campaign 22's six-slice receipt set inconsistent. Campaign 22 has 108 exact obligations: 103 predecessor transfers and five direct UNTRIAGED promotions.

- Observation: making worker termination observable required cleanup ownership to begin at accept-time, not worker-receive-time.
  Evidence: a registration created only after `recv` leaks an accepted socket when a queued work item is dropped with its receiver. Campaign 22 moves the RAII registration inside the queued work value, recovers poisoned socket state for containment while retaining the error, and joins every worker even when admission and drain both fail.

- Observation: PD metadata recovery does not prove that a failed same-address store is selectable again.
  Evidence: the live A-to-B-to-C-to-restarted-B run held exact PD leader, healthy voter, listener, and two exact Go-client reads, yet the retained Rust process made thirty-two unary A/C `NotLeader(B)` attempts and expired. `on_send_failure` had marked B `Unreachable`; PD refresh restored `Resolved` metadata but preserved that liveness, and every selector therefore rejected the real leader forever.

- Observation: ChannelPool version and BatchCommands stream generation must remain independent during ordinary process restart.
  Evidence: the pinned client-go policy and txnkv stream tests keep the same address-local channel version across ordinary unavailable/connection failure while recreating a later BatchCommands stream generation. Only an exact contract such as direct StoreNotMatch or remote gRPC Canceled retires the observed channel version.

- Observation: the repository's current Go TiDB binary cannot be assumed wire-compatible with a pinned older PD/TiKV playground.
  Evidence: the current pre-release TiDB requested a QueryRegion RPC absent from the Campaign 18 v8.5.6 topology. The live runner therefore requires an explicit failpoint-enabled TiDB v8.5.6 fixture for setup and the deterministic prewrite barrier, while every asserted client read still goes through the Rust SQL node.

- Observation: the default 30-second connection timeout correctly closes an idle persistent MySQL session during a long topology mutation.
  Evidence: macOS surfaced the expired socket receive timeout as `EAGAIN`; protocol tracing confirmed this was the configured idle-command deadline, not connection corruption. The campaign explicitly raises that existing timeout for its long-lived proof rather than retrying or suppressing the error.

## Decision Log

- Decision: harden topology and lifecycle before widening the central SQL-node runtime.
  Rationale: rolling store restart and leader movement are ordinary distributed-database behavior and underpin the cluster-level strangler strategy. Every future SQL operator would inherit silent channel or shutdown failure if this boundary stayed incomplete. Independent SQL translation can continue on disjoint files.
  Date/Author: 2026-07-19 / Codex.

- Decision: represent physical dispatch identity explicitly and keep four identities distinct: physical address, physical ChannelPool version, BatchCommands route/stream generation, and RegionCache route/store identity.
  Rationale: these counters have different owners and lifetimes. Equating any pair creates ABA races in which a delayed response retires a newer channel or a logical forwarding error destroys a shared proxy.
  Date/Author: 2026-07-19 / Codex.

- Decision: a current direct StoreNotMatch closes exactly the physical channel version observed by that request; a stale direct response does not close a newer version.
  Rationale: the directly contacted TiKV rejected the store identity, so that physical connection is suspect, but only the immutable attempt version is safe to retire.
  Date/Author: 2026-07-19 / Codex.

- Decision: a forwarded StoreNotMatch refreshes or invalidates the logical target route without closing the physical proxy channel.
  Rationale: the remote rejection describes the logical target named by `tikv-forwarded-host`. The proxy may concurrently serve healthy direct and sibling-forwarded streams, so closing it would turn a logical topology fact into unrelated transport failure.
  Date/Author: 2026-07-19 / Codex.

- Decision: use separate unique lifecycle-owner types and cloneable request/session handle types for RegionCache maintenance, TiKV transport, PD, and the composed read authority.
  Rationale: `Arc::try_unwrap` is a runtime ownership gamble, and `Drop` cannot return errors. A type that owns cancel/join authority must be non-cloneable; handles must not be able to close process resources.
  Date/Author: 2026-07-19 / Codex.

- Decision: process shutdown order is SQL admission and sessions, RegionCache maintenance, TiKV transport, then PD.
  Rationale: each earlier stage can call the later one. Stopping in dependency order eliminates calls into a client that is already closing and matches the pinned client-go KVStore contract.
  Date/Author: 2026-07-19 / Codex.

- Decision: collect every safely obtainable shutdown error in stage order and preserve a simultaneous node/drain error together with authority errors.
  Rationale: returning only the first error makes later leaks and panics invisible. Once sessions and RegionCache maintenance are stopped, transport and PD can still be asked to close safely even if an earlier join reported failure.
  Date/Author: 2026-07-19 / Codex.

- Decision: keep all six slice manifests at `ready` with empty `depends_on`; enforce the intra-campaign DAG in this ExecPlan and each slice's `support_anchors`.
  Rationale: checked whole-slice dependencies require the predecessor to be `covered`, but these broad source families will remain conservatively `partial`. Encoding the implementation order as `depends_on` would make the campaign permanently unclaimable.
  Date/Author: 2026-07-19 / Codex.

- Decision: do not claim direct/forwarded StoreNotMatch race coverage from the topology live run.
  Rationale: leader transfer and real process death do not deterministically produce the exact delayed success-envelope race. Focused source-shaped tests prove that policy; the live run proves the connected SQL-node topology and shutdown behavior.
  Date/Author: 2026-07-19 / Codex.

- Decision: publish exact BatchCommands attempt identity through a request-local observer before waiting for completion.
  Rationale: the server installs the observer after query construction and before the first row pull. The callback fires only after the transport has a real publication receipt, so the live runner can freeze the exact leader without guessing from pre-dispatch query activity. Physical channel version and BatchRoute stream generation remain separate fields.
  Date/Author: 2026-07-19 / Codex.

- Decision: restore a failed store only through a real background TiKV health probe against the exact unchanged store generation.
  Rationale: PD owns store metadata, not data-plane reachability. Probe I/O runs outside the cache lock; publication revalidates store ID, epoch, resolve state, address, and observed liveness. Only explicit `Reachable` may recover the store, so delayed, unknown, or failed probes cannot revive a replaced or still-dead target.
  Date/Author: 2026-07-19 / Codex.

- Decision: build the shutdown barrier from a real prewrite lock instead of a sleep or synthetic transport hook.
  Rationale: a committed helper-region primary plus an asserted table-region secondary lock makes the stock client block for a storage reason. Removing helper quorum prevents lock resolution while the table leader remains available long enough to publish the exact Rust request identity; only then is that leader frozen and SIGTERM sent.
  Date/Author: 2026-07-19 / Codex.

`ChannelPool version` means the monotonically increasing identity of one physical tonic channel created for an address. `BatchRoute generation` means the generation of one direct or forwarded BatchCommands duplex stream. A forwarded stream connects physically to a proxy TiKV but asks it to relay to a separate logical TiKV through the `tikv-forwarded-host` header. `StoreNotMatch` is a TiKV region error saying the request's store identity does not match the TiKV that handled it.

The existing TiKV transport owner lives in `rust/crates/tidb-txnkv/src/rpc/transport_runtime.rs`; request handles are cloneable, but shutdown returns no result. The batch layer in `rust/crates/tidb-txnkv/src/rpc/batch/transport.rs` knows the physical channel version at publication time. Campaign 22 must carry that immutable value into both successful direct-unary and BatchCommands responses so a region error can retire the exact observed physical generation.

The PD client in `rust/crates/tidb-pd-client/src/client.rs` is currently a cloneable `Arc` whose last `Drop` closes and joins its worker. The maintained RegionCache in `rust/crates/tidb-txnkv/src/region/background.rs` similarly combines cloneable cache handles with the maintenance join handle. Campaign 22 separates each unique owner from its handles and composes those owners in the executor layer.

## Plan of Work

Milestone 1 establishes immutable physical dispatch evidence and fallible leaf workers. In `txnkv-physical-channel-evidence-runtime`, add a public immutable evidence value that carries physical address and ChannelPool version and pair it with the existing BatchRoute identity. Preserve it in synchronous direct-unary success, BatchCommands publication, the pending completion, and terminal transport errors. A cloned request handle can inspect only its own attempt evidence; it cannot close or join the worker. Change the unique transport owner's consuming shutdown to return typed errors for command send failure, missing close acknowledgement, and worker panic. Drop may invoke best-effort containment but production tests and the executable must call explicit shutdown.

In parallel, `pd-fallible-worker-lifecycle-runtime` splits the current shared PD value into a unique owner and cloneable request handles without duplicating the Tokio runtime, endpoint clients, membership state, or retained TSO stream. Explicit owner shutdown first cancels in-flight retained work, then asks the worker to close, then joins it exactly once. A deterministic test must inject each failure after first proving the old production API would report success; afterward it must observe the typed error. This milestone is accepted when the focused TiKV and PD lifecycle tests pass without a workspace build.

Milestone 2 applies the exact StoreNotMatch policy. `distsql-store-not-match-exact-channel-runtime` consumes the attempt evidence rather than querying the current pool after completion. For a direct request whose RegionCache observation is still current, call `close_address_version` with the exact physical address/version, then apply the existing route recovery and retry. If that response is delayed past route replacement, it may update no current topology and must not close the newer channel. For a forwarded request, never close the physical proxy because of StoreNotMatch; invalidate or refresh only the logical target route, preserve direct/sibling-forwarded proxy streams, and retry through the canonical selector. Tests must cover direct current, direct stale after replacement, forwarded current, forwarded stale, same physical proxy with two logical targets, and cancellation winning before mutation.

Milestone 3 composes explicit process ownership. `executor-ordered-read-authority-shutdown-runtime` owns changes in the lower maintained-cache files as well as `real_tikv_read.rs`. Split `BackgroundRegionCache` into one non-cloneable maintenance owner and cloneable cache handles, and split the production read authority into a unique process owner plus cloneable session openers. Session handles increment an explicit lease or equivalent lifecycle count and cannot outlive a successful process shutdown. After server workers are drained, the owner shuts down RegionCache maintenance, TiKV transport, then PD. It records all safely obtainable stage failures in order. Tests must prove exact order, no duplicated authority, rejection while a session lease remains, successful retry after the lease is dropped, each injected worker panic, and the upstream `TestKVStoreCloseCheckRegionCacheClosedBeforePDClose` invariant.

Milestone 4 makes the executable consume that owner correctly. `server-fallible-process-shutdown-runtime` must not rely on factory `Arc::try_unwrap`. The fixed worker pool reports terminal worker state to the accept loop. If worker N fails to spawn, already-created workers receive closure and are joined before construction returns. If a running worker dies, admission stops and the death is retained even if another worker remains available. Drain joins every worker and accumulates every panic rather than returning at the first. `run_configured_node` performs authority shutdown even when admission or drain failed and returns a combined ordered error when both node and authority stages fail. A success log is emitted only after every stage succeeds; a structured failure log names every failed stage and the binary returns nonzero.

Milestone 5 runs the product proof. `server-live-topology-churn-shutdown-proof` creates a unique TiUP tag with three PD and three TiKV nodes plus one Go TiDB used only to create the table and discover its physical ID. The Rust executable answers every asserted stock-client query. The runner captures the table region, its peers, exact leader store, store addresses, process IDs, and the Rust physical channel evidence before mutating anything.

Keep authenticated stock clients connected and query the exact projection `SELECT balance AS amount, id FROM campaign20.rows`. Transfer the table-region leader from store A to B and require all completed queries to return exactly `(913,-7)`, `(-2048,0)`, and `(77,42)`. Kill the exact tag-owned process for B, wait for PD to elect surviving store C and for the region to have no down or pending leader, and require queries to recover through the retained Rust process. The transaction layer must expose an immutable physical dispatch evidence value containing at least the physical address and ChannelPool version. BatchCommands evidence also retains the existing direct-or-forwarded BatchRoute and its stream generation. Direct unary and BatchCommands successful responses expose the evidence selected before send; terminal transport errors keep their existing typed physical identity. DistSQL must not call a current-state inspection method to reconstruct past dispatch identity.

The unique TiKV transport owner exposes a consuming fallible shutdown. Cloneable transport handles expose request submission and exact-generation close commands but no worker cancellation or join capability. The unique PD owner follows the same shape: request handles are cloneable; the owner alone cancels, closes, and joins.

The RegionCache layer exposes one non-cloneable maintenance owner and cloneable cache handles. Production maintenance also owns a cloneable TiKV liveness capability: it plans immutable store observations under the cache lock, probes outside the lock, and publishes only an exact explicit-Reachable result. The composed executor process owner retains the RegionCache owner, TiKV transport owner, and PD owner in explicit dependency order. Its cloneable session opener contains only capabilities needed to create worker-local sessions and maintains a session lease count visible to shutdown. The consuming executor shutdown returns an ordered aggregate error whose entries identify `region_cache`, `tikv_transport`, or `pd`.

The server node receives the cloneable session opener while `run_configured_node` retains the unique executor process owner. A worker terminal-state channel makes unexpected exit visible immediately. Worker-pool construction owns cleanup of every successfully spawned prefix. After the node stops and all workers join, `run_configured_node` consumes the process owner and combines node/drain and authority results without `Result::and`, early-return loss, or `Arc::try_unwrap`.

Structured lifecycle events must carry stable stage names and outcomes so the live runner can validate order without scraping prose. A successful `sql_node_stopped` event is emitted only after authority shutdown completes. Failure output contains every observed stage failure but never secrets, authentication hashes, salts, request bodies, or table row data beyond the already-approved live summary.
