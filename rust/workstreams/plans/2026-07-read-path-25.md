# Execute a configured two-relation join against real TiKV

This ExecPlan is a living document and follows `PLANS.md`. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current while implementing it.

## Purpose / Big Picture

Campaign 25 turns the single configured table SQL node into a bounded multi-relation read node. After implementation, a stock MySQL client can select direct signed `BIGINT` columns from exactly two configured real TiKV tables and join them with one non-null equality through `INNER JOIN ... ON`, `INNER JOIN ... USING`, `CROSS JOIN`, or comma syntax. Both scans use one PD timestamp, preserve Campaign 24 clustered-handle ranges and residual TiKV Selection, and feed a TiDB-side join; no in-memory fixture or independent snapshot may satisfy the proof.

The boundary is intentionally narrower than general joins. It admits two nonpartitioned configured tables, unique visible aliases, direct projections, local signed `BIGINT` comparisons joined by `AND`, and one cross-side non-null equality. It rejects more relations, derived tables, subqueries, NULL/coercion/collation semantics, compound join predicates, outer/semi/anti joins, aggregates, ordering, limits, DML, dynamic InfoSchema, and non-BIGINT values before runtime side effects.

## Decision Log

- Decision: make one bounded two-relation vertical the successor, not a dynamic-catalog leaf or a general hash-join rewrite.
  Rationale: it creates the next observable SQL-node capability while keeping catalog lease, DDL visibility, complex types, and join algorithms independently testable.
  Date/Author: 2026-07-19 / Codex.

- Decision: acquire one PD timestamp before either scan.
  Rationale: independent timestamps would violate one SQL statement snapshot and could return a join result that never existed.
  Date/Author: 2026-07-19 / Codex.

- Decision: retain local predicates in each existing scan path and execute only the cross-side equality in TiDB Rust.
  Rationale: TiKV owns scan and Selection pushdown; joins are a TiDB-side operator. This preserves the source architecture and avoids client-side filtering disguised as a join.
  Date/Author: 2026-07-19 / Codex.

- Decision: use exact source-evidence prerequisites at minimum `PARTIAL`, not whole-slice `depends_on`, for bounded provider capabilities.
  Rationale: the provider slices conservatively remain `PARTIAL` because their broad Go source families retain explicit gaps. Exact anchor ownership makes downstream slices claimable as soon as the named capability exists without falsely requiring the entire provider to become `COVERED`. Initially A is claimable; after Campaign 24 evidence refresh D and the independent F0 server foundation are also claimable. B, C, E, and F1 unlock in DAG order as their exact provider anchors move to the named PARTIAL owners.
  Date/Author: 2026-07-19 / Codex.

- Decision: promote completed campaign members incrementally while retaining their claims, then run one final shared gate only after all seven members freeze.
  Rationale: exact evidence dependencies must unlock B/C/E/F1 as soon as their provider exists. Deferring every ledger/status transfer to campaign close serialized the implementation DAG behind bookkeeping even though the expensive validation gate is correctly campaign-wide.
  Date/Author: 2026-07-19 / Codex.

- Decision: split the original server stage into F0 configuration/lifecycle/harness foundation and F1 live-query proof.
  Rationale: the original eleven-source, fifty-three-test server slice was the campaign's largest leaf and unnecessarily held independent preparation behind E's join-runtime prerequisite. F0 now consumes only the already-promoted shared-harness anchor and can be claimed immediately; F1 retains E, consumes F0, and owns the actual MySQL-to-real-TiKV proof.
  Date/Author: 2026-07-19 / Codex.

## Plan of Work

Stage A ports case-insensitive schema/table lookup, stable IDs, source column order, and duplicate validation into `configured_catalog.rs`. It first exposes one checked `ConfiguredTable` construction/validation and identifier-folding seam from the existing single-table planner so both catalog shapes share invariants instead of drifting. It must be immutable and explicit that InfoSchema lease, schema versions, partitions, temporary tables, views, and DDL changes are outside the boundary.

Stage B traverses exactly one two-relation AST, resolves aliases against the configured catalog, binds direct projections and local predicates to their owning relation, and rejects ambiguity before timestamp acquisition. It does not classify or execute the cross-side join predicate.

Stage C consumes B and the existing typed join concepts to build left and right scan plans, stable flattened FullSchema offsets, one cross-side equality, visible projection offsets, and residual predicates. `INNER ... USING` coalesces visible metadata while retaining both physical inputs. The stage exports all three Campaign 25 planner modules through the single planner routing seam.

Stage D introduces a multi-read authority around the existing real-TiKV reader. It refactors that reader once around an internal execute-plan-at-supplied-snapshot seam, acquires one timestamp, submits both planner scans with their exact Campaign 24 ranges and residual Selection, propagates one cancellation token, and publishes immutable per-relation evidence. It must not call the existing single-read public entrypoint twice if that reacquires timestamps, and it must not duplicate Campaign 24 request/DAG construction in a sibling module.

Stage E consumes both decoded streams and the planner join key. The first implementation may use deterministic bounded nested-loop materialization rather than claiming the full Go hash-join fleet, but it must compare typed signed integers, preserve left then right scan order, emit only equality matches, enforce caller row limits without over-reading, and expose final projected metadata. The executor routing seam exports D and E together.

Stage F0 replaces the singular configured read table with one validated ordered table list across the existing `NodeConfig` and real-TiKV process authority; there is no parallel configuration or lifecycle path. It factors reusable query activity, observer, completion, startup-failure, and configuration conversion seams out of `real_tikv_node.rs`, retaining the existing single-table behavior and lifecycle regressions. The shared live harness gains only defaultable fixture-preparation, server-argument, and ready-validation hooks so Campaigns 22-24 remain unchanged. F0 does not implement multi-relation dispatch, create two-table fixture rows, assert join SQL, or claim topology proof.

Stage F1 consumes F0 without editing its configuration, lifecycle, or harness files. It owns the new multi-relation session and the actual query dispatch through the configured planner/executor path. Fixture setup writes rows to two real TiKV tables. One persistent stock connection proves aliases, ON, USING, CROSS/comma with local predicates, projections from both sides, no-match results, leader churn, a blocked query before SIGTERM, ordered shutdown, zero exit, and complete tag-owned cleanup.

## Milestones

## Validation and Acceptance

Leaf agents run only focused package tests, formatting, Clippy for their target, and `git diff --check`. A bug regression must fail against the predecessor for the intended reason before passing. They do not run a workspace gate.

The steward freezes conservative source/test transfers, regenerates ledgers, records integrated membership, and runs one expensive gate from `rust/`:

    python3 scripts/work-unit-queue.py check
    CARGO_BUILD_JOBS=12 scripts/rewrite-gate.sh integrate

Then from repository root:

    make -j12 lint

`make bazel_prepare` is not required unless implementation unexpectedly changes Go imports/files/tests, Bazel metadata, or Go modules. `make bazel_lint_changed` is not run.

Ready acceptance requires all focused tests, exactly one shared timestamp across both real scans, no in-memory fixture reads, stock-client exact rows, topology continuity, bounded blocked-query shutdown, tag-owned cleanup, one shared receipt, and repository lint. The campaign has twenty-five production source anchors and one hundred two original test obligations, satisfying both ordinary admission floors before counting the runnable live consumer.

## Ownership and Recovery

All seven manifests declare pairwise-disjoint Rust paths. Planner and executor routing files each have one steward slice. Because `tidb-exec` has `autotests = false`, stage D owns one existing registered shard so its new module is compiled before integration; stage E exclusively owns `Cargo.toml`, exports both multi-read and configured join modules, and registers its own focused join test. B through F1 use exact evidence prerequisites because their providers truthfully remain PARTIAL; no Campaign 25 whole-slice dependency requires a broad source family to become COVERED. F0 exclusively owns configuration, the generic SQL-node lifecycle (including its configuration-shaped unit fixtures), process lifecycle, and shared-harness files; F1 consumes those promoted seams through its backend adapter and routing owner without editing them. Go anchors currently owned by Campaign 20-24 or older typed-join leaves transfer only after new evidence exists; UNTRIAGED rows promote directly. No Campaign 24 implementation, manifest, plan, campaign, evidence, or live script is edited by this planning increment.

If a leaf fails, abandon only its claim/worktree. If a provider interface changes before a dependent is claimed, amend the provider and dependent manifests together while the campaign is still planned. If the integrated gate fails, release nothing; fix the owning leaf and rerun the frozen gate. Live cleanup follows the shared harness ownership checks and retains diagnostics until every tag-owned process, endpoint, runtime directory, and auth artifact is gone.
