# Execute a prepared signed-BIGINT point read over real TiKV

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds.

Reference: `PLANS.md` at repository root. This plan follows `AGENTS.md`, `rust/PARALLEL.md`, and `rust/workstreams/slices/README.md`; it is a bounded porting vertical, not a claim of full TiDB prepared-statement parity.

## Purpose / Big Picture

Campaign 27 removes the protocol wall in front of a prepared point-read microbenchmark. A MySQL client will be able to prepare `SELECT value FROM configured_table WHERE id = ?`, execute it repeatedly with different signed `BIGINT` values, and close the statement on one authenticated TCP connection. Each execute reaches the existing real-PD/real-TiKV read path and returns a MySQL binary-protocol result set. This is the correct foundation for a custom prepared sysbench point-select workload.

It deliberately does not claim stock `oltp_point_select` or `oltp_read_only` compatibility. Their schema includes strings and indexes that the configured catalog does not yet model, and `oltp_read_only` additionally needs range predicates, aggregates, ordering, distinct, DDL/DML fixture setup, transaction/session commands, and wider parameter types. A successful campaign proves one safe end-to-end statement shape, not a text-query substitution workaround.

## Surprises & Discoveries

- Observation: the protocol already recognizes prepared-command byte values but intentionally exposes their payloads as unsupported raw commands.
  Evidence: `rust/crates/tidb-protocol/src/command.rs` and `rust/crates/tidb-server/src/mysql_connection.rs` decode then reject `COM_STMT_*`.

- Observation: parameter binding cannot be implemented by interpolating execute bytes into SQL text.
  Evidence: the configured planner admits only a typed column-versus-signed-literal comparison in `rust/crates/tidb-planner/src/read_only_scan.rs`; string replacement would bypass parser and literal validation, and would create quoting/encoding special cases.

- Observation: text result rows are incompatible with `COM_STMT_EXECUTE`.
  Evidence: `rust/crates/tidb-protocol/src/resultset_stream.rs` only has text-row encoding. A client that prepared successfully but received text rows would decode the response incorrectly.

- Observation: Homebrew sysbench 1.0.20 linked to MariaDB Connector/C 3.4.9 required TLS despite `--mysql-ssl=off` and crashed in its own fatal cleanup before issuing a statement.
  Evidence: the accepted proof uses a real sysbench 1.0.20 build linked to Oracle MySQL client, keeps native prepared mode enabled, and executes exactly eight events. The server was not weakened with a text fallback or TLS-only compatibility branch.

## Decision Log

- Decision: prioritize prepared point-read support before aggregate work.
  Rationale: it unlocks a real class of benchmark clients and uses the existing exact point-read transport path. Aggregation is useful but does not remove the prepared-protocol blocker.
  Date/Author: 2026-07-20 / Codex.

- Decision: admit exactly one `?` marker bound as one non-NULL signed `MYSQL_TYPE_LONGLONG` value in a configured primary-key equality predicate.
  Rationale: this makes the complete execute packet, type-cache reuse, parser binding, real TiKV read, and binary row protocol observable without falsely accepting arbitrary SQL or parameter coercion.
  Date/Author: 2026-07-20 / Codex.

- Decision: make prepared statements per TCP connection and return binary rows only from `COM_STMT_EXECUTE`.
  Rationale: handles must never cross sessions, and the MySQL command contract—not an ad hoc server shortcut—owns both handle lifecycle and row format.
  Date/Author: 2026-07-20 / Codex.

- Decision: require real TCP, PD, and TiKV acceptance; do not introduce mock session, executor, catalog, or transport implementations for this vertical.
  Rationale: prepared-statement correctness spans packet framing, connection-owned state, typed binding, result encoding, and physical reads. A mocked interface could prove only a local adapter while hiding the exact interoperability failure the user needs removed.
  Date/Author: 2026-07-20 / Codex.

- Decision: reject cursor, fetch, reset, long-data, NULL, unsigned, and non-BIGINT inputs explicitly in this campaign.
  Rationale: silently accepting packet variants without their lifecycle or type semantics would produce false compatibility. Each remains an exact ledger gap.
  Date/Author: 2026-07-20 / Codex.

## Context and Orientation

The existing point-read path is:

    TCP command packet
      -> `tidb_server::mysql_connection::Connection`
      -> authenticated `QuerySession`
      -> `ReadOnlyScanPlan`
      -> one PD timestamp and `tidb_exec::RealTiKvReadSession`
      -> `DistSqlRecordSet`
      -> MySQL result packets

`COM_STMT_PREPARE` receives UTF-8 SQL and must return a statement ID plus parameter and result metadata. `COM_STMT_EXECUTE` contains that ID, a cursor flag, a null bitmap, an optional type vector, and encoded values. The `new_params_bound_flag` is set on an execute that provides types; a later execute may set it to zero and reuse the previous types. `COM_STMT_CLOSE` has no response and must drop only that connection's handle.

The configured catalog currently exposes only non-null signed `BIGINT` clustered-primary-key and stored columns. Therefore `SELECT value FROM db.t WHERE id = ?` is the one accepted SQL shape. A parameter marker is an AST node carrying its zero-based position; a prepared template is a validated SQL plan whose one marker is bound to a `Datum::Int` before the ordinary scan planner opens storage.

## Frozen Public Contracts

The parser/AST owner defines `Expr::ParamMarker { position: usize }`. Parser numbering is left-to-right and restarts at zero per statement. Text `COM_QUERY` continues to reject parameter markers because it has no binding vector.

The planner owner defines a prepared template API with this shape (nearby style may choose exact module names):

    pub struct ConfiguredPreparedPointReadTemplate { /* validated catalog/table/projection/predicate */ }
    pub fn lower_prepared_point_read(
        statement: &tidb_ast::SelectStmt,
        catalog: &ConfiguredCatalog,
    ) -> Result<ConfiguredPreparedPointReadTemplate, PreparedPlanError>;
    pub fn bind(&self, params: &[i64]) -> Result<ReadOnlyScanPlan, PreparedBindError>;

`lower_prepared_point_read` requires one marker exactly where the existing configured primary-key equality accepts a literal. `bind` requires exactly one value and returns the existing `ReadOnlyScanPlan`; it does not introduce a second executor or TiKV decoder.

The protocol owner exposes packet parse/encode types for prepare metadata, execute values, and binary rows. Its execute decoder returns a statement ID, cursor flag, and a `Vec<PreparedValue>` while preserving packet-boundary failures as typed errors. The only accepted `PreparedValue` is `SignedLongLong(i64)`. Binary rows use the MySQL binary-result-set null bitmap and little-endian signed 64-bit cell encoding.

The server owner adds a session-owned registry with monotonically allocated nonzero IDs. Its API prepares one template, returns immutable parameter/result metadata, resolves and binds an execute ID, remembers type vectors only for that ID and connection, and removes an ID on close or connection drop. Unknown/closed IDs are errors; close is silent and idempotent. The registry has no global cache or cross-connection state.

## Plan of Work

Stage A is parser/planner-only. Add the AST marker and parser support, then add a template that shares all configured table/column/WHERE validation with `ReadOnlyScanPlan` and accepts no untyped expression. Tests prove marker numbering, literal/text-query rejection, table/alias binding, exact one-marker admission, and errors before timestamp acquisition.

Stage B is protocol-only and can proceed in parallel with Stage A. Decode the exact prepare/execute/close packet shapes, encode prepare parameter/result definitions, and add a binary row writer for signed BIGINT. Tests use hand-built packets to prove packet lengths, null bitmap, cursor rejection, type-vector reuse representation, little-endian result cells, and no response for close.

Stage C joins A and B at the existing TCP connection. It owns the prepared registry and makes the concrete Rust SQL node call the bound `ReadOnlyScanPlan` through the existing executor/session cancellation path. It must not create another listener, authentication route, snapshot source, record set, row decoder, mock session, mock catalog, or mock executor. Its TCP test starts the actual Rust node against the real fixture, prepares once, executes two different values (the second with type reuse), checks binary result/metadata, proves an unknown and closed ID fail, and proves one connection cannot execute another's handle.

Stage D adds the live proof and benchmark artifact. It creates a Go-TiDB seeded all-BIGINT fixture, starts the Rust node against the same real TiKV topology, runs the exact prepare/execute sequence and exactly eight events through a one-thread custom sysbench Lua point-read script with a 30-second safety cap, validates receipts, and performs tag-owned cleanup. It does not call stock sysbench a success.

## Validation and Acceptance

Acceptance begins with negative packet and SQL cases: truncated execute, bad ID, nonzero cursor, NULL, unsigned or non-BIGINT parameter, wrong parameter count, unsupported SQL, cross-connection ID, and execute after close each fail without PD/TiKV work. These are exercised by a real raw-TCP client against the actual Rust SQL node, not a mock trait implementation. Positive TCP acceptance requires prepare metadata for one parameter and one signed-BIGINT result; two executions with different values; and a second execution with `new_params_bound_flag=0` that uses the stored type vector and does not reuse the first value.

Live acceptance uses a pre-seeded 16-row signed-BIGINT table and one authenticated Rust TCP connection. Each successful execute must have the same connection/session identity, exactly one configured snapshot/real TiKV point-read receipt, exact binary row value, and no active/failed connection after close. The custom sysbench run must complete exactly eight prepared events on one thread with no client errors, zero text-query commands, one successful prepare, eight successful executes, one close, and accepted/completed event counts matching the server receipt. Standard sysbench setup and `oltp_read_only` remain explicitly unverified and unsupported.

## Idempotence and Recovery

Focused unit/TCP tests and live cleanup are repeatable. A failed packet test changes no server state. A failed live run must leave only tag-owned process cleanup; do not remove generic TiUP state. If the shared gate fails, release no C27 claim, repair the owning slice, run its focused regression, and rerun the whole immutable gate. Never interpolate parameters into SQL or retain an alternate text-row execute path as a compatibility fallback.
