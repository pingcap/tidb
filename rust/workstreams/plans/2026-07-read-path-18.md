# Integrate unlocked cache refresh with BatchCommands-first region requests

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current according to repository-root `PLANS.md`.

## Purpose / Big Picture

Campaign 18 removes the last artificial separation between the production region cache, retained BatchCommands transport, and DistSQL retry coordinator. A foreground read must continue selecting from the canonical cache while background PD store refresh is blocked. Its first TiKV attempt must use the real BatchCommands stream, while any region or transport failure continues through the same selector, cache observation, backoff budget, and synchronous fallback already used by the production read path. A tag-owned live topology must then prove previous-region boundaries, forwarding, restart, generation retirement, caller retry, and cleanup.

The campaign owns 12 exact pinned production sources and 50 exact original tests across four disjoint slices. Three code leaves are independently writable; the live proof is dependency-gated on their integration. Rust compilation is deliberately delayed until the leaves contain a substantial batch of work.

## Surprises & Discoveries

- Observation: foreground TiKV send, liveness probing, and guarded failure publication release the cache mutex, but foreground region cache misses and background `load_store` still perform PD I/O while holding it.
  Evidence: `direct_unary_query_transport.rs` sends at 825-852, but bind/retry call `RegionCache::locate_ranges` inside `with_region_cache`; lock resolution does the same with `locate_key`. `background.rs` also called `maintain_stores` while holding the cache guard.
- Observation: the current txnkv async state machine duplicates retry policy and a terminal completion even though `DirectUnaryQueryResponse` already owns both.
  Evidence: `region/async_request.rs` owns `AsyncRegionAttemptPolicy`, a retry phase, and an outer completion; the retained BatchCommands entry already has the sole in-flight completion and cancellation hook.
- Observation: TLS cannot be honestly exercised in this campaign's live proof.
  Evidence: PD rejects `https://`, TiKV builds plaintext `http://` endpoints, and `SecurityConfig` is metadata only.
- Observation: tonic awaited BatchCommands response headers before returning the send-capable stream, while live TiKV may await the first inbound request before publishing those headers.
  Evidence: the first live run timed out opening the stream with zero received requests; the focused regression failed before the generation-owned open task returned immediately and passed after first publication was allowed to race response headers.
- Observation: local opening-slot pressure is neither a connection failure nor a replica attempt.
  Evidence: classifying it as `Connection` poisoned route/liveness feedback, while consuming it without an exact selector rollback left `pending_attempt` installed and failed the synchronous fallback with `AttemptStillPending`.

## Context and Orientation

`rust/crates/tidb-txnkv/src/region/background.rs` owns the sole maintenance thread and canonical cache mutex. `region/cache.rs` owns store state and the metadata loader. `rpc/batch/transport.rs` owns the sole tonic duplex streams and in-flight table. `rpc/tonic_coprocessor.rs` owns the concrete TiKV client. `region/async_request.rs` currently models one asynchronous attempt but incorrectly also models retry policy. `rust/crates/tidb-distsql/src/cop_paging/direct_unary_query_transport.rs` owns the actual production selection and retry loop.

A refresh plan is an immutable snapshot of the store facts observed before PD I/O. Publication succeeds only if those facts are still current. A BatchCommands-first request means exactly one first physical attempt is placed on the retained stream; a failed request chain then becomes synchronous without sending the same opaque command twice.

## Plan of Work

The cache leaf separates loader ownership from cache-state ownership. Store refresh and foreground region lookup select immutable plans or cache hits under the cache mutex, perform PD fetches without that mutex, and conditionally merge results after complete revalidation. It adds blocking-loader regressions that prove concurrent cache access and stale-result rejection for both metadata paths. Production DistSQL and lock resolution call the stable `SharedReadRuntime` lookup APIs instead of invoking loader-bearing `RegionCache` methods under a generic cache closure.

The batch-dispatch leaf creates a Coprocessor-specific adapter over the existing opaque BatchCommands entry. It attaches the final request context, preserves the forwarding host, maps exactly one response or transport error, and lets the existing in-flight cancellation hook retire the route/request ID.

The pending adapter blocks on the existing completion run-loop signal. Canonical unary cancellation registers that same signal as a waiter, and the absolute call deadline bounds the condition-variable wait. This lets response, cancellation, or deadline wake the same driver without CPU polling, sleep slices, detached watcher threads, or a second terminal authority.
Pull-backed `CompletionRequest::invoke` and `schedule` both publish through that wakeable run-loop shape; standalone `CompletionCallback::invoke` retains immediate callback semantics. Thus a terminal result cannot exist behind a sleeping pull driver.

The DistSQL leaf reduces txnkv async state to one pending physical attempt, then makes `DirectUnaryQueryResponse` own pending polling and settlement. Success, region error, send failure, cancellation, and fallback must all reuse current response methods and state maps. The old parallel policy, retry phase, and outer completion are deleted.

After all code leaves integrate, the live leaf starts a unique TiUP v8.5.6 topology with three PD and three TiKV nodes. Rust discovers and splits a region, proves `GetPrevRegion` adjacency, opens direct and forwarded-host streams on the same physical proxy, restarts the exact owned logical follower target at the same address without triggering leader election, proves forwarded-generation failure without retiring the sibling direct route, and then proves explicit caller retry plus full process, registry, endpoint, and data cleanup.

## Validation and Acceptance

Acceptance requires blocking loaders to prove foreground cache progress while PD store or region fetch is paused. Concurrent topology mutation must make a stale result publish nothing; a current result must update the same canonical authority once without full-state replacement.

The concrete adapter must prove exact Coprocessor tag/body/context/forwarding, one completion, pull cancellation, late-response suppression, and terminal transport mapping. DistSQL must prove batch success avoids unary; batch region or send failure resumes the same synchronous selector/backoff/cache path; cancellation wins before feedback; and later independent request chains can use BatchCommands again.

The live proof must publish phase evidence for split adjacency, direct/forwarded stream isolation, restart generation change, exactly-once failure, explicit retry success, and cleanup. If same-address restart cannot be proven safely, the associated obligation remains `PARTIAL`; no mock is substituted.

All manifests, external source/test ledgers, transfers, the status dashboard, workspace Clippy/tests, queue tests, and `make -j12 lint` must pass before archive. Passing Campaign 18 does not claim TLS, router streaming, full BatchCommands command coverage, or whole-project parity.

## Idempotence and Recovery

Claims are local checked files and are released only with a current integration receipt. The live runner uses a unique TiUP tag and traps every owned child PID; rerunning must first prove that no endpoint or registry row remains. A stale refresh plan is safe to retry because it has no publish side effects. Batch requests are never automatically resent after ambiguous publication; only the caller-owned retry loop may create the next attempt.

## Interfaces and Dependencies

`StoreRefreshPlan` captures store ID, epoch, resolve state, address, and labels. Cache publication accepts the plan plus the loader result and returns applied, stale, removed, or failed accounting without owning retries.

`AsyncRequestDispatcher` begins one BatchCommands physical attempt and returns one `PendingRequest`. `TonicCoprocessorClient` implements it using the existing `BatchCommandEntry`, `OpaqueBatchCommand::Coprocessor`, completion run loop, stream, and in-flight cancellation. It has no synchronous retry method.

`DirectUnaryQueryResponse` owns whether one logical request chain is batch-first or synchronous-only, plus the existing selector, observation, backoff, and retry state. The live proof depends on all three code slices and does not edit their production files.
