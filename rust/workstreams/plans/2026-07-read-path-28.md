# Commit prepared INSERT and UPDATE through real TiKV 2PC

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as implementation proceeds.

Reference: `PLANS.md` at repository root. This plan follows `AGENTS.md`, `rust/PARALLEL.md`, `rust/docs/operations/validation.md`, and the source/test evidence rules in `rust/workstreams/slices/README.md`. It is the first real write vertical of the Rust rewrite, not a claim of complete TiDB DML or transaction parity.

## Purpose / Big Picture

Campaign 28 makes the standalone Rust SQL node persist data in the same TiKV cluster used by Go TiDB. After implementation, a stock MySQL client can prepare and execute a signed-`BIGINT` `INSERT` or point `UPDATE` against the Rust TCP endpoint. The Rust node obtains real start and commit timestamps from PD, sends real TiKV `Prewrite` and `Commit` commands through the existing region cache and transport, and returns an OK packet only after the transaction has a determinate committed result.

The observable proof crosses independent implementations. Go TiDB creates the schema and table in a real three-PD/three-TiKV playground. A client sends binary prepared DML to the Rust endpoint. A separate connection to the concurrently running Go TiDB endpoint reads the exact inserted and updated rows, then Go TiDB changes a row and the Rust prepared read sees that change. The Rust process is restarted and Go TiDB still sees the Rust writes. No in-memory `Database`, mock catalog, mock transaction, mock TiKV client, fake RPC server, or fixture-only interface can satisfy acceptance.

This campaign also opens a genuine multi-region normal two-phase commit, abbreviated 2PC. In normal 2PC, every mutation is first prewritten as an MVCC lock at `start_ts`; after all prewrites succeed, PD supplies a greater `commit_ts`; the primary key is committed before secondary keys. A two-row prepared insert is routed across two real regions so the proof cannot collapse into an in-process one-key success path.

## Surprises & Discoveries

- Observation: the checked BatchCommands envelope already reserves exact tags for `Get = 1`, `Prewrite = 3`, `Commit = 4`, and `BatchRollback = 8`, but only Coprocessor has a typed pending adapter.
  Evidence: `rust/crates/tidb-txnkv/src/rpc/batch/wire.rs` and `rust/crates/tidb-txnkv/src/rpc/batch/coprocessor.rs`.

- Observation: the checked `kvrpcpb.proto` projection intentionally omits mutation, prewrite, commit, rollback, and point-get messages.
  Evidence: `rust/crates/tidb-proto/proto/kvrpcpb.proto` contains `Context`, lock-status, and resolve-lock messages only, while the pinned module at `github.com/pingcap/kvproto` version `v0.0.0-20260622063236-b41e86365ce0` defines the required exact fields.

- Observation: the current mutable transaction driver is a source-shaped buffer adapter, not a concrete TiKV transaction.
  Evidence: `rust/crates/tidb-txnkv/src/driver/mem_buffer.rs` says a future TiKV adapter must supply the backend; `rust/crates/tidb-txnkv/src/lib.rs` explicitly states that MVCC write transactions and commit remain outside the implemented boundary.

- Observation: parser and broad in-memory DML execution already exist, but routing them to the in-memory `tidb_exec::Database` would not persist to TiKV and would violate the acceptance contract.
  Evidence: `rust/crates/tidb-ast/src/dml.rs`, `rust/crates/tidb-parser/src/dml.rs`, and `rust/crates/tidb-exec/src/dml.rs` model INSERT/UPDATE over `Database.tables`; the production node in `rust/crates/tidb-server/src/real_tikv_multi_node.rs` owns a separate real read path.

- Observation: the configured catalog already has the physical information needed for the first row writer: table ID, column IDs, one clustered signed handle, and stored non-null signed columns.
  Evidence: `ConfiguredColumn` and `ConfiguredTable` in `rust/crates/tidb-planner/src/read_only_scan.rs`, plus `encode_row_key`, `encode_raw_row`, `RowDecoder`, and `decode_raw_int` in `rust/crates/tidb-codec`.

- Observation: a one-key write would exercise real RPC but would not prove the transaction coordinator's primary/secondary ordering or multi-region regrouping.
  Evidence: normal 2PC in pinned client-go splits mutations by region and commits the primary batch first; C28 therefore includes a two-row insert whose row keys are verified to belong to different real regions.

- Observation: renaming `TonicCoprocessorClient` inside the bounded transport leaf would touch 68 existing references across 18 out-of-slice Rust files without changing the single transport authority.
  Evidence: Stage A retained the concrete client name, added typed transaction-command adapters above its sole `RawTransportClient`, and proved the same channel version and BatchCommands generation in every real receipt. The KV-wide authority/name migration remains steward-owned and must not be approximated with a second client or compatibility layer.

  Date/Author: 2026-07-20 / Codex.

- Decision: evolve the existing read process authority into one KV process authority and remove stale read-only authority names in the same integration increment.
  Rationale: one process must own exactly one PD worker, RegionCache maintenance worker, TiKV channel/BatchCommands authority, retry policy, and shutdown order for both reads and writes.   Date/Author: 2026-07-20 / Codex.

- Decision: execute transaction commands through the retained real TiKV transport, preferring BatchCommands and using the same route recovery machinery as reads.
  Rationale: the batch wire already owns the exact tags and physical publication identity. A new tonic client or direct socket path would split channel lifecycle, region invalidation, cancellation, and observability.
  Date/Author: 2026-07-20 / Codex.

- Decision: admit only a configured table with exactly one signed `BIGINT PRIMARY KEY CLUSTERED` and one or more signed `BIGINT NOT NULL` stored columns; C28's live fixture has `id` and `balance`.
  Rationale: this schema has an exact persisted key/value representation in the current codec and needs no index, NULL, default, collation, auto-ID, partition, or schema-change behavior. Unsupported shapes fail during prepared-plan lowering before PD or TiKV work.
  Date/Author: 2026-07-20 / Codex.

- Decision: support these prepared forms: one or more literal `VALUES` rows in `INSERT INTO db.t (id, balance) VALUES (?, ?)[, (?, ?)...]`; `UPDATE db.t SET balance = ? WHERE id = ?`; and `UPDATE db.t SET balance = balance + ? WHERE id = ?`.
  Rationale: one-row insert and point update are useful immediately, bounded multi-row insert proves real multi-region 2PC, and the arithmetic update is the signed-`BIGINT` equivalent of sysbench's indexed update. All markers are bound by position through C27; SQL interpolation remains forbidden.
  Date/Author: 2026-07-20 / Codex.

- Decision: make the transaction client accept a nonempty vector of typed mutations even though the first UPDATE produces one mutation.
  Rationale: region splitting, primary selection, cleanup, and secondary commit are transaction concerns. Hard-coding one key would make the multi-region proof impossible and create a throwaway API.
  Date/Author: 2026-07-20 / Codex.

- Decision: select the lexicographically smallest encoded mutation key as the transaction primary and sort/group all mutations deterministically before dispatch.
  Rationale: deterministic primary identity makes receipts, retry regrouping, and cleanup auditable without changing TiKV semantics. The SQL primary-key concept is unrelated to the 2PC primary lock and must not be conflated with it.
  Date/Author: 2026-07-20 / Codex.

- Decision: return a MySQL OK packet only for a determinate `Committed` outcome; before primary commit, failure or cancellation must roll back every possibly prewritten key or surface `CleanupFailed`. A published primary attempt is provisionally ambiguous until TiKV returns a decoded response: a lost/malformed response is `ResultUndetermined`, while a decoded rejecting `CommitResponse` is determinate and may enter cleanup exactly as pinned client-go does.
  Rationale: retrying an unknown primary outcome can duplicate an INSERT or apply an UPDATE twice. A failed secondary commit after confirmed primary success cannot turn the transaction into a reported rollback; the coordinator must finish secondaries or leave resolvable locks and report the committed outcome honestly.
  Date/Author: 2026-07-20 / Codex.

- Decision: pure protobuf/rowcodec vectors and commit-state transition tests are allowed, but no fake transport/database/catalog/session is acceptance evidence.
  Rationale: deterministic encoders need local boundary tests, while interoperability and persistence require the actual TCP, PD, RegionCache, TiKV, and Go TiDB path. The live receipt is mandatory and cannot be replaced by a trait double.
  Date/Author: 2026-07-20 / Codex.

- Decision: promote only exact C28-covered TiDB and pinned client-go anchors to `PARTIAL`; leave every unsupported branch and original test visible as `UNTRIAGED`, `BLOCKED`, or a documented remainder of `PARTIAL`.
  Rationale: `TestPreparedInsert`, `TestPreparedUpdate`, and client-go transaction files cover much more than this vertical. File adjacency or a passing subset is not full parity.
  Date/Author: 2026-07-20 / Codex.

## Context and Orientation

The current production read flow is:

    MySQL TCP packet
      -> `tidb_server::sql_node::ConcurrentSqlNode`
      -> one authenticated `QuerySession`
      -> configured parser/planner
      -> `ProductionReadProcessAuthority`
      -> one shared PD timestamp worker + RegionCache + TiKV BatchCommands transport
      -> real TiKV Coprocessor request
      -> MySQL result packets

C27 adds a per-connection prepared-statement registry. `COM_STMT_PREPARE` stores a validated template and returns parameter/result metadata. `COM_STMT_EXECUTE` decodes signed `MYSQL_TYPE_LONGLONG` values and reuses a previously supplied type vector when `new_params_bound_flag` is zero. `COM_STMT_CLOSE` removes only that connection's handle. C28 depends on those behaviors being receipt-released; it extends the template kinds and parameter count rather than adding a second prepared registry.

The current cluster capabilities are split across crates. `tidb-pd-client::PdClient::get_timestamp` owns real monotonic PD TSO allocation. `tidb_txnkv::SharedReadAuthority` owns one maintained RegionCache and cloneable TiKV client handle. `tidb_txnkv::rpc::TonicCoprocessorClient` owns the actual tonic worker and BatchCommands stream, despite its now-too-narrow name. `tidb_exec::real_tikv_read::ProductionReadProcessAuthority` composes their unique lifecycle owners. C28 renames these process-wide authorities to KV names and gives worker sessions one write capability over the same handles.

A TiKV transaction uses multi-version concurrency control, abbreviated MVCC. `start_ts` is the snapshot and identity of the transaction. A prewrite places locks and uncommitted values at that timestamp. `commit_ts` makes them visible and must be greater than `start_ts`. One encoded key is the 2PC primary; its committed or rolled-back state is the authority used to resolve secondary locks.

For the C28 table, the persisted record key is `encode_row_key(table_id, encode_int(id))`. The clustered primary key lives in that record key. Stored columns live in the new-row payload: each configured stored column ID and compact signed integer payload is passed to `encode_raw_row`. UPDATE reads the row at its own `start_ts` with a real TiKV `Get`, finds `balance` through `RowDecoder::column`, decodes it with `decode_raw_int`, performs checked signed arithmetic when requested, and encodes the replacement row. It must not read through a later snapshot or use the in-memory `Database`.

## Frozen C28 SQL and Storage Boundary

The live table is created by Go TiDB as:

    CREATE DATABASE IF NOT EXISTS campaign28;
    CREATE TABLE campaign28.accounts (
      id BIGINT PRIMARY KEY CLUSTERED,
      balance BIGINT NOT NULL
    );

The prepared templates admitted in C28 are:

    INSERT INTO campaign28.accounts (id, balance) VALUES (?, ?)
    INSERT INTO campaign28.accounts (id, balance) VALUES (?, ?), (?, ?)
    UPDATE campaign28.accounts SET balance = ? WHERE id = ?
    UPDATE campaign28.accounts SET balance = balance + ? WHERE id = ?

The implementation may accept any bounded positive number of INSERT rows if the same code naturally generalizes, but startup or prepare must impose a checked process limit and the live proof must exercise two rows across two regions. Parameter markers are positional signed non-NULL `MYSQL_TYPE_LONGLONG` values. Table/schema/column names are resolved through `ConfiguredCatalog`; exactly one clustered handle and the named stored column are required.

INSERT uses `kvrpcpb.Mutation` operation `Insert` and assertion `NotExist`, so TiKV—not a racy preliminary read—enforces duplicate-key absence at prewrite. UPDATE first performs snapshot `Get` at the transaction's `start_ts`. Missing row returns an OK packet with `affected_rows = 0` and sends no Prewrite/Commit. An unchanged replacement also returns zero affected rows under the default client capability. A changed row uses operation `Put` and assertion `Exist`; it returns `affected_rows = 1` only after determinate commit. Arithmetic overflow, missing/NULL stored data, malformed row bytes, unsupported schema shape, duplicate input keys, and marker-count/type errors fail before mutation publication.

C28 does not accept text-protocol DML, SQL `PREPARE`/`EXECUTE`, explicit `BEGIN`/`COMMIT`/`ROLLBACK`, autocommit-off sessions, DELETE/REPLACE/INSERT IGNORE/ON DUPLICATE KEY, INSERT SELECT, defaults, auto-increment, generated columns, NULL, unsigned values, strings, secondary/unique indexes, common handles, partitions, foreign keys, triggers, pessimistic transactions, savepoints, one-phase commit, async commit, pipelined DML, TTL keepalive, schema lease/MDL checks, statistics updates, binlog/changefeed semantics, or plan cache. Each stays rejected before storage work or remains a ledger gap.

## Frozen Transaction State Machine

The concrete transaction owner must retain one explicit monotonic state; no boolean combination may make “rolled back” and “committed” simultaneously possible:

    New
      -> Reading
      -> Prewriting
      -> Prewritten
      -> PrimaryCommitting
      -> PrimaryCommitted
      -> SecondariesCommitting
      -> Committed

Before primary success, an error or cancellation transitions through `RollingBack` to `RolledBack` only after every possibly prewritten key has received a successful real `BatchRollback` terminal outcome. If any cleanup remains unconfirmed, transition to `CleanupFailed`, publish the exact outstanding keys/routes, return no OK, and keep the process authority able to resolve those locks; never label that outcome rolled back. Once a primary Commit is published, rollback is forbidden only while that attempt could have succeeded and no definitive response exists. A decoded primary `CommitResponse` clears provisional ambiguity: success advances to `PrimaryCommitted`; a decoded `CommitTsExpired` may retry with a validated newer real PD timestamp; any other decoded rejecting key/protocol error is determinate and permits cleanup. A lost, malformed, cancelled, explicitly undetermined, or transport-failed response after publication transitions to `Undetermined`, closes the MySQL connection, publishes the exact physical route/request identity, and never emits OK or auto-retries the SQL statement.

A successful primary response makes the transaction committed even if a later secondary RPC fails. Secondary batches are attempted synchronously and retried/regrouped against RegionCache in C28. Exhausting that bound yields a determinate `Committed` outcome whose receipt lists unresolved secondary keys; it must never become rollback or undetermined. The live acceptance run requires the stronger happy-path result—every secondary receives a successful commit response before OK—while the production state model stays truthful for the failure case.

All prewrite batches use one `start_ts`, one deterministic primary key, one lock TTL calculated from pinned client-go's bounded formula (3,000 ms for less than the commit-batch threshold, plus elapsed transaction-read milliseconds), `txn_size` equal to the transaction mutation count, assertion level `Strict`, `try_one_pc = false`, `use_async_commit = false`, and the existing TiDB request source/origin context. After every prewrite succeeds, acquire a fresh PD timestamp and require `commit_ts > start_ts`. Commit the primary-containing batch first with `CommitRole::Primary`, then commit all remaining batches with `CommitRole::Secondary`. The successful live proof requires all secondaries complete before OK so the independent reader observes every row without first resolving a lock.

Region errors never change transaction identity. Update the canonical RegionCache through its one typed recovery/backoff authority, relocate the original immutable mutation set, regroup it, and retry within one checked deadline. A locked prewrite delegates to the existing real lock resolver and retries with the same `start_ts` after resolution. A write conflict or duplicate key maps to the existing TiDB/MySQL error family; an autocommit write-conflict retry, if enabled in C28, restarts the complete SQL transaction with a fresh start timestamp and a bounded retry count. It must never restart the full SQL transaction after a primary Commit was published; the only same-transaction primary retry admitted here is the exact decoded `CommitTsExpired` path with a validated newer timestamp.

## Validation and Acceptance

Protocol acceptance requires exact protobuf round trips for every admitted request/response, exact BatchCommands tags, context injection without field loss, command-tag mismatch rejection, truncated/unknown error rejection, and cancellation/deadline propagation. A generated prost type and a passing encode/decode test are necessary but not sufficient; the typed command must receive a real TiKV response through the retained physical channel.

Transaction acceptance requires all of the following on real PD/TiKV:

- `start_ts > 0`, `commit_ts > start_ts`, and both come from the shared PD worker.
- A two-row insert maps to at least two real region IDs, prewrites every batch with one start timestamp, commits the primary region first, then commits every secondary before OK.
- `try_one_pc` and `use_async_commit` are false in observed requests.
- A duplicate-key failure after at least one successful prewrite produces no OK, rolls back the successful prewrite, and leaves no lock or hidden value. Go TiDB can immediately insert and read that key.
- A real lock conflict either resolves and retries within the bound or returns the exact retryable error; it never commits from a different snapshot accidentally.
- Leader/topology change between attempts preserves the same transaction identity, republishes the refreshed route, and never sends a stale successful receipt.
- Caller cancellation before primary publication produces rollback/no residual lock. Cancellation or transport ambiguity at primary publication never reports success or retries the SQL statement.
- Shutdown drains or cancels active statements, resolves pre-primary cleanup, closes session admission, then stops RegionCache, TiKV transport, and PD in dependency order.

Prepared SQL acceptance uses one persistent Rust MySQL connection and at least these executions:

1. Prepare one-row INSERT; execute `(10, 100)` with a new type vector, then `(11, 110)` reusing types. Expect `affected_rows = 1` each.
2. Prepare the two-row INSERT; choose keys on distinct real regions and execute both. Expect one transaction receipt with two region batches and `affected_rows = 2`.
3. Execute the same INSERT for an existing key. Expect duplicate-key error and no additional row or leaked lock.
4. Prepare direct UPDATE; set key `10` to `150`. Expect `affected_rows = 1`; repeat with `150` and expect zero.
5. Prepare arithmetic UPDATE; add `7` to key `10`. Expect `157`. Execute for a missing key and expect zero with no Prewrite/Commit publication.
6. Execute arithmetic overflow at `i64::MAX`. Expect an error before Prewrite.
7. Execute with NULL, unsigned, wrong marker count, unknown statement ID, cross-connection handle, closed handle, unsupported DML shape, and malformed packet. Expect typed errors and no storage publication.
8. Use the C27 prepared read on the same connection to observe committed values; this read still traverses real PD/TiKV and returns binary rows.

Independent persistence acceptance is stricter than reading back through Rust:

- Go TiDB creates and seeds the table before Rust starts; the live receipt records its table and column IDs.
- After Rust DML, a separate stock client connected to the Go TiDB port executes exact `SELECT id, balance FROM campaign28.accounts ORDER BY id` and receives every expected row.
- Go TiDB changes one balance, and Rust's C27 prepared read returns the Go value.
- Stop and restart the Rust node without reseeding or rewriting expected data. Go TiDB still returns the Rust-committed rows, and Rust reads them after reconnect.
- The script records distinct Go and Rust listener ports/PIDs, plus real PD cluster ID and TiKV region/store IDs, so a single in-memory process cannot masquerade as both sides.

The C28 live receipt must contain the prepared statement and execution identities, connection/session/authority IDs, SQL shape digest, affected rows, table/column IDs, encoded-key digests rather than raw sensitive keys, start/commit timestamps, mutation count, primary digest, region batches, Prewrite/Commit/BatchRollback command tags and request IDs, physical address/channel/generation, retry/regroup history, terminal state, Go verification rows, Rust-restart PID change, and cleanup result.
