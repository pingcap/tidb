# Port Adaptive LIMIT Scan Admission Control to Rust

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current as work proceeds.

Reference: repository-root `PLANS.md`; this plan follows its self-contained, milestone-based format.

## Purpose / Big Picture

TiDB master has an opt-in adaptive admission controller for ordered `LIMIT` queries over two plan shapes: an ordered index lookup join whose outer side is an ordered index lookup, and a direct ordered index lookup. After this work, Rust must accept the same session variable, preserve its default and upgrade behavior, limit speculative outer rows and lookup handles with the same feedback rules, stop and reset at the same lifecycle boundaries, and expose the same execution diagnostics. SQL rows, order, transaction semantics, and plan selection must remain unchanged. With the setting disabled or a plan ineligible, execution must retain the current Rust path.

The package completion unit is all of Go `pkg/executor/internal/exec`, not only the new controller file. Its executor and index-usage portions already have Rust owners; this change must re-audit and retain those mappings while porting every new package artifact and every required builder, executor, system-variable, upgrade, test, support, build, and benchmark integration. No adaptive feature or package-parity claim is complete until the whole inventory and acceptance gates below pass.

## Surprises & Discoveries

- The checked-out Rust worktree is branch `hparser-integration` at `46370bc7f4`; it does not contain the controller addition from current TiDB master. The implementation uses read-only `git show origin/master:<path>` for the Go oracle and preserves the two pre-existing untracked Rust files `rust/crates/tidb-expr/src/vs_helper.rs` and `rust/crates/tidb-planner/src/fragment.rs`.
- The effective default has three parts: Go's compiled/session default and sysvar catalog value are OFF; `GlobalSystemVariableInitialValue` persists ON for fresh installs; `upgradeToVer287` inserts OFF for an upgraded cluster only when the variable is absent. The current test suite checks all three behaviors (`TestAdaptiveLimitExecution`, `TestGlobalSystemVariableInitialValue`, and `TestAdaptiveLimitScanClusterDefaults`). Rust must reproduce that split exactly.
- Rust's direct physical index lookup is built as `IndexRangeSourceExec`; index-join lookup is represented by `JoinExec` plus `IndexJoinLookupExec`. They do not mirror Go's `IndexLookUpExecutor` tree one-for-one, so admission must be mapped to those native lifecycle owners without broadening eligibility.
- Rust's local `Session::run` index scan exposes no coprocessor runtime counters (`cop_count_and_rows` is `(0, 0)`); it cannot reproduce Go's mock-store reporter SQL test. A `CopIndexUsageExec` test now injects the authoritative scan totals and verifies close-path publication and bucketing. Keep the real coprocessor-backed SQL case open until an appropriate test transport can supply those counts.
- Go builds OR and AND IndexMerge candidates from its session-filtered `PossibleAccessPaths`; normal-index AND partials also use only the path's TiKV-pushable access conditions and require explicit names. Rust now applies those boundaries through `DataSource::enumerated_paths` and `pushed_down_conds`, so invisible, ignored, unavailable indexes and non-pushable predicates cannot enter partial scans. Go also refuses IndexMerge on LOCAL temporary tables while allowing the separate GLOBAL case; Rust now carries the local/global distinction through source catalog and DataSource planning.
- The Go `TestAdaptiveLimitEligibility` distinguishes flat multiple ranges from grouped ranges. Rust's `PhysicalIndexLookUpReader`/`PhysicalIndexScan` have no `byItems`, `groupedRanges`, or `GroupByColIdxs`; `IndexRangeSourceExec` has one flat `ranges` vector and advances it sequentially. Those grouped shapes are therefore not expressible in this Rust candidate today. If the planner/executor later gains grouped range reads, it must preserve the same Go eligibility veto before attaching a controller.
- `origin/master` registers upgrade version 287, while Rust's `CURRENT_BOOTSTRAP_VERSION` is 263. Rust's `tidb-server::bootstrap` documents `BootstrapPhase::RunStartMode` as an ordering marker, not an executable upgrade dispatcher, and current `upgrade_versions` stores only names/versions. The adaptive upgrade's persisted OFF behavior therefore depends on broader versioned-bootstrap parity; adding a feature-local helper without a caller would not fix upgraded clusters.
- The current master uses version 287 for two independent upgrades that landed separately: adaptive-limit GLOBAL OFF materialization and the TTL task's `scan_index_id` column. The safe Rust migration scope therefore includes the current combined version-287 effects plus every registered Go migration from 277–286 that can run after Rust's current version 263. A single-variable backfill or a version-number-only bump would silently skip other schema/data migrations.

## Idempotence and Recovery

The controller is statement-local and resettable; its immutable bounds survive reset while counters, feedback, wait stats, windows, and stop channels return to their initial state. A failed or cancelled execution must release reservations or stop the controller before its executor tree is discarded. If a test fails after partial integration, first disable the sysvar in the test fixture and retain the legacy path while fixing the failure; do not silently loosen eligibility or alter SQL output. Rust formatting and focused tests are safe to rerun. Do not delete or rewrite the two pre-existing untracked files.
