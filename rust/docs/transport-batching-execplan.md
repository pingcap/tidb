# Coalesce pending transport submissions


This living ExecPlan follows root `PLANS.md`.

## Purpose / Big Picture


Improve concurrent SQL reads and transactional RPCs by sending pending TiKV commands together, without query-specific shortcuts. TiKV BatchCommands is a streaming RPC whose messages can contain many independent commands. The original worker flushed each caller's vector immediately, and normal callers supplied one command. Initial live read-only measurements showed 1.00 commands/message for Rust versus 5.56 for Go at 32 clients. Shared admission now drains ready callers before selecting a connection. Success requires correct per-caller results and lifecycle behavior plus an unprofiled measured improvement, not just larger messages.

## Context and Orientation


`rust/crates/tidb-txnkv/src/rpc/transport_runtime.rs` owns the shared command queue and connection states. `WorkerCommand::BatchSubmit` carries one caller's entries, absolute deadline/cancellation context, and a reply channel for publication identity. A publication receipt identifies the physical connection, forwarding target, stream generation and request IDs; it is not the eventual RPC result. Each connection's `rpc/batch/transport.rs` state owns grouping, streams and in-flight completion. `rpc/batch/scheduler.rs` owns priority/cancellation filtering and Go's adaptive batch trigger; request IDs and address-local physical channel versions are allocated across the owner.

The pinned Go module is `github.com/tikv/client-go/v2@v2.0.8-0.20260724023932-61ecd7c11416`. Its `internal/client/conn_batch.go` drains a shared queue before selecting a connection. The standard policy may adaptively collect for 100 microseconds; `max-batch-wait-time=0` only disables a separate overload wait. The old Rust implementation had four separate admission shards. The current implementation collects at one owner before rotating through four connections; measurement must determine whether that ownership change improves workloads.

## Plan of Work and Milestones


The current ownership milestone replaces clone-pinned admission shards with one command queue. It retains multiple independently reusable connection states and chooses one only after collecting a batch. The current probe gives each connection a single-worker I/O runtime; an earlier probe used one shared runtime. Share address-local channel-version allocation and request-ID allocation across those connection states; a retirement event is dispatched only to the connection whose exact physical identity matches. Preserve per-address round-robin selection, caller-local close, owner-wide cancellation/join, and address-wide versus exact-version invalidation. Expose an explicit nonzero connection-count constructor for deterministic single-connection lifecycle tests and use the normal four-connection default in new rotation/retirement tests. Replace the obsolete shard-count knob with `TIKV_GRPC_CONNECTION_COUNT`; do not maintain a second admission architecture.

First extend the transport worker's unit tests with fully queued commands before the worker starts. Observe each command's existing batch progress state, making the test independent of thread timing or a new test-only production hook. Add controls for a lifecycle barrier and canceled/expired siblings. Reuse the existing streaming fake in `tests/batch_tonic_stream_source.rs` for wire-size and receipt/result checks.

Next gather compatible adjacent submissions at the retained worker, stopping at lifecycle commands or a different physical address so connection-close ordering cannot change. Admit every caller independently, then group their surviving entries at the existing transport owner. Keep per-caller receipts restricted to that caller's actual published IDs. Bound wire packets to the source default of 128 commands, including explicitly supplied larger vectors. Start with immediate queue draining; add the existing adaptive policy only if measurements show it is needed, and then test sparse traffic and deadlines. Do not add workload switches or an unconditional sleep.

Finally rebuild with 12 jobs and start one candidate endpoint without replacing or stopping the approved baseline servers. Run alternating read-only sysbench trials and compare batch counters, result aggregates, TPS, SQL/TiKV CPU and errors. A successful batch-size assertion does not establish a performance win. Persistent TPC-C writes need separate user authority.

## Surprises & Discoveries


Go's adaptive policy has its own collection timer despite zero overload wait. Rust's scheduler already implemented that policy but production dispatch did not call it. The prior worker-reuse regression disappeared after restart; that older environment is not a valid baseline for this batching increment.

Immediate draining raised request batch size to approximately 1.5–1.6 but median TPS changed -0.84%, -0.22% and -0.12% at 1/8/32 clients. The adaptive probe reached 1.87 commands/message at 32 clients, with TPS -0.80%; its lower-concurrency medians were essentially flat. These are not accepted throughput wins.

The same adaptive binary with the existing `TIKV_TRANSPORT_SHARDS=1` option raised 32-client median batch size from 1.7632 to 9.7707, TPS from 2625.74 to 2710.77 (+3.24%), SQL CPU/transaction from 2.70875 to 2.34667 ms, and TiKV CPU/transaction from 2.31958 to 2.05875 ms. All three paired throughput deltas were positive. This isolates a combined queue/runtime/connection ownership effect, not queue count alone. The eight-client one-shard warmup was slower, so changing the default is not justified. Historical Go batch sizes were measured in another window and are not a contemporaneous speed ranking.

Source review found that Go returns immediately when its collection timer expires. The timed adaptive probe yielded once afterward; the latest source removes that extra yield and only does the additional yield/drain after reaching the target. The saved probe binary and its results remain distinct from the latest source.
