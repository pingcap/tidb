# Align the Rust node's structure with Go TiDB, in dependency order

This ExecPlan is a living document. Keep Progress, Surprises and discoveries, Decision log and Outcomes current at every stopping point.

## Purpose and outcome

The Rust node is meant to answer every statement the way Go TiDB (the "oracle", run from a scratch worktree of this branch) does. For a long stretch the work fixed one wrong answer at a time. Each fix was real, but most of them were emulations of a structural difference: Rust decides something at a different time, in a different place, or twice, where Go decides it once. Emulations pile up and then have to be deleted when the structure is corrected. The user directive of 2026-10-17 is to correct the structure first, in dependency order, accepting temporary regressions, and to stop adding emulations for anything a structural item covers.

After this plan: the replay harness cannot hide a regression, privileges are decided from the plan the way Go decides them, a view body is built by one code path, and the statement paths that exist twice (in-process session and cluster node) share one definition per statement kind. Observe it through the replay (`cargo test -p difftest-result-tests --test integration_diff integrationtest_replay_matches_recorded_tidb_output`), the cluster replay (`INTEGRATION_TOPIC=... cargo test -p tidb-server --lib corpus_unistore -- --ignored`) and the Go oracle probes (`difftool.sh` in the session scratchpad).

## Context for a reader new to the repository

`rust/crates/tidb-session` holds `Session`, the statement dispatcher (`dispatch.rs`), privilege collection (`table_privilege.rs`, `identity.rs`) and the in-process DDL entry points. `rust/crates/tidb-executor` holds the volcano executors, the in-memory `Catalog` (`driver/catalog.rs`), the DML drivers and the in-process DDL (`ddl/`). `rust/crates/tidb-exec` holds the cluster tier: `cluster_ddl.rs` plans DDL against the durable meta key-value store, and `table_info_build.rs` builds `TableInfo` the way Go's `ddl` package does. `rust/crates/tidb-planner` is the port of Go's logical planner (`plan_builder*.rs`). `rust/crates/tidb-server/src/cluster_session_node` is the production session: it wraps `tidb_session::Session` and routes DDL and writes to the cluster tier. A "visit info" is Go's list of (database, table, privilege) entries that the plan builder appends while planning and that `CheckPrivilege` verifies after planning. The "replay" runs the recorded TiDB integration tests (`tests/integrationtest/t/**` with results in `r/**`) through Rust and compares.

## The structural mismatches, with their symptoms and risks

First, the replay harness skipped statements both engines rejected without comparing the error code, and skipped statements Rust refused but Go answered (`OutOfDomain`) without any budget. Both hid real divergences (about 150 wrong codes; a jump from 5 to 61 out-of-domain statements went unreported). Risk of fixing: low; it only makes red what was already wrong.

Second, privileges are collected from the syntax before planning (`table_privilege.rs`), while Go collects visit info during planning and verifies afterwards. Symptoms already patched by emulation: view definer security (1356), a CTE named as an UPDATE target (1046 instead of 1288). Risk: every statement kind needs its visit info appended in Go's order, and the planner builds only SELECT plans, so write statements need their own hook.

Third, a view body is processed by two things: `view.rs` canonicalises it against the catalog, and the planner expands it later. Symptoms: the replaced-view name had to be hidden by catalog surgery before the planner got a renaming-view field. Risk: SHOW CREATE VIEW text and stored bodies must not change.

Fourth, the in-process executor DDL (`tidb-executor/src/ddl`, about 23,000 lines) and the cluster DDL (`tidb-exec`: `cluster_ddl.rs` and `cluster_ddl/`, about 25,000 lines as of 2026-10-19) each implement statement semantics, and the cluster node calls into both. Since Batch 10 every cluster schema change Go runs as a job is a persisted job in `mysql.tidb_ddl_job`, stepped by the owner as Go's `ddl` worker does; the in-process tier still runs its own one-step implementation. Symptoms: nearly every DDL error-code fix had to be made twice. Risk: highest of all; it is the largest surface and the in-process tier is what most unit tests run on.

Fifth, execution details are incomplete: commit and write details are blocked on the native committer, DML source reads bypass the coprocessor, EXPLAIN ANALYZE runtime info is missing, and Go's grouped-range ordered scans (`PropMatchedNeedMergeSort`) are unported.

Sixth (rewritten 2026-10-18; the "three logical trees" item is stale): the planner now has one logical tree (`tidb_planner::logical::LogicalPlan`; join enumeration and stats derivation run on it, and `find_best_task::LogicalJoin` is a per-call view). The real planner gap is that statistics set-up runs in the executor: `planner_bridge.rs`'s InitStats pass decides which statistics to load from the AST's WHERE (so a predicate in a derived table or one added by propagation loads none), recomputes index ranges and fills `derived_index_paths[..].row_estimate` with the executor's own `GetRowCountByIndexRanges` (`access_cost.rs`), a second port beside the planner's `cardinality/selectivity.rs`, over a third statistics shape. Go does this in `initStats`/`fillIndexPath`/`deriveIndexPathStats`. Non-SELECT statements have no `PlanBuilder.Build`: DML values, ON DUPLICATE and SET assignments, `TryFastPlan`, partition pruning (behind a trait the executor implements) and most EXPLAIN operator text live in the executor; SHOW WHERE and SET literals use a second, AST-walking evaluator (`tidb_expr::eval_in`).

### The review of 2026-10-18

Five read-only reviewers compared each layer with its Go owner. Their findings, by layer, most dangerous first within each:

Transactions (Go `session` + `sessiontxn`). Production runs two transaction objects at once: the session's `Transaction` (which copies the whole catalog at BEGIN and still runs the in-process rebase/`NotRebasable` commit rule) and the node's `explicit` store transaction, kept in step only by call order. Reading suggests a session commit that fails returns before `explicit` is discarded, so a later statement's `commit_if_session_left_transaction` could publish a COMMIT reported as failed (to verify). There is no isolation-provider seam: the cluster read snapshot ignores READ-COMMITTED (`record_set.rs` `open_read_snapshot` reads at `start_ts`); pessimistic DML first reads at `start_ts` rather than for-update ts; `handlePessimisticDML`, the retry loop, savepoints, implicit commit and the `autocommit=0` lazy opener are each implemented twice; `COMMIT AND CHAIN`/`ROLLBACK RELEASE` fail only on the cluster (1105; Go ignores the completion type); a refused `BEGIN READ ONLY` still commits the open transaction on the cluster; `tidb_disable_txn_auto_retry=OFF` retries are refused on the cluster. Target: one TxnManager in `tidb-session` over a store-transaction trait, the in-process catalog one backend of it; stale read (session-owned, node-injected provider) is the precedent.

Caches (Go `domain`). `SharedCatalog::store` is unserialized, so a slow reloader can publish an older schema version over a newer one (Go's `InfoCache` is max-version under `s.m`). The session catalog loader drops non-public indexes, non-public tables and partition reorg definitions, so a Rust node's DML during a Go owner's ADD INDEX writes no entries for the write-only index (Go's `TableFromMeta` keeps every non-`StateNone` index). LFU eviction updates `StatsCacheImpl` but readers read `published`, so evictions never reach the planner; `publish_temporary_table_stats` is a clone-insert-store lost-update race. `PrivilegeRegistry::replace_from` swaps nine maps one by one (a reader can see half a reload); FLUSH PRIVILEGES does not notify peers. `tidb_domain::sysvar_cache` is a complete port with no caller; the in-process tier never reloads `mysql.global_variables`. Some information_schema providers read the latest catalog instead of the statement's pinned one.

Execution and storage. (Fixed since the review: partition DDL replays over the table `TableFromMeta` builds, indexes, defaults and generated columns included, and runs as persisted jobs (Batches 9a/9b); MODIFY COLUMN rows are rewritten by the owner in checkpointed batches (`AddIndexReorgWork::UpdateColumn`, Batches 6-7); ADD INDEX and the region listings in Batch 4; the `mysql.*` row-id reservations run in their own transactions (Batch 3).) `system_row_write.rs` is still a third row writer. Cop selection is lowered through a second, bounded predicate IR and silently drops conjuncts it cannot express. `real_tikv_dml.rs` is a non-deployed DML path that tests still exercise (no `sql_mode`).

Session versus server duplicates still open after the batch below: LOCK STATS partition resolution and ANALYZE target resolution still live in `tidb-exec` (now with Go's name matching and 1505, but written twice); `prepare_general` runs statement routing at PREPARE, so DDL-lowering and flush warnings appear at COM_STMT_PREPARE; slow-log recording and TRACE are written twice.

Bootstrap layout (found 2026-10-18 while porting region pre-splits). Under the classic kernel, which the oracle and the integration server run, Go's bootstrap allocates every `mysql.*` table an ordinary global id through a DDL job (object id then job id: `mysql` is 1, `sys` 2 with job 3, `user` 4/5 ... `tidb_masking_policy` 108/109, the two views 110 and 112, `test` 114, the resource-group job 116), so user tables start at 117; only the seven DDL tables use reserved ids, and the 58 bootstrap jobs are in DDL history. Rust's bootstrap (`tidb-exec` `mysql_bootstrap`, `tidb-metadef` `BOOTSTRAP_TABLES`) follows the next-gen layout: every system table at a reserved id, user tables from 4, five materialized-view tables Go's bootstrap on this branch does not create (`tidb_mview_*`, `tidb_mlog_*`), and no bootstrap job history. Ids leak into `tidb_table_id`, region keys and `ADMIN SHOW DDL JOBS`. The fix must keep next-gen's layout for a next-gen kernel and remove the fixed-id dependencies first (`advisory_lock_key` encodes `ADVISORY_LOCKS_TABLE_ID`; the system database is read by its fixed id).

Order of work implied (as reviewed on 2026-10-18; since then the DDL job model took precedence, Batches 5-10, and the GC worker follows it, see `gcworker-execplan.md`): finish the statement-route seams (statistics done; transactions next, which needs the TxnManager), then the domain caches (catalog version ordering and the lossy loader are correctness hazards on a shared cluster and should be fixed as soon as found, ahead of order), then Milestone 3b-3e, then planner statistics set-up (Milestone 5, re-scoped from "three trees" to InitStats).

## Plan of work

Milestone 0 makes regressions visible. The replay compares error codes by default, keeps an exact list of recordings known to be stale (each confirmed against the oracle), and asserts an `OutOfDomain` budget that may only go down. Do this before touching any structure so that every later change is judged by a stricter instrument.

Milestone 1 scouts and then moves privilege decisions to plan time for reads. First read how Go appends visit info in `buildDataSource`, `BuildDataSourceFromView`, `buildInsert`, `buildUpdate` and `buildDelete`, and list every Rust site that builds a plan. Then give `PlanBuilder` a visit-info list, append in Go's order for SELECT, subqueries and views (definer clearing included), verify after planning, and delete the definer emulation in `identity.rs` and the CTE ordering patch in `planner_bridge.rs`. Writes follow in the same milestone only if the driver can append in Go's order; otherwise the milestone ends with writes documented and scheduled.

Milestone 2 makes a view body one code path. Compare `view.rs` canonicalisation with what the planner already produces, move the remaining logic into the planner, and delete the catalog-surgery fallbacks. SHOW CREATE VIEW output is the acceptance test and must stay byte-identical.

Milestone 3 scouts the DDL duplication before committing to a design. Inventory which statement kinds the cluster node already routes through `cluster_ddl.rs` only, which it validates in-process first, and which only run in-process. The decision to be recorded afterwards is whether the in-process tier becomes a thin front over the cluster definitions or the shared definitions move into one crate; choose the smaller reversible step, and migrate one statement kind at a time with a gate per kind.

Milestone 4 completes execution details: DML reads through the coprocessor, EXPLAIN ANALYZE runtime info, grouped-range ordered scans. Commit details wait on the native committer.

Milestone 5 was the planner's three trees; the planner now has one logical tree (see the sixth mismatch), so it is re-scoped to statistics set-up: move InitStats, index-path statistics and row estimates from the executor's `planner_bridge.rs` / `access_cost.rs` into the planner as Go's `initStats` / `fillIndexPath` / `deriveIndexPathStats`, starting with a prototype on one access path.

## Validation and acceptance

Every milestone ends with the same gate: the main-crate nextest run, the in-process replay, and the extra-crate nextest run, followed by the locked `tidb-server` build. A milestone is accepted when the replay reports no divergence outside the stale list, the `OutOfDomain` budget has not grown, and the new behavior is pinned by a test that fails before the change. Report the compared-statement count too: a drop in it means statements moved into a skipped class.

## Idempotence and recovery

Each milestone lands as its own commit through the pre-commit hook, so any one can be reverted alone. A structural change that makes the replay worse is reverted only if the worsening cannot be explained as emulation code that the change makes redundant.

## Surprises and discoveries

The first replay with the harness change reported 56 fewer compared statements than the run before it. The cause was a new view-definer check that did not match the definer's host pattern (`root`@`localhost` against the stored `root`@`%`), so views created by that definer became unreadable and their statements fell into `OutOfDomain`. Only the compared-count drop and the skip-class totals showed it, which is why the budget assertion exists.

The visit-info pass plans a statement a second time, which is not free of effects. Three had to be neutralised: planning raises warnings (truncated afterwards), constant folding evaluates builtins (`RELEASE_ALL_LOCKS()` ran twice; folding is suspended on the thread for the pass, null-flag derivation included), and an uncorrelated subquery is run at plan time (the pass answers with a row of NULLs instead, because the catalog it plans against is not the statement's execution image, whose virtual tables are materialised per statement). A pass that fails for any reason contributes no visits and the statement's own planning raises the error, which also keeps Go's observable `get_lock(..), no_such_fn()` folding order. Double planning is the temporary price of Milestone 1a; the plan's end state plans once and checks after planning.

Milestone 3 scouting (2026-10-17; updated 2026-10-19: since Batch 10 the lowered statement is submitted as a persisted job, `prepare_persisted_job_submission`, and stepped by `plan_persisted_ddl_job_step`; `plan_ddl` answers only the statements Go finishes without a job). The production session (`tidb-server`'s `cluster_session_node`) routes a schema change as `schema_route_for_change` -> `StatementRoute::Ddl(DdlStatement)`: the statement is lowered by `cluster_ddl::lower_ddl_with_context` (about 70 `DdlStatement` variants) and planned against a `MetaSnapshot` of the durable meta key-value store; the in-process executor DDL (32 files, about 23,000 lines under `tidb-executor/src/ddl`, 15 `run_*_in` entry points) is reached by a bare `Session::new()` only, plus the validation helpers the cluster tier calls into. So there are two implementations of statement semantics, and the in-process replay checks one while the cluster replay checks the other. `MetaSnapshot` has no general in-memory implementation: the existing ones are test-local or real-TiKV, and the catalog is rebuilt from meta by the cluster loader (`cluster_catalog_loader`, `table_from_meta`). The end state is therefore: a `Session` without a cluster owns an in-memory meta store, lowers and plans DDL exactly as production does, applies the plan's writes, reloads the catalog, and the executor DDL semantics are deleted once their shared helpers have moved. One fact changes the shape of that prototype: the in-process `Catalog` also OWNS the table rows (`KvTable` keeps them in memory), while the cluster tier keeps rows in the store and rebuilds the catalog from meta. A plan-apply-reload cycle over an in-memory meta store would therefore drop every table's data on reload, so unifying the DDL implementations is the same project as making a bare `Session` a cluster-lite over an in-process unistore (what `cop_backed_stack` in `tidb-server`'s tests already boots), which in turn means moving the roughly 2,800 `tidb-session` tests, which assume the in-memory tier, onto it. The alternative that avoids that move is to keep two tiers and extract each statement kind's semantics into functions both call, so only the lowering and the storage differ; it removes the duplicated decisions without removing a tier. The choice between the two is recorded as open in the Decision log until it is made. Prototype 3a, for the first option, proves it on the smallest statement kinds (CREATE / DROP VIEW and DROP TABLE) behind the session's DDL entry: an in-memory `MetaSnapshot`, a plan-apply-reload cycle, and `tests_views` plus the in-process replay unchanged. Only if 3a holds is the per-kind migration scheduled, one kind per gate.

## Decision log

Decided 2026-10-17 by the owner ("follow Go version implementation"): Milestone 3 takes the first option. Go has exactly one DDL implementation, the `ddl` package, whose executor builds a job and whose worker applies it to meta and the store, and every session, including a unit test's, runs on a store (`testkit.CreateMockStore` boots a mock unistore, bootstraps it and creates a domain). The Rust target is the same shape: one DDL implementation (the cluster tier), reached by every session through one seam, over a store that a bare `Session` also owns.

Milestone 3a seam design (2026-10-18, from reading both entry points). A seam already exists on the cluster side: `tidb-server`'s `cluster_session_node::ddl::ClusterDdl` (`execute(&DdlStatement, &StmtContext) -> ClusterDdlReport`, plus `is_owner`), held as `Arc<dyn ClusterDdl>` and called from `run_ddl`. What differs between the tiers is the orchestration around it. Both run the same prefix (`validate_snapshot_statement`, privilege check or `validate_ddl_preprocess`, implicit commit, local-temporary handling) and then diverge: `run_ddl` lowers the statement (`prepare_cluster_ddl_parsed` -> `DdlStatement`), checks `validate_cached_table_ddl` and `validate_persistent_ddl_references`, opens a table-lock job, calls `ddl.execute`, drains plan warnings, and finishes the lock job, while `Session::apply_schema_stmt` (`tidb-session/src/dispatch.rs`) has about 35 `DdlStmt::` arms that call `tidb_executor::run_*_in` on the shared `Catalog`. The step is: (1) move the trait to `tidb-session`, error type `DriverError` (the server converts at its boundary), so the session owns the one orchestration, `Session::run_schema_statement`, whose middle is `self.ddl.execute(..)`; (2) the cluster tier supplies `RealClusterDdl` unchanged; (3) the in-process tier supplies `CatalogDdl`, which wraps the current arms behind the same trait method, so the branch on cluster versus bare moves from every call site to one constructor; (4) only then does a statement kind move from `CatalogDdl` to the plan-apply-reload path (3d), starting with the kinds that own no rows (CREATE and DROP VIEW, sequences, placement policies, resource groups), because a reload of the in-process catalog from meta drops row storage until 3c lands. The first commit of 3a changes no behaviour: it moves the orchestration and proves it with the existing `tests_views` and `tests_core` suites plus the cluster `run_ddl` tests unchanged.

Decided 2026-10-18 (owner: "you make the call"): Milestone 3 continues before Milestone 4, and it starts by measuring the production engine. The gate's corpus replay (`integration_diff.rs`, the plan-text budget) drives the in-process engine, which production does not run; the production replay (`corpus_unistore.rs`, `one-engine-corpus-execplan.md`) was last run on 2026-10-12 (46975 matched / 66 diverged) and is not in the gate. The duplication is also wider than DDL: `ClusterServerSession` wraps `tidb_session::Session` and re-routes DDL, accounts, `SET GLOBAL`, ANALYZE, the statistics statements, transactions and row storage (`StatementRoute`). Milestone 3 here and Milestone 4 of the one-engine plan are therefore one program, one session over one store as Go's `testkit` runs every test, and Milestone 4 of this plan (execution details) would have to be built twice before it. Order: (1) a production replay baseline at HEAD, sharded; (2) that replay joins the gate with exact budgets and becomes the alignment measure; (3) its divergences are fixed first; (4) 3b/3c give `Session::new()` the production stack and test modules move onto it one gate at a time; (5) 3d/3e delete the in-process tier. The `CatalogDdl` wrapper proposed for the end of 3a is dropped: the in-process arms take the AST while the seam takes the lowered `DdlStatement`, so the wrapper would be an adapter 3d deletes.

Structure first, symptoms later, by direction of the user on 2026-10-17. Harness visibility comes before every refactor so that regressions show. The stale-recording list is explicit and exact rather than a tolerance, so a recording that becomes correct again has to be removed by hand.
