## TO_BASE64 encodes the argument's BYTES, so a non-string argument is
## stringified first (1 -> 'MQ==', 1.1 -> 'MS4x') and whitespace inside the
## input is data, not separator. FROM_BASE64 is the inverse and additionally
## IGNORES whitespace in its input -- space, tab, CR and LF may appear anywhere
## between base64 characters, which the escaped row below is there to pin.
##
## Refused from the Go tables: every TO_BASE64 row whose expected output
## exceeds 76 characters. MySQL wraps the encoding with a newline every 76
## characters, and this corpus's golden format is one result per line, so a
## wrapped result cannot be represented. FROM_BASE64 covers the same long
## vectors from the other direction (its outputs contain no newline), so the
## wrapping rule is the only thing left unguarded here. For the same
## one-result-per-line reason, FROM_BASE64('YWIKYw==') -- whose result 'ab\nc'
## contains a real newline -- is refused; TO_BASE64('ab\nc') below covers that
## byte from the encoding side. Also refused: the
## `character_set_connection = 'gbk'` rows, which need session charset state,
## and the 32-bit-only `strings.Repeat("a", 1589695687)` row.
