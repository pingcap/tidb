  NOT enough: case 3 needs the exchange although 17 is functionally determined
  by hash column 9, because only equivalence closures count.

## Parity gap assessment

Nothing the test exercises exists in this workspace:

- `NeedMPPExchangeByEquivalence` / `checkEquivalence`: no Rust port anywhere
  (workspace-wide grep). `tidb-planner/src/physical_property.rs` deliberately
  omits `MPPPartitionCols` (header defers "MPP partitioning ... functional-
  dependency sets, and physical-property construction" to future planner
  layers) and has no such method.
- `MPPPartitionColumn`: no Rust type; only `MppPartitionType`/
  `ExchangeKind` classifications are ported.
- The caller chain agrees: `tidb-planner/src/enforce.rs`
  (`the_mpp_exchanger_refuses_by_name`) records `EnforceExchanger` itself as
  unported.
- The FD primitives used by the Go builders do exist as
  `tidb-funcdep::FdSet::{add_equivalence, add_strict,
  closure_of_equivalence}`, but `tidb-proto` does not depend on that crate
  (and adding a dependency would exceed this batch's edit scope). More
  importantly, even with FDs at hand there is no ported decision function to
  assert against; hand-reimplementing Go's subset/equivalence walk inside the
  test body would pin our derivation, not Go's behavior, which the method
  forbids ("never approximate").

Per the batch method (§4) the single test is therefore recorded as an ignored
go-parity gap carrying the full re-derived intent (case table + fixture
contents) so the future porter can implement directly from it. This follows
the established in-workspace precedent (`tidb-funcdep/src/tests_extract_fd.rs`,
`tidb-chunk/src/tests_alloc.rs`). No golden files or testdata are required;
there are no actively passing assertions to add, because there is no Rust
surface under test yet. No files outside `rust/crates/tidb-proto/src/` and
this receipt were touched; no parity gaps were closed by approximation.
