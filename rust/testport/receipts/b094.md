## Why every item is a documentary port

As with neighbouring parts 15/16/18/19, all sixty Go entries are execution
benchmarks needing a live session: `prepareBenchSession` (:72) boots the mock
store + domain, per-access fixtures DDL the partitioned table and `analyze
table t` (`preparePointGet` :196 five rows; `prepareIndexLookup` :218 /
`prepareTableScan` :224 both feeding the doubling inserts of `insert1kRows`
:203 → 1024 rows), then either `runPointSelect` (:122: `explain <query>`
first row must satisfy `strings.HasPrefix` :166, `FoundInPlanCache` hits
counted :182-183, `expectHits` :159-160 excludes [Batch]PointGet) or
`runPreparedPointSelect` (:852: `PrepareStmt` :859, b.N ×
`ExecutePreparedStmt` :866, hits counted unconditionally at :866-868 AND a
second time per iteration at :877-880 when enabled and `i > 0`, log-only
starvation check `hits < b.N/2` :892-894, TODO :856-857 = no EXPLAIN check).
The `tidb-planner` crate has no session/executor/plan-cache layer (no
`FoundInPlanCache`, no mock-store bootstrap). No Rust surface exists for
these contracts and none was approximated; each port keeps Go's `Benchmark`
name shape so the gate filter `not test(/bench/)` excludes it exactly as
`go test` skips Benchmarks. Load-bearing behaviors recorded in the port
file's header:

1. Range schemes (`:54-56`) use boundaries 10/1000/100000/maxvalue with
   partition names p0, p1, p3, pMax — no `p2` in any of the three strings.
2. `getListPartitionDef` (:516-538) generates p0=(1..256),
   p1=(5000..5255), p2=(10000..10255), p3=(99900..100155), and because
   every call site in this part passes a non-empty `expr`, the
   `expr != "" && i == 1` branch (:527-531) appends value `0` to partition
   `p0` — the range loop binds `i` to the *value* 1 whose `partID` is 0.
   This corrects (withdraws) the part16 port file's doc-comment claim that
   the extra value lands in "p1"; part18's file already recorded `p0`.
3. For every partitioned scheme the batch-IN query's expected plan is
   `TableReader` — statically in these standalone benchmarks, and at
   runtime inside the umbrellas via `benchmarkPointGetPlanCache`
   :248-252 ("Batch_Point_Get is not yet enabled for partitioned tables!").
4. `expectHits` (:159-160) counts plan-cache hits only for
   IndexLookUp/TableReader; [Batch]PointGet never registers hits ("already
   using the FastPlan" :159).
