## Re-derivation notes

### TestSQLDigestTextRetriever → ignored gap

The Go test exercises only the MOCK half of the retriever
(`pkg/expression/util.go:1883` type decl through `:2049`, end of
`RetrieveGlobal`). With `mockLocalData` / `mockGlobalData` set,
`runFetchDigestQuery` (`util.go:1922`) short-circuits to `runMockQuery`
(`util.go:1905`) before any use of the executor argument — which is why the
test passes literal `nil` for it (`util_test.go:462`). The asserted contract
is map merging only:

1. `RetrieveLocal(ctx, nil)` (`util.go:1970`) over `{digest1..digest5}` all
   empty fills only digests present in `mockLocalData`: digest1→text1,
   digest2→text2; digest3/4/5 stay `""`; an unrequested mock entry (digest6)
   never appears. Source of the fill rule: `updateDigestInfo`
   (`util.go:1956`) overwrites only previously-empty slots with query hits.
   The wholesale-map shortcut in `RetrieveLocal`'s ≤fetchAllLimit branch
   (`len(queryResult) == len(SQLDigestsMap)` → replace and return) does NOT
   fire here because the filtered result has 2 entries vs the requested 5.
2. `RetrieveGlobal(ctx, nil)` (`util.go:2004`) runs RetrieveLocal first, then
   queries exactly the still-empty digests through `mockGlobalData`:
   digest3→text3 and digest4→text4 are added; digest5 stays `""`; unrequested
   digest7 stays absent.
3. With `fetchAllLimit = 1` (constructor default 512, `util.go:1898`) both
   calls produce identical results: five keys exceed the limit so the
   "fetch all" branch passes empty `inValues`, and `runMockQuery` returns its
   whole data table unchanged (`util.go:1907`), after which
   `updateDigestInfo` still merges only into empty slots.

Since none of this surface exists on the Rust side (the boundary decision is
recorded at `src/expr_util/mod.rs:115`, not re-decided by batch b077), the
port is written as an `#[ignore]`d documentary test in `src/tests/util_source.rs`;
behavior is NOT approximated. Reason string cites the go-parity-gap rule.

### TestProjectionBenefitsFromPushedDown → verified port

The production switch reads ONLY node kind, function name, and — for
JSON_UNQUOTE — the grandchild structure:
`ProjectionBenefitsFromPushedDown` (`util.go:1683`: *Column counts refs,
*ScalarFunction switches on lowercase name over the 11-function JSON
whitelist plus JSONUnquote fallback `jsonUnquoteFunctionBenefitsFromPushedDown`
at `util.go:1665` = arg0 is CAST whose arg0 is JSONExtract, everything else
returns false; pure-column case requires pruning `colRefCount <
inputSchemaLen`). Coercibility metadata on args (`newConstString(...,
CoercibilityNone, ...)`) plays no role in the function under test.

Row-by-row against origin/master (cast built at `util_test.go:489`, rows at
`util_test.go:490–512`, loop at `:514–517`):

- `{[col0, col1], 5} → true` and `{[col0, col1], 2} → false`:
  pure-column benefit ⇔ pruning (`util.go:1702–1704` area of the final
  `if allColRef` return).
- Column 0 + 11 whitelisted JSON functions (JSONExtract/JSONDepth/
  JSONLength/JSONType/JSONValid/JSONContains/JSONContainsPath/JSONKeys/
  JSONSearch/JSONMemberOf/JSONOverlaps) over input schema length 3 → true.
- `[JSONUnquote(<string column>)]` at `util_test.go:508` → false; and
  `[JSONUnquote(CAST-as-string(JSONExtract(...)))]` at `util_test.go:511` →
  true via the grandchild check.

Pre-existing Rust test `go_projection_benefits_from_pushed_down`
(`src/expr_util/tests.rs:970`) pins exactly these five rows plus one extra
negative case (`abs(col)` blocks push-down). The Rust fixture substitutes
plain string/int constants for Go's json-typed columns/coercibility-tagged
constants — observable-equivalence-preserving for THIS function per the
source reading above; ports live at
`src/expr_util/predicates.rs:363` (`projection_benefits_from_pushed_down`)
and `:337` (`json_unquote_benefits_from_pushed_down`). Go's
`forcePushDownTiKV` failpoint short-circuit has no failpoint mechanism here
and is not part of the tested contract.

(`eq(c0,c1)`, `eq(c1,c2)`, `eq(c2,c3)`, `eq(c3,1)`, `or(1,c0)` — conditions
