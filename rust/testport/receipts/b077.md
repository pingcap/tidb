## Re-derivation notes

### TestSQLDigestTextRetriever → ignored gap

The Go test exercises only the mock half of the retriever. With
`mockLocalData` / `mockGlobalData` set, `runFetchDigestQuery`
(`util.go:1922`) short-circuits to `runMockQuery` (`util.go:1905`) before any
use of the executor argument — which is why the test passes literal `nil`
for it (`util_test.go:462`). The asserted contract is map merging only:

1. `RetrieveLocal(ctx, nil)` over `{digest1..digest5}` all empty fills only
   digests present in `mockLocalData`: digest1→text1, digest2→text2;
   digest3/4/5 stay `""`; an unrequested mock entry (digest6) never appears.
   Source of the fill rule: `updateDigestInfo` (`util.go:1956`) overwrites
   only previously-empty slots with query hits.
2. `RetrieveGlobal(ctx, nil)` (`util.go:2004`) runs RetrieveLocal first, then
   queries exactly the still-empty digests through `mockGlobalData`:
   digest3→text3 and digest4→text4 are added; digest5 stays `""`; unrequested
   digest7 stays absent.
3. With `fetchAllLimit = 1` both calls produce identical results: five keys
   exceed the limit so the "fetch all" branch passes empty `inValues`, and
   `runMockQuery` returns its whole table for empty input (`util.go:1906`),
   after which `updateDigestInfo` still merges only into empty slots.

Since none of this production surface exists on the Rust side, the behavior
remains unclaimed. The former `#[ignore]`d documentary function had no
executable assertion and was removed; implementing only the mock branch would
not establish parity with the SQL-executor and system-table behavior.

### TestProjectionBenefitsFromPushedDown → verified pre-existing port

The pre-existing Rust test predates batch partitioning; this batch
re-verified each of its assertions against origin/master row-by-row:

- `{[col0, col1], 5} → true` and `{[col0, col1], 2} → false`: pure column
  projections benefit only when they prune (`colRefCount < inputSchemaLen`,
  `util.go:1705`).
- The 12-expression row (column 0 plus JSONExtract/JSONDepth/JSONLength/
  JSONType/JSONValid/JSONContains/JSONContainsPath/JSONKeys/JSONSearch/
  JSONMemberOf/JSONOverlaps) over schema length 3 → true.
- `[JSONUnquote(<string column>)]` → false; and
  `[JSONUnquote(CAST-as-string(JSONExtract(...)))]` (`util_test.go:486`
  builds the cast) → true via `jsonUnquoteFunctionBenefitsFromPushedDown`
  (`util.go:1665`).

One substitution difference exists between the fixtures: Rust builds args as
int/string constants where Go uses json-typed columns and constants with
coercibility metadata. This is observable-equivalence-preserving because the
function under test (`util.go:1683`, port at
`src/expr_util/predicates.rs:363`) inspects ONLY node kind, function name,
and — for JSON_UNQUOTE — the grandchild structure; argument types play no
role. All other rows match structurally 1:1. Go's `forcePushDownTiKV`
failpoint short-circuit (`util.go:1685`) has no failpoint mechanism here and
is not part of the tested contract.
