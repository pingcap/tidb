## Results

The Go nightly endpoint had no plan or result errors in either mode. The Rust
endpoint produced the same error set in both modes:

| item | result |
| --- | --- |
| Rust plan errors | Q6, Q9, Q10, Q35, Q45, Q69 (6/42) |
| Rust result errors | Q3, Q6, Q9, Q10, Q35, Q45, Q62, Q65, Q69, Q79, Q85, Q90, Q99 (13/42) |
| result hashes equal | 28/42; Q41 returned rows with a different hash; 13/42 errored |
| normalized plan hashes equal | 0/42 in this smoke snapshot |

Error families are:

- Q6/Q9: `uncorrelated scalar-subquery evaluation is not available to the planner`;
- Q10/Q35/Q45/Q69: `Unsupported("expression form is not yet supported by the rewriter")`;
- Q3/Q65: `an index-join inner HashJoin must contain one retained lookup reader`;
- Q62/Q79/Q85/Q90/Q99: `a physical expression does not resolve in its child`.

Across successful timed queries, the median of per-query p50 values was
`29.784 ms` for Go source, `124.971 ms` for Rust source (4.20x), `14.802 ms`
for Go control, and `130.449 ms` for Rust control (8.81x). This is one smoke
run, not a performance gate; the error population also makes it unsuitable as
a complete Rust-vs-Go performance conclusion.

## Status and next package boundary

This latest tip does not meet the requested parity criteria. The immediate
Rust work items are planner/executor subquery lowering and physical-column
resolution, followed by retained lookup-reader construction for index joins;
the unsupported TiFlash/MPP executor path remains a separate plan-parity gap.
The corresponding Go source packages must be inventoried before any Rust
transcreation claim or fix is merged. No production code was changed for this
snapshot.
